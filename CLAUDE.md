# Kinopeer

A qBittorrent web UI built around movies and TV series. Find a title in TMDB, pick a release via Prowlarr, send it to qBittorrent, and manage downloads. No playback. Mobile-first PWA with a desktop layout. Installs on umbrelOS.

## Product

- Core principle: find a title, pick a release and download it without leaving Kinopeer.
- Not doing: playback, Sonarr/Radarr-style automation (watchlists, RSS, new episodes), a season picker on the series page, tracker logins or getting around site protection, Jackett, telemetry. Only Umbrel installs are supported for now.
- What each screen does and the log of product decisions: `docs/SPEC.md`.

## Stack

- Vite + React 19 + TypeScript (strict), Node.js 22.18+ (the tests: 22.22.2+, 24.15+ or 26+, jsdom's range)
- oxlint for linting
- Vitest + Testing Library (jsdom) for tests
- Playwright screenshot tests (`e2e/`), run in the Playwright Docker image, and smoke journeys through the production server (`e2e/smoke/`), run on the host
- GitHub Actions CI: lint, typecheck, test, build, the screenshot tests and the smoke journeys on every PR and on push to `main`, grouped per PR, so a push cancels its PR's run in progress, while every push to `main` runs to the end. A ruleset on `main` requires a pull request and the `check`, `docker`, `visual` and `smoke` checks (not an up-to-date branch) and blocks force pushes and deletion, so `gh pr merge --auto` waits for those checks; another lets only the repository's admins create, move or delete `v*` tags. Every workflow is read-only at the top and gives write permissions only to the job that needs them; actions are pinned by commit SHA with their version in a comment, and the Playwright image by digest; checkouts keep no token (`persist-credentials: false`) unless the job pushes with it; the release job takes nothing from the Actions cache (the image's layers, QEMU's binfmt image, and buildx should the action ever download it), which any job on `main` can write to; the deploy secrets live only in the `deploy` environment, which only `main` and `v*` tags can use (`docs/DEVELOPMENT.md` → The TMDB proxy), and a job that needs one names it
- Dependabot (`.github/dependabot.yml`): monthly grouped updates for npm in the root and in `tmdb-proxy/` and for the workflows' actions (their SHA pins and version comments), each version a week old at least; `@playwright/test` is left to us, since it moves with the Playwright image the screenshot baselines are rendered in, and so are `@types/node`'s majors, which follow the Dockerfile's Node
- Stryker mutants over a branch's changed lines (`scripts/mutants.mjs`, `stryker.config.mjs`): run by the author before marking a PR ready, and in CI on every push to the head of a ready PR whose changes include the code or what Stryker runs with (the workflow's `paths`), the latest one only (`.github/workflows/mutants.yml`), whose `Mutants report` check on the commit the review reads (a check, not a PR comment, so it emails no one); a branch with no production line changed, a dependency bump among them, gets Stryker's dry run instead, so a bump that breaks Stryker shows there

## Commands

```sh
npm run dev        # dev server at http://localhost:5173
npm test           # Vitest, single run
npm run test:coverage  # the same with a coverage report and its threshold
npm run test:mutants   # breaks the lines this branch changes, lists the breaks no test noticed
npm run lint       # oxlint
npm run typecheck  # tsc -b
npm run build      # production build into dist/
npm start          # production server (server/main.ts) serving dist/
npm run test:visual         # screenshot tests in Docker
npm run test:visual:update  # re-render their baselines
npm run test:smoke          # smoke journeys in Chromium through the production server, no Docker
```

Run lint, typecheck, test and build before pushing, and the screenshot tests when the UI changes. CI must be green before merge.

## Conventions

- Everything in the repo and on GitHub is in English: code, comments, docs, commit messages, PR titles and descriptions, issues.
- Nothing in the repo or on GitHub names a real tracker or indexer, links a real release or torrent page, or uses a real release group's name: not in code, comments, test data, screenshots, docs, commits, PRs, issues or Discussions. A public torrent client that points at specific trackers and uploads invites takedown notices. Test data uses `Indexer A`, `Indexer B`…, URLs on `example.org`, `example.com` or `.test`, and made-up groups (`-GRPA`); a release name keeps a real naming style with a movie's title, which is TMDB data. A fact about how some indexers behave says "some indexers". The one exception is product logic that has to know a name, such as the voice-over studios `parseRelease` recognizes, with its own test (`docs/TESTING.md` → Shared test data).
- UI copy is localized (Russian and English) with i18next. Never hardcode user-facing strings: add keys to both `src/i18n/locales/en.json` and `ru.json` (a test checks they match). Russian plurals need `_one`, `_few`, `_many` and `_other` keys.
- One meaning, one key. Before adding UI copy, search `src/i18n/locales/en.json` for the same meaning, not only the same words: if it's there, use its key, and a text that includes it as a whole sentence nests it with `$t(key)` rather than repeating it (a fragment nested into another sentence breaks Russian grammar; `src/i18n/locales.test.ts` checks every nested key exists). A new key that words the same meaning differently, shorter for a tight spot say, is the exception, and its PR says why the existing one didn't fit (#312, where a hint was written three ways before it became one key).
- Work in small, reviewable PRs, one issue or less each. A PR's title says its kind with a prefix, `feat:`, `fix:`, `chore:` or `docs:`, which the squash merge keeps in `main`'s log; the branch's name is free (Claude Code names its own `claude/…`). Once a PR has its "ready to merge", it takes only fixes of what it already does: a new request, the owner's included, is a PR of its own from `main` after this one merges (#336, where 10 of 19 findings came after its first verdict, from three commits of new requests and their fixes).
- Never push to `main` directly; open a PR. Every PR targets `main`, never another feature branch: the owner squash-merges, often several in a row, and a stacked PR would land in its stale base. Work that depends on an open PR waits for it to merge, then rebases onto `main`. Merge only after the owner approves.
- Before starting, say so if a request is suboptimal by any measure (performance, maintainability, developer experience, workarounds in code, security, UX, cost, complexity): name the risks and the alternatives, and let the owner decide. Product decisions aren't fixed: the owner is ready to revise one or drop a feature for performance, developer experience or other technical gains, so when changing the product is the better trade-off, offer that as an alternative too.
- While working, too: when a task grows past what it was expected to be (a change of a few lines needs new hooks or workarounds, each fix uncovers the next problem, review rounds keep finding bugs in the same new mechanism), stop and ask the owner before going on, a session started by another through its coordinator. Say what it grew into (lines, new mechanisms, what will need maintaining), what it gains (numbers), and the options, a simpler version and dropping it included. A risk named in the task is a reason to weigh its cost, not to fix it at any price (#252, closed unmerged: +514 lines of frame-timed hooks and clipping workarounds for a gain seen only on a throttled CPU).
- Feature ideas, ours included, go to GitHub Discussions → Ideas, so they can be upvoted. Issues are for bugs and for work we've decided to do. A deferred issue is closed as not planned with a link to its idea.
- Keep the docs current: when a change affects them, update them in the same PR. Behavior or a product decision → `docs/SPEC.md` (and its decision log); a shipped issue → the PR closes it (`Closes #N`); setup, environment variables or releases → `docs/DEVELOPMENT.md`; user-visible changes → `CHANGELOG.md` and, if needed, `README.md`; architecture → `docs/ARCHITECTURE.md`.
- The plan is GitHub's milestones, one per version (`gh api repos/kinopeer/kinopeer/milestones`), each with the issues it ships; anything to settle before a version is an issue in its milestone. `docs/RELEASE_CHECKLIST.md` lists what to check before every release.
- Keep Kinopeer runnable without its server: installing with Docker Compose beyond Umbrel (the 1.1 milestone) and a qBittorrent Alternative WebUI (its own milestone) are planned. A new server feature either has a browser fallback (as torrent-to-title matches do) or is an extra the app works without, and pure logic (name and release parsing, picking a title) imports no React, DOM or Node APIs.
- Every PR covers what it changes with tests, each statement on one layer, the lowest that sees it (`docs/TESTING.md` → Choosing a layer): tests sit next to the code as `*.test.ts(x)`, query by role and accessible name. A change without a test says why in the PR's Tests section, with one of the accepted reasons (`docs/TESTING.md` → Saying why something is uncovered); "later" or "trivial" aren't reasons. A flaky test is fixed or deleted, never retried. Before marking a PR ready, its author (for an outside contributor's PR, the maintainer's session: `docs/TESTING.md` → Reviewing a PR's tests) runs `npm run test:mutants` and accounts for each survivor in the PR, sees every new or changed test fail with the code it covers broken, and fills the Tests table (`docs/TESTING.md` → A test that can fail). Before it merges (Dependabot's PRs aside, `docs/TESTING.md` → Reviewing a PR's tests), a separate session reviews it with `/test-review <PR#>` (`.claude/skills/test-review/`, which reads the Tests section first) and `/code-review`, and runs a second round after the fixes, re-checking the tests written for them. Every round is posted on the PR with the commit both reviews saw, and the PR merges only on a posted "ready to merge" at its current head; a commit of its own after it needs another round, and a merge of `main` one only when it reaches the PR's own lines or a file the PR changes other than `CHANGELOG.md`, SPEC's decision log and `CLAUDE.md`, else the author's `Merged main at <sha>` comment carries the verdict over (`docs/TESTING.md` → Reviewing a PR's tests). The author answers each round with a `Fixes for round <n>` comment. A bug `/code-review` finds in the PR's own change is fixed in that PR, red test first. Review findings are tagged so the retro after every twenty merged PRs can fix the rules where findings repeat (`docs/TESTING.md` → Improving the system).
- A bug that reached `main` (found on the test stand, on Umbrel or by a test) is an issue of the Bug type first, with its steps, environment and a `test-gap:*` label, then a red test on its layer, then the fix; the PR's "Why tests missed it" section names the class (`docs/TESTING.md` → When we find a bug). Behavior that works as `docs/SPEC.md` describes it but turned out a poor choice is a Feature, without that procedure (the same section). A problem of the tests, CI or the development tools that no user meets, such as a flaky test, is a Task, still with a `test-gap:*` label when the tests missed it (the same section).
- A PR that changes how a screen covered by the screenshot tests looks updates its baselines in the same PR and lists the changed screens: `docs/TESTING.md` → Screenshot tests.
- Accessibility basics are a requirement: real `<button>`/`<a>`/`<input>`, labels on icon-only buttons, touch targets ≥ 44px, `prefers-reduced-motion` respected. Keyboard navigation and focus management (tab order, where focus goes when something opens or closes) aren't a goal for now. Focus rings show only on keyboard navigation: style them with `:focus-visible` and `outline: var(--focus-ring)`, which `src/lib/inputModality.ts` turns off after a click or tap, since browsers also match `:focus-visible` when a dialog opens or the app moves focus.

## Design

- The design lives in Claude Design: the Kinopeer canvas (screens for mobile, desktop, states; a reference as of 0.4.0, no longer kept in sync) at https://claude.ai/code/artifact/d36cd9ea-367d-40f4-9cca-b5ae066c5c19 and the Kinopeer design system (tokens, components, README) at https://claude.ai/artifact/Hezz9q11HdhKm5P2bW3MTn.
- The design system's `tokens.json` is the source of truth for colors, type, spacing, radii, shadows and motion. Use the CSS custom properties, never raw hex values in components.
- The canvas shows how a screen should look, not how to build it. Implement a design the way the codebase does things: tokens, the wrapper's `gap`, shared components and existing patterns, never the canvas's inline styles, pixel values or element structure. Match the look, not the markup.
- Spacing (`gap`, `padding`, `margin`) and radii go through the tokens in `src/styles/tokens.css` (`var(--space-N)`, `var(--r-*)`). A raw px value is for what the scale doesn't have (an offset made of other elements' sizes), with a comment on its line saying why; `src/styles/tokens.test.ts` checks both.
- Type goes through the design system's roles, `--t-display` … `--t-mono` in `tokens.css` (a `font` shorthand each, plus `--t-*-tracking` where the role has letter-spacing): a screen's text gets the `t-*` class (`src/styles/base.css`) in the TSX, a component's own text gets `font: var(--t-*)` in its stylesheet, so its look stays in its CSS. The role sets the size, line-height and family; an element's weight is its own (`font-weight` after the role). The `font` shorthand resets `font-variant-numeric`, so an element that also needs `ks-num` takes the class, or sets tabular figures after the shorthand. A raw `font-size` or `line-height` in px is for what a role can't express (16px in inputs, so iOS Safari doesn't zoom), with a comment; the same test checks it.
- Space between siblings comes from their parent's `gap` (flex or grid), one value on the wrapper, not from margins on the children: a child with a `margin-top` to "fix" its distance is a sign the wrapper's `gap` is wrong. Margins are for exceptions (a negative offset, an element that leaves the flow), with a comment. When porting from the canvas, don't copy its inline margins.
- Dark theme is primary; light and "follow system" are supported.
- Desktop layout from 1024px (`DESKTOP_QUERY` in `src/lib/breakpoints.ts`; stylesheets repeat it as `@media (min-width: 1024px)`, since media queries can't use custom properties). There `App` renders `Sidebar` (`ks-side`, an icon rail up to 1100px, then 248px with labels) in place of `TabBar`. `useIsDesktop()` (`src/lib/useIsDesktop.ts`) is for behavior that differs on desktop (what renders); differences only in looks stay in CSS. In tests jsdom has no matchMedia, so the phone layout applies unless a test calls `stubDesktop()` (`src/lib/stubDesktop.ts`). Fixed elements offset themselves by `--nav-left` (the sidebar's width, 0 on phones) and `--nav-bottom` (the tab bar's height, 0 on desktop) from `tokens.css`. Screenshot tests use `DESKTOP` (1440×900) and `DESKTOP_RAIL` (1024×768) from `e2e/app.ts`.
- Overlays: `Sheet` (`src/components/Sheet`) is a bottom sheet on phones and a centered modal on desktop, in CSS only; `size="lg"` is for long lists (full height on phones, 680×720 on desktop). On a phone its top (the grabber and the title row, `.ks-sheet-handle`) drags it down to close it, through `useSheetDrag` (`src/components/Sheet/useSheetDrag.ts`), with the close rule (how far, how fast) in the pure `shouldClose` (`sheetDrag.ts`): the drag follows the finger inline, the spring back is the stylesheet's transition and the slide off the screen a Web Animation of the same length. Sheets sit above the on-screen keyboard: Safari on iOS and Chrome on Android open it over the page and shrink only the visual viewport, so `trackKeyboardInset` (`src/lib/keyboardInset.ts`, started in `main.tsx`) keeps the part of the page above it in `--keyboard-inset`, `--visible-top` and `--visible-height` on `<html>` from `visualViewport`, and `Sheet.css` places and sizes sheets by them, a gap above the keyboard while `--keyboard-open` is 1. While a `Sheet` or a `Dialog` is open, `holdPage` (`src/lib/holdPage.ts`) keeps the page behind still on a touch screen, where iOS Safari scrolls it with the keyboard open despite `overflow: hidden`: it stops swipes that nothing in the modal scrolls, moves a text field out of the page for the frame it gets focus in (for `NAVIGATION_HOLD_MS` when the keyboard's previous and next buttons moved focus there, since Safari scrolls to such a field a moment later) so Safari doesn't scroll to it, brings the field into view in its own scroller instead, and from the moment a modal with such a field opens (`Sheet` and `Dialog` hand `holdPage` their element) keeps the window a pixel from the top (the very top brings Safari's collapsed toolbar back) and the page in place with the body's negative margin, because on a page scrolled further opening the keyboard takes the window to the top in Safari and scrolling back leaves the layout viewport up by the keyboard's height, with sticky bars and the backdrop in it. It's done as the modal opens because doing it as a field gets focus jumps on a phone, and only for such a modal because a link in another one leaves the page's real place for the browser to bring back. On a touch screen (`pointer: coarse`), while any modal is open, `html:has(:modal)` in `base.css` keeps the page behind from scrolling. Not under a mouse: there it would hide a classic scrollbar (Windows) and shift the page by its width, and `scrollbar-gutter: stable` would also reserve the room where scrollbars are hidden, as in the screenshot tests' Chromium. `Dialog` is a centered confirmation (`alertdialog`) on both. `Accordion` (`src/components/Accordion`) is a full-width toggle with a chevron over what it shows or hides, rendered only while open; with `heading` it's a page's section (a region named by its toggle in an `h2`): the torrent page's Details and Files and the add sheet's Options. Both are native modal `<dialog>`s in the top layer, so they ignore `--nav-left`. On desktop, `Popover` (`src/components/Popover`, the design system's `ks-pop`) opens next to its anchor button: rendered in place (so it works inside a modal `<dialog>` and keeps the tab order), it handles placement, Escape with focus back to the anchor, and closing on a click outside, focus leaving, a scroll or a resize (`follow` keeps it on an anchor in a sticky bar instead). `Menu` (`role="menu"` with arrow keys) is built on it; the desktop release filters use it directly.
- Below the desktop breakpoint, screens sit in a centered column of `--column` width on wide screens; the tab bar's tabs stay over it.
- One accent color (teal). Status colors are separate from the accent; "downloading" is the only status in the accent color.
- Font: Onest. Numbers that update (speeds, sizes, percentages) use tabular figures.
- The app, not the canvas, is the reference for how screens look and behave: changes are built in code and shown on the test stand, and the canvas isn't updated. Draw on the canvas only when the owner asks for it, e.g. to compare variants of a new screen side by side.

## Workflow

- The author's and the reviewer's sessions hand rounds to each other directly: the reviewer posts the round and messages the author, the author posts `Fixes for round <n>` and messages the reviewer. The coordinator (the session that hands out the PRs) takes part only in questions to the owner and in merges.
- In the owner's sessions, a big change to the docs (a new section, a new or rewritten rule, an edit across several docs) starts with clarifying questions to the owner. Then the session shows the owner drafts of the wording in Russian and waits for approval, and only then writes the English text and opens the PR. Without drafts go small edits (a typo, a link, a stale fact), docs that describe a code change in the same PR, a release's `CHANGELOG.md` section and the retro's row in `docs/TESTING.md`'s table (the rules a retro changes do get drafts). An outside contributor with a big change opens an issue or an idea first, as `CONTRIBUTING.md` says.
- The test stand is the dev server (`npm run dev`, port 5173) on the owner's machine, running the branch under review. Start it when a PR has UI changes so the owner can try them before merging, and stop it when they're done. Don't leave detached processes (nohup, launchd) running there. In the Claude desktop app, start it as the `dev` configuration in `.claude/launch.json` (`dev-lan` is the same with `--host`, so the owner can open it on a phone at the Mac's LAN address; `preview` runs `npm run preview` on port 4173 after a build, and `preview-lan` the same with `--host`, for a PR that changes a phone screen, since the dev server has no manifest, so what it adds to the Home Screen isn't the installed app); no secrets go in that file.
- A release follows `docs/DEVELOPMENT.md` → Releasing: a PR with the version, the `CHANGELOG.md` section and the "as of version" line at the top of `docs/SPEC.md`; after it merges, the `v*` tag (pushed from the owner's machine, because the cloud git proxy refuses tag pushes); then a PR to the store repo with the new version, release notes and image digest. Tagging and the store PR need the owner's go-ahead.
