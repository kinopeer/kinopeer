# Kinoseed

A qBittorrent web UI built around movies and TV series. Find a title in TMDB, pick a release via Prowlarr, send it to qBittorrent, and manage downloads. No playback. Mobile-first PWA with a desktop layout. Installs on umbrelOS.

## Product

- Core principle: find a title, pick a release and download it without leaving Kinoseed.
- Not doing: playback, Sonarr/Radarr-style automation (watchlists, RSS, new episodes), a season picker on the series page, tracker logins or getting around site protection, Jackett, telemetry. Only Umbrel installs are supported for now.
- What each screen does and the log of product decisions: `docs/SPEC.md`.

## Stack

- Vite + React 19 + TypeScript (strict), Node.js 22.18+
- oxlint for linting
- Vitest + Testing Library (jsdom) for tests
- Playwright screenshot tests (`e2e/`), run in the Playwright Docker image, and smoke journeys through the production server (`e2e/smoke/`), run on the host
- GitHub Actions CI: lint, typecheck, test, build, the screenshot tests and the smoke journeys on every PR and on push to `main`

## Commands

```sh
npm run dev        # dev server at http://localhost:5173
npm test           # Vitest, single run
npm run test:coverage  # the same with a coverage report and its threshold
npm run lint       # oxlint
npm run typecheck  # tsc -b
npm run build      # production build into dist/
npm start          # production server (server/main.ts) serving dist/
npm run test:visual         # screenshot tests in Docker
npm run test:visual:update  # re-render their baselines
npm run test:smoke          # smoke journeys in Chromium through the production server, no Docker
```

Run lint, typecheck, test and build before pushing, and the screenshot tests when the UI changes. CI must be green before merge.

## Architecture

- The browser talks to qBittorrent and Prowlarr only through same-origin routes. `/qbt/api/*` → qBittorrent Web API, served by `server/qbittorrent.ts` (Vite middleware in dev using `QBITTORRENT_URL` from `.env.local`, and the production server). The server always logs in itself (login saved from the app's connect screen via `PUT /api/settings/qbittorrent`, else `QBITTORRENT_USERNAME`/`QBITTORRENT_PASSWORD`), keeps the session and re-logs in on a 403; after one rejected login it stops trying (IP-ban protection) and requests go without a session, so qBittorrent's auth bypass still works and otherwise the app asks for a login. Browser cookies never reach qBittorrent and `/qbt/api/v2/auth/*` is blocked. Never call those services cross-origin.
- TMDB goes through `/tmdb/*` → `https://api.themoviedb.org/3/*` (`server/tmdb.ts` adds the key, so it never reaches the browser) and images through `/tmdb-img/*` → `https://image.tmdb.org/t/p/*`. Client: `src/api/tmdb/`.
- Server-side settings: `server/settings.ts` keeps what the user enters in the app (the TMDB key, the qBittorrent login and the download defaults) in `$KINOSEED_DATA_DIR/settings.json` (default `./data`, git-ignored; `/data` volume in Docker). `GET /api/settings` says only whether each secret is set and where it comes from; `PUT /api/settings/tmdb` checks the key with TMDB, then saves it; `PATCH /api/settings/downloads` merges in the download defaults sent (`downloads` in `GET`, null until one is saved). A saved key wins over `TMDB_API_KEY`. Client: `src/api/settings/`. Onboarding asks for the key after qBittorrent connects (`src/session/useTmdbSetup.ts`, `src/screens/TmdbKeyScreen.tsx`); Settings → Connections changes it.
- Releases come from Prowlarr through `/prowlarr/*`, served by `server/prowlarr.ts` (Vite middleware in dev, and the production server), not a plain proxy: it adds `PROWLARR_API_KEY` and strips it from results, because Prowlarr's download links carry the key. The key is `PROWLARR_API_KEY`, else read on every request from Prowlarr's `config.xml` at `PROWLARR_CONFIG_XML` (the Umbrel package mounts it). `/prowlarr/search` returns `Release[]`; `/prowlarr/download?token=` returns the `.torrent` or `{ magnet }`; `/prowlarr/status` returns `{ version, indexers }` for the Settings connection check. Client: `src/api/prowlarr/`. Browser clients call these routes with `credentials: 'same-origin'`, because a proxy in front of Kinoseed (Umbrel's app_proxy) authenticates with cookies. Server code under `server/` runs in Node; its tests run in the `server` Vitest project (no jsdom).
- qBittorrent Web API client: `src/api/qbittorrent/` (incl. adding torrents, file lists and priorities). The add and move sheets get the categories, the default save path and the preferences that decide category folders through `getSaveLocations`, and `src/torrents/folders.ts` places a category's folder as qBittorrent's `categorySavePath` does. Moving files: `src/screens/useMoveTorrent.tsx` gives a screen the Move files sheet and runs the move itself, so its outcome shows as a toast even after the sheet was closed. `.torrent` files and magnet links are read in the browser (`src/torrents/torrentFile.ts`, `magnet.ts`) to get the info hash and files before adding; the hash goes through `src/lib/digest.ts`, which uses Web Crypto when the page has it and its own SHA-1/SHA-256 over plain HTTP, where `crypto.subtle` doesn't exist. Session state: `src/session/useQbitSession.ts` checks `app/version` first, so a working server login or qBittorrent's auth bypass goes straight in without a login form.
- Adding a release (`src/screens/AddReleaseSheet.tsx`, `FilePicker.tsx`): Kinoseed gets only the `.torrent` (preferred, so files can be picked) or magnet link from Prowlarr, then adds it to qBittorrent itself via `src/releases/addRelease.ts` with the `tmdb:<type>:<id>` tag, category, save path and options. Prowlarr's own download clients are not used. Skipped files: the torrent is added stopped, those files get priority 0, then it starts. After adding, the app goes to `/` with `{ added: title }` in the location state for a toast.
- Desktop Downloads (`useIsDesktop()`): the header keeps the name filter, the status as a `StatusMenu` (phones keep the chips), a type `Segmented` and the sort as a `SortMenu`, all on one row; the list is a table of `DownloadRow`s (columns from a CSS custom property, the title takes what the fixed columns leave; container queries show the size only from a 1240px table, and below 920px move the ETA under the speed, so the title keeps ≥ 200px), the grid is the phone's `DownloadCard`s with a Pause/Resume button on hover. Each layout keeps its own view (`downloadsView`, `downloadsDesktopView`, grid by default). `TorrentActionsSheet` and the sort become `Menu` popovers (`src/components/Menu`) when given an anchor on desktop. The sidebar's downloading count and qBittorrent card (`SidebarStatus`) read the shared poll in `App`; in the icon rail the count is a badge on the icon and the card a narrow column of speeds and free space. The table's first column (queue positions, or the checkboxes while selecting) shows only while selecting or when a torrent shown has a queue position (the Priority sort), via `.has-lead`. The header is sticky; the table's head row group sticks under it at the header's height, which `useHeightVar` (`src/lib/useHeightVar.ts`) keeps in `--downloads-head` on the screen, and its menus take `follow` so they stay open while the list scrolls. On phones only `.downloads-bar` (chips, sort, view, the selection row) is sticky, under the scrolling title and totals.
- Multi-select in Downloads: `DownloadsScreen` keeps the selected hashes (null outside selection mode); rows and cards (`DownloadItem`, `DownloadCard`) become checkboxes, and `BulkActionsBar` (pause, resume, delete through `DeleteTorrentDialog`, which takes several torrents) replaces the tab bar, which `App` hides through `onSelectingChange`. Actions apply only to selected torrents the filters show.
- Torrent state: `src/torrents/useMainData.ts` polls `sync/maindata` every 2 s (only while the tab is visible, and right away when the device comes back online) and merges the incremental deltas. `App` wraps the screens in `MainDataProvider` (`src/torrents/MainDataProvider.tsx`), so every `useMainData()` under it shares one poll, which runs only while something uses it and keeps the last state between screens; outside a provider (tests) the hook polls on its own. Never start a second poll for the same data. When qBittorrent stops answering, screens keep the last state under `OfflineBanner` (its age, actions disabled) or show an unreachable state before the first answer; `src/screens/ErrorBoundary.tsx` shows a crash screen with Reload instead of a blank page; `src/torrents/status.ts` maps qBittorrent states to the design's statuses. Sizes, speeds and ETAs go through `src/lib/format.ts`.
- Routing: React Router (`react-router`). `App.tsx` routes `/` (downloads), `/search`, `/torrent/:hash` (torrent details: `TorrentScreen` on a phone; on desktop a drawer, `TorrentDrawer`, a native modal `<dialog>`, both showing `TorrentDetails`. A link from another page passes it as background in the navigation state (`overPage` in `src/lib/background.ts`; the title page's `TitleDownloads` does), and `App` renders the routes for that background location with `TorrentDrawerOverPage` on top, which closes by going back and tells the sidebar which page is behind. Without a background, as from Downloads or on a direct load, `DownloadsWithDrawer` renders Downloads with the drawer), `/title/:type/:id` (type is `movie` or `tv`, id is the TMDB id; its "In downloads" block, `TitleDownloads.tsx`, lists the title's torrents through `useTitleTorrents` in `titleMatches.ts`; at the page's end `TitleRelated.tsx` shows TMDB's recommendations, else its similar titles, in a `PosterRow`, the Search screen's browse row), `/title/:type/:id/releases` (Prowlarr results with quality filters; `src/releases/parseRelease.ts` reads resolution, source, HDR, voice-over, seasons and episodes from release names; searches don't filter by category, because some indexers such as RuTor file every release under "Other"; both title paths render `TitleRoute`: on phones the releases path is `ReleasesScreen`, on desktop it is the title page with `TitleReleases` under the hero, which "Find releases" opens by replacing the title's path, so nothing is searched until it's pressed; the desktop hero's overview is `TitleOverview.tsx`, cut to five lines with Show more while it's clipped (`scrollHeight > clientHeight`, measured again when fonts load or the width changes); the search, filters and sort live once in `src/screens/useReleases.ts` with the pure filtering in `src/releases/filterReleases.ts`, the shared states in `ReleasesBlock.tsx`) and `/settings` behind the tab bar; `server/static.ts` falls back to `index.html` for these paths. Search's rows before a search are TMDB Discover queries by digital or disc release date and recently aired episodes (`src/search/browseRows.ts`), so they show what's likely on torrents already; search state (`q`, `type`) lives in the URL; the scroll position comes back on Back through `useScrollRestoration` (`src/lib/useScrollRestoration.ts`, position per history entry in sessionStorage, restored once the screen says its content is loaded, since the browser's own restore runs while the page is still short).
- Download rows show the TMDB title and poster: `src/torrents/titleMatches.ts` takes the user's choice from the server, else a `tmdb:<movie|tv>:<id>` torrent tag (Kinoseed adds it when sending a release), else a guess the server keeps, else guesses from the release name (`parseName.ts`) by searching TMDB and saves the guess on the server. Titles and guesses are also cached in localStorage. Bump `GUESS_VERSION` when guessing changes, so old guesses are redone. The Downloads type filter (in `SortSheet.tsx`, not remembered) uses `titleType`: the matched title's type, else the lookup's (a known title, season markers, the category).
- Torrent-to-title matches: `server/matches.ts` keeps them by info hash in `$KINOSEED_DATA_DIR/matches.json` (`{ type, id, source: 'user' | 'guess', version }`), not in qBittorrent tags. `GET /api/matches`, `PATCH /api/matches` (a guess never replaces the user's choice), `PATCH` with `null` forgets a torrent (`forgetMatches` after deleting it), `DELETE /api/matches` forgets the guesses (Settings → Clear cache). The server checks qBittorrent's torrents every hour (`startMatchesCleanup`, through `qbittorrentBridge().get` with the server's session) and forgets a match once its torrent has been missing for a week (`missingSince`). Client: `src/api/matches/`, shared state in `src/torrents/serverMatches.ts` (loaded once, guesses saved in batches, the user's choice saved right away by `chooseMatch`). The user changes a title in `src/screens/ChangeTitleSheet.tsx` (TMDB search) or confirms a guess in `MatchPrompt.tsx`, both through `chooseTitle` in `titleMatches.ts`; `isGuessed` tells whether to ask. They open from `TorrentActionsSheet` (the row's and the torrent screen's More menu) and the torrent screen. Both data files go through `server/jsonFile.ts` (atomic writes, one at a time).
- Preferences live in `src/settings/settings.ts` (localStorage, `useSettings`, `useTmdbLanguage`). TMDB language, list or poster grid and the sort in Downloads (`src/torrents/sort.ts`) are per browser. The download defaults (category per type, start paused, sequential) are also kept on the server: `useSettings` loads them once per page (`loadServerSettings`) and the server's win, a change is saved to both, a default the server doesn't have yet is sent from the browser that changed it, and without the server the browser's copy applies. Connection settings stay on the server: service addresses in its environment, the TMDB key and the qBittorrent login in its settings file. The theme (`src/theme/theme.ts`, `useTheme`) and the interface language (`src/i18n/language.ts`, `useLanguage`) are their own per-browser stores, each `'system'` by default and following the system's (the browser's languages, `languagechange`) while that's chosen; change the language through `setLanguagePreference`, not `i18n.changeLanguage`, so the choice is saved.
- PWA: `vite-plugin-pwa` builds the manifest (in `vite.config.ts`) and the service worker from `src/sw.ts` (injectManifest, own tsconfig `tsconfig.sw.json`, which also compiles its smoke test `src/sw.test.ts`). It precaches the app shell, serves `index.html` for app routes, caches `/tmdb-img/*` posters and never caches `/qbt`, `/prowlarr` or `/tmdb`; those rules live in `src/pwa/swRoutes.ts`, apart from workbox, with their own test. A new version activates right away (no lazy chunks, so open pages keep working). The service worker is off in `npm run dev`; try it with `npm run build && npm run preview`. Icons: SVG sources in `scripts/icons/`, PNGs rendered by `scripts/render-icons.mjs`. Service workers need HTTPS (or localhost); umbrelOS 2.0 serves apps over HTTPS with its own certificate, and Kinoseed sets up nothing for it. Over plain HTTP there is no `crypto.subtle` either, so hashing goes through `src/lib/digest.ts`. Push notifications aren't planned.
- Production: `server/main.ts` is a dependency-free Node server (run as `.ts` through Node's type stripping, so server code must stay erasable TypeScript with `.ts` import paths) that chains the routes `kinoseedServer()` builds (the `server/` middleware and `/healthz`, shared with Vite's dev and preview servers, which also run its `startJobs()`), and `server/static.ts` (serves `dist/`, `index.html` for app routes, hashed `/assets/*` cached for a year, everything else incl. `sw.js` revalidated, Brotli/gzip). `Dockerfile` builds it into a `node:24-alpine` image with no `node_modules`; config comes from environment variables only. Installs are supported on Umbrel only; the package lives in the `homelab-kinoseed/` folder of https://github.com/MrShakhov/umbrel-homelab-store.
- Releases: semver in `package.json` (Vite injects it as `__APP_VERSION__`, shown in Settings → About), notes in `CHANGELOG.md`. A `v*` tag runs `.github/workflows/release.yml`: multi-arch image to `ghcr.io/mrshakhov/kinoseed` and a GitHub Release. Add user-facing changes to `CHANGELOG.md` under the next version as they land.
- Screens live in `src/screens/`, shared UI components in `src/components/` (ported from the design system with the same class names).

## Conventions

- Everything in the repo and on GitHub is in English: code, comments, docs, commit messages, PR titles and descriptions, issues.
- UI copy is localized (Russian and English) with i18next. Never hardcode user-facing strings: add keys to both `src/i18n/locales/en.json` and `ru.json` (a test checks they match). Russian plurals need `_one`, `_few`, `_many` and `_other` keys.
- Work in small, reviewable PRs, one roadmap step or less each. Branch names: `feat/…`, `fix/…`, `chore/…`, `docs/…`.
- Never push to `main` directly; open a PR. Every PR targets `main`, never another feature branch: the owner squash-merges, often several in a row, and a stacked PR would land in its stale base. Work that depends on an open PR waits for it to merge, then rebases onto `main`. Merge only after the owner approves.
- If a request is suboptimal by any measure (performance, workarounds in code, maintainability, security, UX, cost, complexity), say so and suggest alternatives before starting, and let the owner decide.
- Feature ideas, ours included, go to GitHub Discussions → Ideas, so they can be upvoted. Issues are for bugs and for work we've decided to do. A deferred roadmap item moves to "Later" with a link to its idea.
- Keep the docs current: when a change affects them, update them in the same PR. Behavior or a product decision → `docs/SPEC.md` (and its decision log); a shipped roadmap item → tick it in `docs/ROADMAP.md`; setup, environment variables or releases → `docs/DEVELOPMENT.md`; user-visible changes → `CHANGELOG.md` and, if needed, `README.md`; architecture → this file.
- Anything to settle before the public release goes into `docs/RELEASE_CHECKLIST.md`, which also lists what to check before every release.
- Keep Kinoseed runnable without its server: plain Docker and a qBittorrent Alternative WebUI are planned (`docs/ROADMAP.md`, Later). A new server feature either has a browser fallback (as torrent-to-title matches do) or is an extra the app works without, and pure logic (name and release parsing, picking a title) imports no React, DOM or Node APIs.
- Every PR covers what it changes with tests, each statement on one layer, the lowest that sees it (`docs/TESTING.md` → Choosing a layer): tests sit next to the code as `*.test.ts(x)`, query by role and accessible name. A change without a test says why in the PR's Tests section, with one of the accepted reasons (`docs/TESTING.md` → Saying why something is uncovered); "later" or "trivial" aren't reasons. A flaky test is fixed or deleted, never retried. Before marking a PR ready, its author sees every new or changed test fail with the code it covers broken, and fills the Tests table (`docs/TESTING.md` → A test that can fail). Before it merges, a separate session reviews it with `/test-review <PR#>` (`.claude/skills/test-review/`, which reads the Tests section first) and `/code-review`, and runs a second round after the fixes, re-checking the tests written for them. A bug `/code-review` finds in the PR's own change is fixed in that PR, red test first. Review findings are tagged so the retro after every ten merged PRs or each release can fix the rules where findings repeat (`docs/TESTING.md` → Improving the system).
- A bug that reached `main` (found on the test stand, on Umbrel or by a test) is an issue first, with its steps, environment and a `test-gap:*` label, then a red test on its layer, then the fix; the PR's "Why tests missed it" section names the class (`docs/TESTING.md` → When we find a bug).
- A PR that changes how a screen covered by the screenshot tests looks updates its baselines in the same PR and lists the changed screens: `docs/TESTING.md` → Screenshot tests.
- Accessibility basics are a requirement: real `<button>`/`<a>`/`<input>`, labels on icon-only buttons, touch targets ≥ 44px, `prefers-reduced-motion` respected. Keyboard navigation and focus management (tab order, where focus goes when something opens or closes) aren't a goal for now. Focus rings show only on keyboard navigation: style them with `:focus-visible` and `outline: var(--focus-ring)`, which `src/lib/inputModality.ts` turns off after a click or tap, since browsers also match `:focus-visible` when a dialog opens or the app moves focus.

## Design

- The design lives in Claude Design: the Kinoseed canvas (screens for mobile, desktop, states; a reference as of 0.4.0, no longer kept in sync) at https://claude.ai/code/artifact/d36cd9ea-367d-40f4-9cca-b5ae066c5c19 and the Kinoseed design system (tokens, components, README) at https://claude.ai/artifact/Hezz9q11HdhKm5P2bW3MTn.
- The design system's `tokens.json` is the source of truth for colors, type, spacing, radii, shadows and motion. Use the CSS custom properties, never raw hex values in components.
- The canvas shows how a screen should look, not how to build it. Implement a design the way the codebase does things: tokens, the wrapper's `gap`, shared components and existing patterns, never the canvas's inline styles, pixel values or element structure. Match the look, not the markup.
- Spacing (`gap`, `padding`, `margin`) and radii go through the tokens in `src/styles/tokens.css` (`var(--space-N)`, `var(--r-*)`). A raw px value is for what the scale doesn't have (an offset made of other elements' sizes), with a comment on its line saying why; `src/styles/tokens.test.ts` checks both.
- Type goes through the design system's roles, `--t-display` … `--t-mono` in `tokens.css` (a `font` shorthand each, plus `--t-*-tracking` where the role has letter-spacing): a screen's text gets the `t-*` class (`src/styles/base.css`) in the TSX, a component's own text gets `font: var(--t-*)` in its stylesheet, so its look stays in its CSS. The role sets the size, line-height and family; an element's weight is its own (`font-weight` after the role). The `font` shorthand resets `font-variant-numeric`, so an element that also needs `ks-num` takes the class, or sets tabular figures after the shorthand. A raw `font-size` or `line-height` in px is for what a role can't express (16px in inputs, so iOS Safari doesn't zoom), with a comment; the same test checks it.
- Space between siblings comes from their parent's `gap` (flex or grid), one value on the wrapper, not from margins on the children: a child with a `margin-top` to "fix" its distance is a sign the wrapper's `gap` is wrong. Margins are for exceptions (a negative offset, an element that leaves the flow), with a comment. When porting from the canvas, don't copy its inline margins.
- Dark theme is primary; light and "follow system" are supported.
- Desktop layout from 1024px (`DESKTOP_QUERY` in `src/lib/breakpoints.ts`; stylesheets repeat it as `@media (min-width: 1024px)`, since media queries can't use custom properties). There `App` renders `Sidebar` (`ks-side`, an icon rail up to 1100px, then 248px with labels) in place of `TabBar`. `useIsDesktop()` (`src/lib/useIsDesktop.ts`) is for behavior that differs on desktop (what renders); differences only in looks stay in CSS. In tests jsdom has no matchMedia, so the phone layout applies unless a test calls `stubDesktop()` (`src/lib/stubDesktop.ts`). Fixed elements offset themselves by `--nav-left` (the sidebar's width, 0 on phones) and `--nav-bottom` (the tab bar's height, 0 on desktop) from `tokens.css`. Screenshot tests use `DESKTOP` (1440×900) and `DESKTOP_RAIL` (1024×768) from `e2e/app.ts`.
- Overlays: `Sheet` (`src/components/Sheet`) is a bottom sheet on phones and a centered modal on desktop, in CSS only; `size="lg"` is for long lists (full height on phones, 680×720 on desktop). `Dialog` is a centered confirmation (`alertdialog`) on both. Both are native modal `<dialog>`s in the top layer, so they ignore `--nav-left`. On desktop, `Popover` (`src/components/Popover`, the design system's `ks-pop`) opens next to its anchor button: rendered in place (so it works inside a modal `<dialog>` and keeps the tab order), it handles placement, Escape with focus back to the anchor, and closing on a click outside, focus leaving, a scroll or a resize (`follow` keeps it on an anchor in a sticky bar instead). `Menu` (`role="menu"` with arrow keys) is built on it; the desktop release filters use it directly.
- Below the desktop breakpoint, screens sit in a centered column of `--column` width on wide screens; the tab bar's tabs stay over it.
- One accent color (teal). Status colors are separate from the accent; "downloading" is the only status in the accent color.
- Font: Onest. Numbers that update (speeds, sizes, percentages) use tabular figures.
- The app, not the canvas, is the reference for how screens look and behave: changes are built in code and shown on the test stand, and the canvas isn't updated. Draw on the canvas only when the owner asks for it, e.g. to compare variants of a new screen side by side.

## Workflow

- The test stand is the dev server (`npm run dev`, port 5173) on the owner's machine, running the branch under review. Start it when a PR has UI changes so the owner can try them before merging, and stop it when they're done. Don't leave detached processes (nohup, launchd) running there. In the Claude desktop app, start it as the `dev` configuration in `.claude/launch.json` (`dev-lan` is the same with `--host`, so the owner can open it on a phone at the Mac's LAN address; `preview` runs `npm run preview` on port 4173 after a build); no secrets go in that file.
- A release follows `docs/DEVELOPMENT.md` → Releasing: a PR with the version, the `CHANGELOG.md` section and the "as of version" line at the top of `docs/SPEC.md`; after it merges, the `v*` tag (pushed from the owner's machine, because the cloud git proxy refuses tag pushes); then a PR to the store repo with the new version, release notes and image digest. Tagging and the store PR need the owner's go-ahead.
