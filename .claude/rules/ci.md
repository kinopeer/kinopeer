# CI, Dependabot, the checks guard and the mutants

Part of the stack (`CLAUDE.md` → Stack). Claude Code loads this file with the workflows, the scripts and the checks' config.

- GitHub Actions CI: lint, typecheck, test and build, the speed budgets (the build's size, each screen's requests on opening and each move's between screens, the `performance` job, which also reads each screen's layout shift on a phone and on desktop), the screenshot tests with their accessibility budgets and both sets of smoke journeys on every PR and on push to `main`, grouped per PR, so a push cancels its PR's run in progress, while every push to `main` runs to the end. A ruleset on `main` requires a pull request with one approving review, dismissed when the PR's diff changes, and the `check`, `docker`, `visual`, `smoke`, `guard` and `performance` checks (not an up-to-date branch) and blocks force pushes and deletion, so `gh pr merge --auto` waits for those checks; another lets only the repository's admins create, move or delete `v*` tags. Every workflow is read-only at the top and gives write permissions only to the job that needs them; actions are pinned by commit SHA with their version in a comment, and images by digest (Node's in the `Dockerfile`, BuildKit's in the image builds, whose built-in Dockerfile frontend the `Dockerfile` uses, the Playwright image, qBittorrent's in `scripts/test-smoke-webui.sh`); the image builds set up no QEMU, since the `Dockerfile`'s runtime stage runs nothing on the target platform; checkouts keep no token (`persist-credentials: false`) unless the job pushes with it; the release job takes nothing from the Actions cache (the image's layers, and buildx should the action ever download it), which any job on `main` can write to; the deploy secrets live only in the `deploy` environment, which only `main` and `v*` tags can use (`docs/DEVELOPMENT.md` → The TMDB proxy), and a job that needs one names it
- Dependabot (`.github/dependabot.yml`): monthly grouped updates for npm in the root and in `tmdb-proxy/`, for the workflows' actions (their SHA pins and version comments) and for Node's image in the `Dockerfile` (its digest), each version a week old at least; `@playwright/test` is left to us, since it moves with the Playwright image the screenshot baselines are rendered in, and so are `@types/node`'s and Node's image's majors, which move together; BuildKit's image, which Dependabot can't see, moves by hand before every release (`docs/RELEASE_CHECKLIST.md`)
- The checks guard (`scripts/guard/`, `docs/QUALITY.md`): a script with no AI in it that the `guard` job runs on every PR (`.github/workflows/guard.yml`), `main`'s copy of the script over the PR's branch, which it reads through git without running any of its code (the workflow file itself runs as the PR has it), and over the lists of the tests each side ran, which the workflow's `tests` job makes with no permission to write, since the branch's code runs there (the `guard` job, which can write checks, takes those lists as data and nothing from the Actions cache, which `tests` can write to). It writes into the PR's `guard report` check, as its summary, what weakens the checks (a threshold lowered, a lint rule turned off, a command CI ran no longer run, retries, fewer tests run), what adds a design value (a token added, changed or removed in `src/styles/tokens.css`, a value off the scale that a comment lets through, by the definition of a raw value `src/styles/tokens.test.ts` shares, `scripts/guard/stylesheets.ts`) and what changes existing ones (an assertion rewritten or removed in a test that stays, a test renamed); it holds nothing: the `guard` job passes whatever it marks and fails only when the guard breaks or can't write its report, so a mark emails no one. The deputy judges every mark in its round (the `deputy` skill → The round), and the `guard` job is one of `main`'s required checks. The thresholds and the exclusion lists of coverage and the mutants, and the budgets (the build's size, each screen's and each move's requests, a screen's layout shift, what axe finds broken in each screenshot's state, and how far a screenshot's pixel may drift from its baseline), sit in `checks.json`, as data, so it compares them exactly: a new one goes there, not into the config that uses it
- Stryker mutants over a branch's changed lines (`scripts/mutants.mjs`, `stryker.config.mjs`, with the folders mutated and what is left out in `checks.json`): run by the author before marking a PR ready, and in CI on every push to the head of a ready PR whose changes include the code or what Stryker runs with (the workflow's `paths`), the latest one only (`.github/workflows/mutants.yml`), whose `Mutants report` check on the commit the review reads (a check, not a PR comment, so it emails no one); a branch with no production line changed, a dependency bump among them, gets Stryker's dry run instead, so a bump that breaks Stryker shows there
