# The two builds, preferences and the PWA

## The two builds

One source, two builds (`buildTarget` in `vite.config.ts`): `npm run build` into `dist/`, the app Kinopeer's server serves, and `npm run build:webui` (Vite's mode `webui`) into `dist-webui/public/`, the Alternative WebUI that qBittorrent serves itself, with no Kinopeer server (#360 and its milestone). qBittorrent's Alternative WebUI folder is `dist-webui/`: it serves the files under its `public/` folder, and once signed in those under `private/` first, which the build has none of. A request for `/` that finds no `public/index.html` there is a 500, and from qBittorrent 5.2 (in `qbittorrent-nox`) it also turns the Alternative WebUI off in qBittorrent's settings; any other path that isn't a file is a 500, which is why the routes go after the `#`. Code branches on `__WEBUI__` (`src/webui.d.ts`), a constant the build defines as it does `__APP_VERSION__`, so each bundle drops the other's branch and the server's build doesn't grow for the WebUI; a pure module doesn't read it (`pure-logic.md` → Pure logic), its caller passes in what it needs. The tests run with it false; a test of the WebUI's branch stubs the global (`vi.stubGlobal`) and imports the module again, as `src/lib/appRouter.test.tsx` does. Besides its router (`screens.md` → Routing), it differs in how it reaches the services, what it shows and how it ships (`webui.md` → The WebUI build). CI's `check` job builds both, and the size budget counts the server's.

## Preferences

Preferences live in `src/settings/settings.ts` (localStorage, `useSettings`, `useTmdbLanguage`; `initSettingsSync`, started in `main.tsx` like `initLanguage`, reads them again when another tab saves them; the release filters and sort are checked when read). TMDB language, list or poster grid, the sort in Downloads (`src/torrents/sort.ts`) and the release filters and sort are per browser (`useReleases` starts a search from the remembered filters through `startingFilters` in `filterReleases.ts`, which sets aside what the results don't meet, alone or together; `ReleasesBlock` names what's set aside with Forget). The download defaults (category per type, start paused, sequential, first and last pieces first, notify when finished) are also kept on the server: `useSettings` loads them once per page (`loadServerSettings`) and the server's win, a change is saved to both, a default the server doesn't have yet is sent from the browser that changed it, and without the server the browser's copy applies. Connection settings stay on the server: service addresses in its environment, else in its settings file when saved from the app, and the TMDB key and the qBittorrent login in its settings file. The theme (`src/theme/theme.ts`, `useTheme`) and the interface language (`src/i18n/language.ts`, `useLanguage`) are their own per-browser stores, each `'system'` by default and following the system's (the browser's languages, `languagechange`) while that's chosen; change the language through `setLanguagePreference`, not `i18n.changeLanguage`, so the choice is saved and the language's texts are loaded first. The texts aren't in the main bundle: `showLanguage` (`src/i18n/language.ts`) imports a language's file the first time the page shows it, then switches, and the last language asked for wins over one still loading; it resolves to false when the file can't be loaded, and `useLanguage`, which the places that switch use (Settings, `Preferences` on the sign-in and connect screens), then says so in a toast in the language still shown; `main.tsx` waits for the first one before rendering, so neither the keys nor the other language flash. The size budget counts one language file, the heaviest ([QUALITY.md](QUALITY.md) → The size budget), and the requests budget counts none, as with the rest of the build's files.

## PWA

PWA: `vite-plugin-pwa` builds the manifest (in `vite.config.ts`) and the service worker from `src/sw.ts` (injectManifest, own tsconfig `tsconfig.sw.json`, which also compiles its smoke test `src/sw.test.ts`). It precaches the app shell, serves `index.html` for app routes (in the server's build; the WebUI build loads pages from the network first: `webui.md` → Shipping it) except a load with `PROXY_SIGN_IN_PARAM`, which has to reach the sign-in proxy (`server.md` → Prowlarr), caches `/tmdb-img/*` posters and never caches `/qbt`, `/prowlarr` or `/tmdb`; those rules live in `src/pwa/swRoutes.ts`, apart from workbox, with their own test. A new version activates right away. Open pages keep working because the app loads as one bundle, with one exception: each language's texts are a chunk of their own (`language-<code>-<hash>.js`, named by `chunkFileName` in `vite.config.ts`), loaded when the page shows that language (#492). They're precached with the shell, so either language opens offline, but the new version's precache drops the old ones, so a page an update left behind can't load the other language: `showLanguage` then calls the update check (`startUpdateChecks` registers it with `onLanguageUnavailable`), which reloads it into the new version when the server has one, and otherwise the page keeps the language it shows and the switch says so in a toast (`useLanguage`). The WebUI build's own texts (`src/i18n/locales/webui/`, `webui.md` → What the WebUI build shows) are a second chunk per language of that build, loaded in the same step, so a page an update left behind falls back the same way. No other lazy chunk: a new one would have the same problem. An open page reloads into it through `startUpdateChecks` (`src/pwa/updates.ts`, started in `main.tsx`): at startup and on every return to the foreground it compares `__APP_VERSION__` with `/version.json` (written by `versionFilePlugin` in `vite.config.ts`, not precached), and when they differ and no `dialog` is open and no field has focus it has the service worker take over first (over HTTPS) and reloads, once per version per session; `UpdatedToast` in `App` then names the new version. The service worker is off in `npm run dev`; try it with `npm run build && npm run preview`. Icons: SVG sources in `scripts/icons/`, PNGs rendered by `scripts/render-icons.mjs`. The touch icon iOS takes for the Home Screen goes into the built `index.html` as a `data:` URL (`inlineTouchIconPlugin` in `vite.config.ts`, from the file index.html's `<link>` names in `public/`): iOS fetches a linked one in a process of its own, which got nothing over Umbrel's HTTPS (#304). Service workers need HTTPS (or localhost); umbrelOS 2.0 serves apps over HTTPS with its own certificate, and Kinopeer sets up nothing for it. Over plain HTTP there is no `crypto.subtle` either, so hashing goes through `src/torrents/digest.ts`. The service worker also shows the server's push notifications (`push`), opens a tapped one's page in an open window of Kinopeer's or a new one (`notificationclick`), and saves a subscription the browser renewed in place of the old (`pushsubscriptionchange`): that logic is `src/pwa/swPush.ts`, apart from the worker's globals, with its own test.
