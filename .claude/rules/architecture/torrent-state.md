# Torrent state from the poll, and the titles matched to torrents

## Torrent state and the poll

Torrent state: `src/torrents/useMainData.ts` polls `sync/maindata` every 2 s (the app's poll intervals are in `src/torrents/pollIntervals.ts`, which imports nothing, so the requests test reads them by its path: `docs/QUALITY.md` → The requests budget; only while the tab is visible, and right away when the device comes back online; `refresh` polls right away, or once the poll in flight is answered, since that one went out before the change) and merges the incremental deltas (`applyMainData` in `sync.ts`), keeping only the fields of `Torrent`, listed in `TORRENT_FIELDS` beside the merge (a field of `Torrent` missing from the list fails to compile), and a torrent's object while none of those changed: qBittorrent reports `time_active`, `seeding_time`, `reannounce` and `popularity` for most running torrents on each poll. Downloads' rows (`DownloadItem`, `DownloadRow`, `DownloadCard`) are memoized on that, so with hundreds of torrents a poll renders only those that changed; the callbacks the screen hands them keep their identity. A poll unanswered after `POLL_TIMEOUT_MS` (10 s) is aborted and counts as offline; one in flight when the device comes back online or the page becomes visible is dropped and sent again at once, and one in flight when the page is hidden is dropped without counting as offline.

Besides the data's snapshot the store keeps the poll's own state (`PollState`: in flight, offline, `updatedAt`), a separate object handed out as `poll` (`PollSource`), so a request going out renders only what subscribes to it: `PollRing` (`src/screens/PollRing.tsx`), which fills in CSS over the interval from each answer, pulses while one is awaited and is red offline (two half rings that turn behind half-ring windows and an opacity pulse: only `transform` and `opacity` animate, which the compositor runs, since an arc's `stroke-dashoffset` repainted the page every frame, #220; its test checks the keyframes), in the phone's Downloads title row and as `SidebarStatus`'s `indicator` on desktop (a render prop, which gives the rail's ring the connection's status for its tooltip), where it replaced the connection dot.

`App` wraps the screens in `MainDataProvider` (`src/torrents/MainDataProvider.tsx`), so every `useMainData()` under it shares one poll, which runs only while something uses it and keeps the last state between screens, and its rhythm: started again, it waits for what's left of its interval since its last answer (`dueAt`, never longer than the interval, should the clock be set back), so a screen that comes back on a phone asks nothing at once, and `PollRing` mounts filled as far as the time since that answer (#385); a poll that got no answer (it failed, or was dropped as the store stopped or the page was hidden) and a `refresh` while the store is stopped leave nothing to wait for; outside a provider (tests) the hook polls on its own. Never start a second poll for the same data, and no one-off `getMainData` either: qBittorrent keeps one `rid` per session and the server's session is shared, so a `rid=0` outside the poll is a full answer and makes the poll's next answer a full one too. A screen that shows what's in downloads only in passing (the title cards' badge, #460) reads the poll without starting it: `useLastTorrents` (`useMainData.ts`) takes the store's last data through `watch`, which doesn't count as a subscriber, with what the torrent requests expect, as `useMainData` shows it, and hands the screen only what its `select` makes of the torrents, inside the subscription, so a poll that changes nothing the screen shows (by its `same`) renders nothing, and only when the page has none and no poll is asking, asks `torrents/info` once for the page (`oneOffTorrents.ts`): it looks as the screen opens and again each time the poll settles, since a poll in flight as the last screen that polled leaves is dropped unanswered.

When qBittorrent stops answering, screens keep the last state under `OfflineBanner` (its age, actions disabled) or show `UnreachableState` (`src/screens/UnreachableState.tsx`) before the first answer, and both, the poll's ring, the sidebar, the connect screen, Settings' qBittorrent check and a failed add (`AddReleaseSheet`) say who didn't answer: `unreachable` in `src/api/qbittorrent/client.ts` tells Kinopeer's server (a network failure, a sign-in proxy, or a failure without the bridge's `x-kinopeer-bridge` header, which `server/qbittorrent.ts` puts on every answer) from qBittorrent, the poll keeps it as `unreachable` beside `offline` and the session check as `who`, and the texts pick it as an i18next context through `unreachableText` (`src/lib/unreachable.ts`: `noAnswer.qbittorrent_kinopeer` for both of Kinopeer's cases, `unreached` and `kinopeer`); `src/screens/ErrorBoundary.tsx` shows a crash screen with Reload instead of a blank page; `src/torrents/status.ts` maps qBittorrent states to the design's statuses. Sizes, speeds and ETAs go through `src/lib/format.ts`, which keeps its `Intl.NumberFormat`s per language and digits, since building one costs far more than formatting with it. qBittorrent's free space goes through `freeSpace` (`src/torrents/freeSpace.ts`), which treats 0 or less as unknown.

## Titles in Downloads

Download rows show the TMDB title and poster: `useTitleMatches` (`src/torrents/useTitleMatches.ts`) takes the user's choice from the server, else a `tmdb:<movie|tv>:<id>` torrent tag (Kinopeer adds it when sending a release), else a guess the server keeps, else guesses from the release name (`parseName.ts`) by searching TMDB and saves the guess on the server; that order (`lookupFor`) and the pick among TMDB's results (`pickBest`) are pure logic in `titleLookup.ts`. TMDB is asked `CONCURRENCY` (3) at a time, one run per list and language (`startLookups`): a lookup joins its queue as its torrent comes and leaves it if the torrent goes before its turn, and none is stopped or asked again while the run lasts, which a title arriving would otherwise do with every answer (#239); a failed one (or one TMDB doesn't answer in `LOOKUP_TIMEOUT_MS`, 15 s) is asked again after `RETRY_DELAYS_MS` (30 s, 2 min, then every 10 min), not with the list's changes, and a 429 (`TmdbError.retryAfterMs`, from the `Retry-After` the server passes on) stops the run for that long, or `RATE_LIMIT_WAIT_MS`, then puts its lookup back in line. Titles show as they arrive at most every `SHOW_EVERY_MS` (250 ms), since each time the whole list renders again. Titles and guesses are also cached in localStorage, written at those moments and when the list goes away rather than with every answer: the titles' own data per language, which the server doesn't keep, and the guesses as the fallback without the server (a miss for a day, a title for 30 days), read only when the server has no match; a miss the server keeps (`lookupFor`'s `miss`) gives no title without asking TMDB. Bump `GUESS_VERSION` when guessing changes, so old guesses are redone. The title cards outside Downloads (Search's, `TitleRelated`'s) mark the titles in downloads through `useTitlesInDownloads`, which files `useLastTorrents`' torrents by title with only what's known without TMDB (`torrentsByTitle` in `titleDownloads.ts`: the user's choice, the tag, the server's guess, else the browser's cached guess through `cachedTitle`), so it starts no lookup, and gives each title its mark (`marksByTitle`, the title page header's rule, `downloadsMark`) as `useLastTorrents`' select, with `sameMarks` (the same titles, counts and whole percents, `wholePercent` in `src/logic/`, which `format.percent` uses too) as its `same`, so Search and the title page's related row render on a poll only when a mark changes; `InDownloadsMark` (`src/screens/`) shows it over the poster, a card without one gets none. The Downloads type filter (in `SortSheet.tsx`, not remembered) uses `titleType`: the matched title's type, else the lookup's (a known title, season markers, the category).

## Torrent-to-title matches

Torrent-to-title matches: `server/matches.ts` keeps them by info hash in `$KINOPEER_DATA_DIR/matches.json` (`{ type, id, source: 'user' | 'guess', version }`, or `{ source: 'miss', version }` for a guess that found no title, so no device asks TMDB again: `StoredTitle` and `StoredMiss` in `src/api/matches/types.ts`), not in qBittorrent tags, with no expiry by time (#461). `GET /api/matches`, `PATCH /api/matches` (a guess or a miss never replaces the user's choice, and nothing replaces a match of a newer version of guessing, nor a miss a guess of the same version, `replaces`), `PATCH` with `null` forgets a torrent (`forgetMatches` after deleting it), `DELETE /api/matches` forgets the guesses and misses (Settings → Clear cache). The server checks qBittorrent's torrents every hour (`startMatchesCleanup`, through `qbittorrentBridge().get` with the server's session) and forgets a match once its torrent has been missing for a week (`missingSince`). The store's rules (`replaces`, and `merged`, `pruned` and `withoutGuesses`, which answer what they're given when nothing changes) are pure logic in `src/logic/titleMatches.ts`, shared with the WebUI build's store (`webui.md` → Matches in qBittorrent); `server/matches.ts` imports it, so the `Dockerfile` copies that file of `src/` into the image beside `server/` (`server.md` → The production server). Client: `src/api/matches/`, shared state in `src/torrents/serverMatches.ts`, which `useServerMatches` (`useServerMatches.ts`) reads (loaded once, guesses saved in batches, the user's choice saved right away by `chooseMatch`). The user picks a title in `src/screens/ChangeTitleSheet.tsx` (TMDB search, given by `useChangeTitle` in `src/screens/useTitleChoice.tsx`, on the request manager: kind `title`, one save per torrent), saved through `chooseTitle` in `useTitleMatches.ts` as the user's choice, the title already shown too; nothing asks whether a guess is right (SPEC's decision log, 2026-11-13). It opens from `TorrentActionsSheet` (the row's and the torrent screen's More menu: Fix match, or Match title without a title); when no title was found, the torrent screen's More has a dot (`IconButton`'s `dot`, whose text is the button's accessible description; on a glass button it's the same light teal in both themes, elsewhere it follows the theme) and the menu's Match title is in the accent (`MenuItem`'s `highlight`, `.ks-row-btn.is-highlight` in the phone sheet), both reusable for anything else worth pointing at. Both data files go through `server/jsonFile.ts` (atomic writes, one at a time).
