# How the server reaches qBittorrent, TMDB and Prowlarr, and how it is served

## The qBittorrent bridge

The browser talks to qBittorrent and Prowlarr only through same-origin routes. `/qbt/api/*` → qBittorrent Web API, served by `server/qbittorrent.ts` (Vite middleware in dev using `QBITTORRENT_URL` from `.env.local`, and the production server). The server always logs in itself (login saved from the app's connect screen via `PUT /api/settings/qbittorrent`, else `QBITTORRENT_USERNAME`/`QBITTORRENT_PASSWORD`), keeps the session and re-logs in on a 403; after one rejected login it stops trying that login at that address (IP-ban protection; a new address or login is tried afresh) and requests go without a session, so qBittorrent's auth bypass still works and otherwise the app asks for a login. Browser cookies never reach qBittorrent. The bridge forwards only the calls `src/api/qbittorrent/` makes, each with its method (`ENDPOINTS` in `server/qbittorrent.ts`, matched on the path as written, so no `..` or encoded path reaches `/auth/*` or the preferences), and only requests with the `X-Kinopeer` header the client sends on every call: it attaches the server's session and rewrites `Origin` and `Referer`, so without that header a form on any other site could act through it, and a page can't add a header to a cross-origin request without a CORS preflight, which the bridge never allows (Vite's own CORS is off in `vite.config.ts`, since in dev and preview it would answer that preflight for any localhost origin before the bridge runs; `vite.config.test.ts` starts both servers from the config to check). The bridge also hands the server's own jobs its session (`qbittorrentBridge().get` and `post`): the matches cleanup and the notifications. A new qBittorrent call in the client goes into `ENDPOINTS` too, and into `EVERY_CALL` in `server/integration/qbittorrent.test.ts`, which doesn't compile without it and checks that each passes the bridge. Of qBittorrent's preferences, which hold its own login and web UI settings, the bridge lets only the default save path through: `BODY_FILTERS` reads an `app/setPreferences` body (16 KiB at most) and sends it on only as a form with one `json`, an object with nothing but a string `save_path`, written anew, and answers anything else 400 without asking qBittorrent, a query on the call among it. Never call those services cross-origin. Each bridge, and the checks behind `PUT /api/settings/tmdb`, `/prowlarr` and `/qbittorrent` (the TMDB key's with TMDB's time limit too), gives its request upstream up once the browser's request has gone before its answer (`abandoned` in `server/abandoned.ts`, taken before the first `await`), so a request the app stopped waiting for doesn't hold a connection to the service until it answers; the shared session's login isn't given up with it, since other requests wait for it too (a login saved from the connect screen is the browser's own attempt, and is). A write to qBittorrent given up that way has normally reached it whole already (its body is small and goes out at once), and the browser that left learns the outcome from the next poll either way.

## TMDB and its proxy

TMDB goes through `/tmdb/*` → `https://api.themoviedb.org/3/*` (`server/tmdb.ts` adds the key, so it never reaches the browser) and images through `/tmdb-img/*` → `https://image.tmdb.org/t/p/*`; a path that `fetch` wouldn't keep as written (dots, encoded dots, a backslash) or with an encoded slash or backslash is refused, since it would lead out of `/3/` or `/t/p/` (#305). Client: `src/api/tmdb/`. The bridge marks every answer with the qBittorrent bridge's `BRIDGE_HEADER`, so the client throws `KinopeerUnreachableError` for a failure without it, something in front of the server answering for it, and `TmdbFailedState` (`src/screens/`, the title page's, Search's, the phone's releases' and Fix match's state for a TMDB call that failed) tells by `unreachable` whether Kinopeer's server or TMDB didn't answer, with Open again where `useMayOpenAgain` says so, or that there's no key (#537); Search's banner for a next page that failed tells the same (#553). Kinopeer's own key sits behind a Cloudflare Worker, `tmdb-proxy/worker.ts` (`docs/DEVELOPMENT.md` → The TMDB proxy): it answers only the paths the client calls, has Workers Cache keep TMDB's answers (the Cache API does nothing on `workers.dev`) and limits calls per IP, an IPv6 caller by its /64. It gives CORS headers only to a page on a private origin (`isPrivateOrigin`: a LAN address or name, as qBittorrent serving Kinopeer as its Alternative WebUI is), with `Vary: Origin` on every answer, so Workers Cache keeps one per origin. Two workers, `kinopeer-tmdb-edge` deployed by `edge.yml` and `kinopeer-tmdb` by `release.yml`, both through `tmdb-proxy.yml`, which has no trigger of its own and deploys a worker only when its fingerprint (`tmdb-proxy/fingerprint.ts`) differs from the tag of the version it runs; each answers on a Workers Custom Domain, the release worker on `tmdb.kinopeer.com` and the edge worker on `tmdb-edge.kinopeer.com` (`wrangler.jsonc`'s `routes`, not `workers.dev`), so the deploy token needs Workers Routes on that zone. A new TMDB path in the client needs adding to its `ROUTES` too (and, outside `/3/`, to the WAF rule on `kinopeer.com` that DEVELOPMENT names), and a path is never removed or changed while a released version calls it: a breaking change goes into a new worker. The server sends calls without a key there (`proxyBase` in `server/tmdb.ts`, the address from `tmdbProxy` in `server/main.ts`: `TMDB_PROXY_URL`, else the edge worker baked into edge images and defaulted to by `vite.config.ts`, else the release worker), and `GET /api/settings` says `source: 'shared'` then, so onboarding skips the key step and Settings names Kinopeer's key. It sends no `Authorization` there, which Workers Cache would bypass. A call or an image TMDB (or the proxy) hasn't started answering in `TMDB_TIMEOUT_MS` (15 s, as long as the client's title lookups wait) is given up with a 504, while a body that has started may stream for longer (an image to a slow phone); qBittorrent's and Prowlarr's requests have no such limit, since a Prowlarr search across indexers can rightly take long, apart from `/prowlarr/failing`'s own and the checks behind `PUT /api/settings/qbittorrent` and `/prowlarr` (`ADDRESS_CHECK_TIMEOUT_MS`, 15 s, in `server/settings.ts`, past undici's 10 seconds to connect).

## Why a service didn't answer

When a request to qBittorrent or Prowlarr fails without an answer, `connectionFailure` (`server/connectionFailure.ts`) names why from what `fetch` threw, by the code in its `cause` (the same on Linux and macOS): `name` (the name doesn't resolve), `refused`, `timeout` (undici's time limits, the host unreachable, or the caller's own limit), `http` (an https address on a plain HTTP port), `certificate` (one the server doesn't trust) or `closed` (closed with no answer, or an answer that isn't HTTP), else nothing (#508). The list is `CONNECTION_FAILURES` in `src/api/connectionFailure.ts`, which the server imports only as a type. The checks behind `PUT /api/settings/qbittorrent` and `/prowlarr` send it as `failure` beside `unreachable`; the qBittorrent bridge sends it in `FAILURE_HEADER` (`x-kinopeer-failure`) beside its 502, since its answer is text, and the Prowlarr bridge as `failure` in its JSON. The clients keep it on their errors (`SettingsError`, `QbittorrentError`, `ProwlarrError`), only a cause this app knows (`knownFailure`), read through `failureOf`, and `failureText` (`src/lib/failureText.ts`) says what to check, naming the service, and for qBittorrent its Web UI where nothing listens. It's shown on the forms' address field or banner (`QbittorrentLoginForm`, `ProwlarrKeyForm`), in the connect screen's `UnreachableState` (the session's `failure`), in Settings' connection rows and in the releases' error state (`Releases.failure`), each saying what it said before when there's no cause. The poll doesn't read it. A refusal that does answer is told apart too where it would read as another: `checkQbittorrent` answers `host-refused` when qBittorrent's Host header validation refuses the address's port (`refusesHost` in `server/qbittorrent.ts`: after a login's 401, which qBittorrent 5.3 also gives a wrong password, the version asked without a session gets 401 rather than 403, and only qBittorrent's own 401, `isHostRefusal`: the text `Unauthorized` with the `X-XSS-Protection` qBittorrent puts on every answer and no `WWW-Authenticate`, so another 401 stays `not-qbittorrent` without a login and a wrong login with one, as before), which `PUT /api/settings/qbittorrent` sends as 502 `host-refused` and `QbittorrentLoginForm` says over the form.

## Prowlarr

Releases come from Prowlarr through `/prowlarr/*`, served by `server/prowlarr.ts` (Vite middleware in dev, and the production server), not a plain proxy: it adds `PROWLARR_API_KEY` and strips it from results, because Prowlarr's download links carry the key; how it reads Prowlarr's answers (the query, the releases, a .torrent, the failing indexers, a key's check) is `src/releases/prowlarrResults.ts`, which the WebUI build shares (`webui.md` → The transport). The key (`prowlarrKey` in `server/settings.ts`) is the one saved from Settings → Connections (`ProwlarrKeyForm`), else `PROWLARR_API_KEY`, else read on every request from Prowlarr's `config.xml` at `PROWLARR_CONFIG_XML` (the Umbrel package mounts it). `/prowlarr/search` returns `Release[]`; `/prowlarr/download?token=` returns the `.torrent` or `{ magnet }`; `/prowlarr/status` returns `{ version, indexers }` for the Settings connection check, whose answer About also shows (`SettingsScreen` runs the checks and both read them). `/prowlarr/failing?within=<ms>` names the enabled indexers that failed in that many milliseconds or are on hold (Prowlarr's search doesn't say), which `useReleases` asks once a search answers, without holding its results, for the count's line (`ReleasesCount` in `src/screens/ReleasesBlock.tsx`, which names them on a tap), or a note when there's no count to say it: under the empty state when nothing was found (#401), above the empty state when the filters let nothing through on a phone. A search the server can't send for want of Prowlarr's address or key (`not-configured`), or whose key Prowlarr refuses (`unauthorized`), throws `ProwlarrSetupError`, which `useReleases` gives as the `setup` or `rejected` status.; `ProwlarrSetupState` (`src/screens/`) then reads the server's settings (the page's shared answer, asked for only in that state), offers `ProwlarrKeyForm` in a sheet, with the address where the app can set it, as Settings does, and searches again once it's saved (#510). The bridge answers every failure with its code, so an answer without one, something in front of the server answering for it, throws `KinopeerUnreachableError`, as the TMDB client does; the `error` status says through `unreachable` whether Kinopeer's server or Prowlarr didn't answer, and for the first the releases' error state is the connect screen's `UnreachableState`, and the add sheet's failed fetch of the torrent and Settings' Prowlarr and TMDB rows say Kinopeer isn't answering, as Settings' Telegram row does only when nothing answered or a sign-in proxy redirected (#566). Client: `src/api/prowlarr/`. Browser clients call these routes, and every other route of Kinopeer's, through `fetchKinopeer` (`src/api/fetchKinopeer.ts`): with `credentials: 'same-origin'`, because a proxy in front of Kinopeer (Umbrel's app_proxy) authenticates with cookies, and with `redirect: 'manual'`, because Kinopeer's routes never redirect, so a redirect is that proxy sending the request to its sign-in on another origin once its cookie lapses (#303). Then `startProxySignIn` (`src/pwa/proxySignIn.ts`, started in `main.tsx`, which hands it to the clients through `onProxySignIn`, so they also run without a DOM) loads the screen the app is on again with `PROXY_SIGN_IN_PARAM`, at most once per `SIGN_IN_RETRY_MS`, and takes the parameter out of the address the proxy sends it back to; back from a sign-in it doesn't sign in again until a request is answered without a redirect (`answered`), so a cookie that doesn't stick can't loop. `loadPastTheShell` there is the same load without that limit, for Open again, which `UnreachableState`, `OfflineBanner` and the connect screen offer beside Retry (the second action of `Banner` and `EmptyState`) when `useMayOpenAgain` (`src/lib/unreachable.ts`) says nothing answered for Kinopeer's server (`unreached`, as against `kinopeer`, something answering for it), the device is online and a service worker controls the page: the browser then shows a sign-in or a certificate it no longer trusts (#311). Two actions in a `Banner` go under its text when the banner itself is narrow (a container query on it), with the icon at the title. The connect screen shows `UnreachableState` with the session check's texts (`texts="connect"`) in place of the form when that check got no answer. Server code under `server/` runs in Node; its tests run in the `server` Vitest project (no jsdom).

## The production server

Production: `server/main.ts` is a dependency-free Node server (run as `.ts` through Node's type stripping, so server code must stay erasable TypeScript with `.ts` import paths) that chains the routes `kinopeerServer()` builds (the `server/` middleware and `/healthz`, shared with Vite's dev and preview servers, which also run its `startJobs()`; first `securityHeaders` (`server/securityHeaders.ts`), so every answer has `nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: same-origin`, a `Permissions-Policy` and `Cross-Origin-Opener-Policy`, and no HSTS, since Kinopeer is also opened over plain HTTP; then `hostCheck` (The host check, below); `createApp` and `vite preview`, not the dev server, whose pages run Vite's inline scripts, also send `CONTENT_SECURITY_POLICY` (`contentSecurityPolicy`): only the app's own files, images also as `data:`, no inline script, so the theme applied before first paint is `public/theme.js` rather than inline in `index.html`, and a smoke journey fails on anything it blocks (`e2e/smoke/test.ts`); the qBittorrent bridge answers `no-store`, and the TMDB bridge passes on only JSON from the API and raster images, else `application/octet-stream`), and `server/static.ts` (serves `dist/`, `index.html` for app routes, hashed `/assets/*` cached for a year, everything else incl. `sw.js` revalidated, Brotli/gzip). `Dockerfile` builds it into a `node:24-alpine` image with no `node_modules`, and of `src/` only the modules the server imports for more than their types, each copied by name, which no other server module may count on: `src/logic/titleMatches.ts` (the matches store's rules) and `src/releases/prowlarrResults.ts` (Prowlarr's answers as the bridge and the WebUI build read them), whose own imports are types only, with `.ts` paths; config comes from environment variables only. The supported installs are listed in CLAUDE.md → Product. The Umbrel package lives in the `homelab-kinopeer/` folder of https://github.com/MrShakhov/umbrel-homelab-store; `docker-compose.yml` lets Kinopeer into qBittorrent without a login (`docs/DEVELOPMENT.md` → Docker); beside a qBittorrent and a Prowlarr the user runs, onboarding asks for their addresses (README → Install next to your own qBittorrent and Prowlarr), and Unraid's template is `unraid/kinopeer.xml` (DEVELOPMENT → Docker). The Alternative WebUI runs no server of Kinopeer's (`webui.md` → The WebUI build).

## The host check

`hostCheck` (`server/hostCheck.ts`, #356) answers a request only for the host names Kinopeer is meant to be reached at, against DNS rebinding: a page whose host name its owner points at Kinopeer's address is same-origin with it, so it can send the `X-Kinopeer` header the bridges ask for (above) and read every answer (and Kinopeer's own login's first-run setup and sign-in). What tells such a page apart is its `Host`, its own name. So by default the server answers only at names public DNS never answers for, which no one can register (`isPrivateHost`): an IP address, `localhost` and `*.localhost`, `*.local` (mDNS: `umbrel.local`), `*.onion`, `*.home.arpa`, `*.internal`, and a name of one label (a LAN name, a Docker service). `KINOPEER_ALLOWED_HOSTS` adds names (`kinopeer.example.com`) and domains (`.example.com`), and `*` answers at any name, which the Umbrel package sets, since Umbrel's app gateway, which keeps the `Host`, signs in first and its cookie doesn't go to a rebound name. Behind a reverse proxy the check sees what the proxy sends: a proxy that keeps the `Host` (nginx's `proxy_set_header Host $host`, Caddy's default) or sends the page's name in `X-Forwarded-Host` lets it refuse a rebound name, and each host in `X-Forwarded-Host` must be allowed too, which never lets through a request its `Host` doesn't. One that sends the upstream's address as `Host` and no `X-Forwarded-Host` (nginx's default, `$proxy_host`) hides the page's name: the check sees only the upstream's name, which it allows whenever the proxy works at all (an IP, a name of one label, `localhost`, a `.local` or `.internal` name, or one added to the variable), so behind such a proxy it protects nothing. A `server_name` alone refuses nothing there either, since nginx hands a `Host` that matches none to the port's default server, which with one `server` block is that block; only a catch-all `default_server` that turns unknown names away (`return 444`) does. DEVELOPMENT's row for the variable says to pass `Host` or `X-Forwarded-Host`. A refused request gets a 403 with a plain text naming the host and the variable to set; it's the second route, after the security headers, so it covers `/healthz` and the app's files as well. It runs in `vite` and `vite preview` with the other routes, behind Vite's own `server.allowedHosts`, whose default is stricter (no `.local`).

## Versions, release images and edge builds

Releases: semver in `package.json` (Vite injects it as `__APP_VERSION__`, shown in Settings → About), notes in `CHANGELOG.md`. A `v*` tag runs `.github/workflows/release.yml`: multi-arch image to `ghcr.io/kinopeer/kinopeer` and a GitHub Release. Every push to `main` that changes what goes into the image runs `.github/workflows/edge.yml`: unless the build's fingerprint (`scripts/edge/fingerprint.ts`, what the image would run and how it's built) matches the image the edge store runs, an arm64 `edge` image with the commit in its version (`KINOPEER_COMMIT`, `0.6.0+abc1234`), which it pins in the edge store's Kinopeer Edge app, so the owner's Umbrel offers it as an update (`docs/DEVELOPMENT.md` → Edge builds). Add user-facing changes to `CHANGELOG.md` under the next version as they land.
