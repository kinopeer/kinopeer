# Notifications when a download finishes: Telegram and Web Push

## Notifications

The server tells the user when a download finishes (`server/notifier.ts`): `startNotifier`, one of `startJobs()`'s jobs beside the matches cleanup, checks every `NOTIFY_INTERVAL_MS` (30 s), and only while a channel says it's `ready()`: with none it asks qBittorrent nothing. A pass asks for the torrents tagged `NOTIFY_TAG` (`kinopeer:notify`, the client's `NOTIFY_TAG` in `src/api/qbittorrent/client.ts`, which the integration test checks is the same) with `torrents/info?tag=` through the bridge's `get` and the server's session, never `sync/maindata`, whose `rid` the browsers' polls share; a finished one (`isFinished`: complete and in a seeding or stopped-after-finishing state) goes out through every ready channel, and the tag comes off through the bridge's `post` (`torrents/removeTags`), so the tag is the "notify once" flag and lasts across restarts. What each channel did with each torrent is kept in memory for the pass after: a channel that answered isn't sent to again, one that didn't is tried again after `RETRY_DELAYS_MS` (30 s, 2 min, then every 10 min) counted from the start of the pass that sent it, or the `retryAfterMs` it threw, counted from its answer as the service counts it, whichever ends later, and one that refused counts as done, with a line in the log. A channel is a `NotifyChannel` (`id`, `ready`, `send`, and `forget`, which the notifier calls for a torrent that lost its tag or went away while it was sent again, so a channel drops what it kept for it), so Web Push sits beside Telegram. The tag is switched from the torrent's page (`useNotifyToggle` in `src/screens/`, `addTags` and `removeTags` on the torrent requests, kind `notify`) and set when adding a release (`AddReleaseSheet`'s switch, starting from the `notify` download default), each shown only while `GET /api/settings` says `notifications` (some channel is set up: `useNotificationsAvailable`), and without it the default adds no tag.

Telegram (`server/telegram.ts`) is a small Bot API client: `botName` (`getMe`), `startedChats` (the chats that sent the bot `/start` among its last 100 pending updates, newest first, or `conflict` when Telegram answers 409 because a webhook or another program takes the bot's updates, which the settings' routes answer as 409 `bot-in-use`) and `sendMessage`, all with `TELEGRAM_TIMEOUT_MS` (15 s); a 429 or a 5xx throws `TelegramUnavailable` with Telegram's `retry_after`, a refusal answers `'rejected'`, and no error carries the token, which is part of the URL. `telegramChannel` (`server/telegramChannel.ts`) sends `finishedText` (`server/notifyText.ts`, with its texts in `server/locales/*.json`, the server's own translation files, so the app's bundle, which never shows them, doesn't carry them) in the language saved with the chat, and records in the settings which part Telegram refused (`refusedPart`: `getMe` tells the token from the chat), as long as the bot and chat are still the ones it sent to; when `getMe` doesn't answer, a refusal already recorded for that bot and chat stands, and otherwise `send` throws, so the notifier sends again and the next refusal says which part. The title comes from `finishedTitle` (`server/finishedTitle.ts`): the torrent's match on the server or its `tmdb:` tag, then TMDB through `tmdbJson` in `server/tmdb.ts` (the key or the proxy, with `TMDB_TIMEOUT_MS`), else the release name alone. The bot's token and chat are kept in `settings.json` (`StoredTelegram`) and set up through `/api/settings/telegram` (`PUT` the token, checked with `getMe`; `GET` and `PUT /chat` find the chat that sent `/start` and save it once the user has seen it, only while the token is the one it was found with; `POST /test`; `GET /check`; `DELETE`); `GET /api/settings` says only the bot's name, the chat's name and kind and which part Telegram refused (`telegram`), never the token. Client: `src/api/settings/`, the form in `src/screens/TelegramForm.tsx`, whose requests (the token, finding the chat, the chat, the test, turning off) go through Settings' saves as one target, kind `telegram`, so one is on its way at a time: the form open takes the outcome, else it's handed to Settings and said in a toast (a chat found then is forgotten).

Web Push (`server/webPush.ts`) is written on `node:crypto`, with no dependency, since the image ships no `node_modules`: `encryptPayload` encrypts a payload as RFC 8291 says (aes128gcm, one record of at most `MAX_PAYLOAD` bytes; its test checks RFC 8291's own example byte for byte), `vapidAuthorization` signs the request with the server's VAPID key (RFC 8292, an ES256 JWT for the push service's origin, valid 12 hours) and `sendPush` sends it with `PUSH_TTL_S` (a day) and `PUSH_TIMEOUT_MS` (15 s), following no redirect, answering `'sent'`, `'gone'` (404 or 410: the subscription is no more) or `'refused'` (a redirect among them), and throwing `PushUnavailable` with the service's `Retry-After` on a 429, a 5xx or no answer; keys it can't encrypt for throw as themselves, before the request, so they aren't taken for a service that didn't answer; no error carries the endpoint, which is the device's secret address. `isPushEndpoint` lets through only an HTTPS address with no port or login on the push services browsers use (Google's, Mozilla's, Apple's, Microsoft's, by the services' own host names, `PUSH_SERVICE_HOSTS`), so a page can't make the server send requests into its own network (SPEC's decision log, 2026-11-20); `PUSH_TEST_ORIGIN` adds the fake service of the tests. `PushStore` (`server/push.ts`) keeps `push.json` in the data directory, read as the server starts (`loadStores` in `server/main.ts`, with the settings and the matches), since the notifier asks it without waiting: the VAPID key pair, made on the first device turned on (only the public key leaves the server), and the subscriptions, one per device (its endpoint, its keys and the language it was turned on in), the newest `MAX_SUBSCRIPTIONS` (50). `pushMiddleware` serves `/api/push` behind Kinopeer's login, JSON bodies only: `GET key`, `PUT subscription` (checked endpoint, and keys `isPushKeys` can encrypt for: a P-256 point and a 16-byte secret; `replaces` swaps a renewed one in and keeps its language) and `DELETE subscription`, both answering the server's settings, which the page keeps in its shared answer (`SERVER_SETTINGS_KEY`), and `POST test`, which sends this device a test notification (404 `unknown-device`, 410 `gone` after forgetting it, 502 `refused`, 503 `unreachable`). `GET /api/settings` says only how many devices get push (`push.devices`). `pushChannel` (`server/pushChannel.ts`) is the second `NotifyChannel`, `ready` while some device is kept: it sends each device `finishedText`'s title and release name under "Download finished" in its own language, with the torrent's page as the notification's address and its hash as its tag; it remembers which devices took a torrent, so a retry goes only to the rest (until the notifier has it `forget` the torrent), forgets a gone one, counts a torrent done when every device took it or refused it (`'rejected'` when none took it), and throws the longest wait a service asked for when one didn't answer.

In the browser, `src/pwa/push.ts` reads whether this device can get push from the browser alone (`pushState`: not a secure context, an iPhone or iPad outside the Home Screen app, no Push API, no service worker, notifications blocked, else off or on by `pushManager.getSubscription`), so Settings asks the server nothing about push when it opens; `turnOnPush` asks for the permission in the tap (as Safari requires), takes the server's key, drops a subscription made for another key and saves the new one in the interface's language, `turnOffPush` has the server forget the device before the browser drops it, and `testPushDevice` sends the test and, when the server answers it doesn't send to the device (`unknown-device`, `gone`), drops the browser's subscription too, so the card shows it off and Turn on subscribes afresh. `usePushDevice` (`src/screens/`) gives Settings → Connections its push card, with what each failure says, its actions sent through Settings' saves (`screens.md` → A screen's own requests), kind `push`, one target for the device: the card shown again takes the outcome, its state over what the browser said as it showed, else a toast says it. Client: `src/api/push/`.
