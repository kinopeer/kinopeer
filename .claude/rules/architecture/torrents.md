# The qBittorrent client and the requests every action on a torrent goes through

## The qBittorrent client and torrent requests

qBittorrent Web API client: `src/api/qbittorrent/` (incl. adding torrents, file lists and priorities), which reaches qBittorrent through a transport of the build's (`webui.md` → The WebUI build). The add and move sheets get the categories, the default save path and the preferences that decide category folders through `getSaveLocations`, which reads qBittorrent's version from the session check's answer the page keeps (`subcategoriesUnderParent`: 4.6 puts a subcategory by its whole name under the default save path, 5.0 under its parent with subcategories on, 5.2 always), and `src/torrents/folders.ts` places a category's folder as qBittorrent's `categorySavePath` does.

Settings → qBittorrent folders (`src/screens/FoldersSheet.tsx`) loads the folders when it opens (`getFolders`: the categories and the preferences, the default save path among them, and what a change of either does to the torrents under automatic management in it, failing rather than showing part of them) and saves one through `prepareFolder` (`torrents/setLocation` for no torrents, which has qBittorrent create the folder and answers 409 when it can't; it checks no write access, nor does anything else qBittorrent offers), then `setDefaultSavePath` or `setCategoryFolder` (which sends a category's incomplete-downloads folder back, since qBittorrent before 5.3 resets it otherwise). A save outlives its form and the sheet through Settings' saves (`screens.md` → A screen's own requests), kind `folder`, by the default save path or the category: one opened again, Settings left and opened again included, is busy with what's sent, and an outcome moves the sheet (back to the list, the failure in the form) only while that folder is shown, else it's a toast, a failure naming the folder or the category (the sheet gone with Settings included), and the list asks qBittorrent again when it's next shown. The folder field and its known folders are `FolderField`, shared with Move files, and what a refusal says is `folderFailure` (`src/screens/folderFailure.ts`), with `categoryFailure` for a category qBittorrent no longer has (409 before 5.2, 404 from it), which isn't a folder it can't create.

Moving files: `src/screens/useMoveTorrent.tsx` gives a screen the Move files sheet and runs the move itself, so its outcome shows as a toast even after the sheet was closed or the screen is gone.

Per-torrent speed limits: `src/screens/useSpeedLimits.tsx` gives a screen the Speed limits sheet in the same shape (a failed save after the sheet was closed is a toast on that screen); the field parsing lives in `src/torrents/speedLimits.ts`, with `ownLimits` and `describeLimits`, which Downloads' `SpeedLimitMark` (`src/screens/SpeedLimitMark.tsx`, the gauge on a row, a table row or a card) and the More menu's Speed limits item read.

Both are built on `useTorrentSheet` (`src/screens/useTorrentSheet.ts`), which keeps which torrent the sheet is open for through `useTorrentOverlay` (`src/screens/useTorrentOverlay.ts`, by hash and `added_on`: closed when that torrent goes away or another with the same hash replaces it, the rule for every overlay a screen opens for one torrent: the More menu, Recheck and the title search in Downloads and the torrent details; the delete confirmation keeps it for each of its torrents) and sends its requests (`send`) through the app's torrent requests (`createTorrentRequests` in `src/torrents/torrentRequests.ts`, its kinds in `REQUEST_KINDS` (`src/torrents/requestKinds.ts`), shared by `TorrentRequestsProvider` in `App`, a store of its own beside the poll's; outside a provider, as in tests, each hook keeps its own): one per kind and torrent at a time, `pending` on every screen until it settles, so a sheet opened again or a sheet of the same kind on another screen (the drawer over Downloads) shows it busy and starts from what's being sent; when it settles every sheet that shows the torrent then closes or keeps the failure (`failure`, what was sent and why, until a sheet opens or sends again), and `send` says whether one did, else the outcome goes to a toast. It's a request manager for every action on a torrent, decided on 2026-10-30, moved step by step, now all of them (the alternative speed limits switch stays out, SPEC's decision log says why). A new sheet for one torrent uses it too.

Naming for a media server is such a sheet too: `useMediaNames` (`src/screens/useMediaNames.tsx`, kind `names`) gives a screen `MediaNamesSheet` (`src/screens/MediaNamesSheet.tsx`) for a torrent matched to a title, which loads the files and the torrent's own .torrent (`getTorrentFiles`, `exportTorrent`, read by `readTorrentFile`, its metadata taken only when its info hash is the torrent's) when it opens, never with the More menu, and sends `renameFiles` (one `torrents/renameFile` per file, in order, since qBittorrent applies each later and a folder's rename would find its files by the names they have then). What to rename is pure logic in `src/torrents/mediaNames.ts`: `movieNames` (the main video, the files named after it, the folder; or why nothing is named: `no-video`, `several-videos`, `disc`, or `split` when its files are split between the movie's folder and another, which `splitFromFolder` reads for a series' show folder too), `titleName` (the title made a name, a movie's or a show's folder, with `{tmdb-ID}` after the year when given the title's TMDB id, which `useMediaNames` and the add sheet pass, as `NamingTitle`'s `tmdbId`, only while Settings' `tmdbIds` download default is on), `torrentsIn` (the other torrents at or under the folder naming would use in this one's save path) and `folderTakenBy` (the first of them, which `useMediaNames` checks against `listed`, every torrent qBittorrent lists, the screen's torrents unless the screen passes it and `addRelease` asks `torrents/info` for, so neither names a movie over it) and `originalNames` (back to the metadata's paths, matched by the files' indexes, under its folder when `TorrentMeta.multiFile`, none when only the torrent's folder differs, as qBittorrent's content layouts place it). A series' episodes are pure logic in `src/torrents/seriesNames.ts`, with its heuristic's scope in its header (SPEC's decision log): `episodeOf` (a video's season and episodes from its path, and the torrent's name for a video in no folder, else nothing), `seriesNames` (the renames into `Show (Year)/Season NN/`, with `unread`, the videos it leaves, or `no-episodes`), `filesTakenBy` (another torrent with a file where one of this one's would go, or whose files are unknown, each torrent's paths `placed` under its own save path, ours by `namedPaths`, the files' paths once renamed) and `titleNames`, which picks `movieNames` (the id on the folder and the video) or `seriesNames` (the id on the show's folder alone) by the title's type for the sheet and `addRelease`. Seasons share the show's folder, so for a series `useMediaNames` hands the sheet the torrents in it (`torrentsIn` over `listed`, `neighbours`), whose files the sheet loads with its own, in the same request, and refuses on `filesTakenBy` rather than `folderTakenBy`. A failure reloads the sheet's names `RENAMES_SETTLE_MS` (a second) later, since some files may be renamed and qBittorrent applies the renames it took a moment after answering; what's being sent (`pending`, its mode and renames) is what a sheet opened meanwhile shows, whatever the names read then.

The force recheck confirmation is such a sheet: `useRecheck` (`src/screens/useRecheck.tsx`) gives a screen `RecheckDialog` and sends the recheck with `expect: withChecking` (`status.ts`).

An action sent from a button or menu item rather than a sheet uses `useTorrentAction` (`src/screens/useTorrentAction.ts`: `busy` and `send` for one kind, and a watcher for a place that shows the torrent and takes the outcome): reannouncing through `useReannounce` (the More menu, with its toasts) and pausing and resuming through `usePauseResume` (`src/screens/usePauseResume.ts`) from a row's button, the More menu (`TorrentActionsSheet`, which watches the torrent it shows: it closes or shows the failure, else a toast keyed `TOAST_KEYS.pauseResume`), the torrent details and the selection's bar (one request for several torrents, without those already in flight).

File priorities go through `useFilePriorities` (`src/screens/useFilePriorities.ts`, used by `TorrentFiles`), one request per file or per folder (its files in one request; `SendOptions.part`, keyed `requestKey(kind, hash, part)`, the files' indexes, read back per file through `inFlightParts`; nothing is sent while one of the files has a change in flight, so a folder is busy while a file under it is and the other way round); it shows what's in flight over the files poll (`useTorrentFiles`, which says when the answer shown was asked for, `requestedAt`, and polls only while the Files section is open, keeping the last answer while it's closed) and keeps what qBittorrent took until a files poll sent after the answer, through a watcher of its own rather than `expect`, since the torrents poll has no files.

Deleting goes through `useDeleteTorrents` (`src/screens/useDeleteTorrents.tsx`), which gives a screen `DeleteTorrentDialog` for a row's torrent, the selection or the torrent details, watches the torrents it shows, sends with an `expect` that returns nothing (the torrents are gone until a poll), forgets their matches, says it in a toast and tells the screen (`onDeleted`) only while it's still there.

The torrent page's Download section (`src/screens/DownloadSettings.tsx`, always open, above Details) switches sequential download and first and last pieces first through `useDownloadToggle` (`src/screens/useDownloadToggle.ts`, kinds `sequential` and `firstLastPieces`, on `useTorrentAction`, whose `pending` gives the value being sent and `holding` whether its expected state is still held): qBittorrent can only flip them, so it reads the torrent with `getTorrents` just before and flips nothing when it's that way already, with an `expect` held for `stateLag`, and the switch stays busy until that hold ends. It changes the category through `useChangeCategory` (`src/screens/useChangeCategory.tsx`, `CategorySheet.tsx`, on `useTorrentSheet`, kind `category`): `categoryChange` (`src/torrents/categoryChange.ts`) says what the change does with the files, moved to the category's folder under automatic management (`auto_tmm`), or left there with automatic management turned off when qBittorrent's preferences say so (`relocateOnCategoryChange` in `getSaveLocations`), an incomplete torrent with a download path (`downloadPath`, a category's `download_path`) moving to a folder it doesn't name, and `withCategory` is the state it expects.

The store is linked to the poll: `TorrentRequestsProvider` sits inside `MainDataProvider` and takes its store, and a request sent with `expect` (`withRunning` in `status.ts` for pause and resume; an `expect` that returns nothing takes the torrent away) polls again when it settles and keeps that state from qBittorrent's answer until a poll sent at that moment or later, or with `hold` that much later (`withExpected`, applied by `useMainData` under the provider, so every screen, count and filter shows it). Pause and resume hold for `stateLag` (`src/torrents/stateLag.ts`): qBittorrent reports their new state only at its next refresh, so the interval is read from its preferences once per page, alongside the first one. Move files and Speed limits still call `refresh` themselves.

`.torrent` files and magnet links are read in the browser (`src/torrents/torrentFile.ts`, `magnet.ts`) to get the info hash and files before adding, the files in qBittorrent's order (a v2 file tree's in the file's own key order, which a JS object doesn't keep for keys like `10`, so the decoder keeps it beside each dictionary); the hash goes through `src/torrents/digest.ts`, which uses Web Crypto when the page has it and its own SHA-1/SHA-256 over plain HTTP, where `crypto.subtle` doesn't exist.

Session state: `src/session/useQbitSession.ts` checks `app/version` first, so a working server login or qBittorrent's auth bypass goes straight in without a login form. With no address for qBittorrent the bridge answers 503 marked `BRIDGE_HEADER: no-address` (`NO_ADDRESS`), which the client throws as `NoAddressError` and the session reads as `no-address`: `ConnectScreen` then asks for the address with the login (`QbittorrentLoginForm`, which Settings shares, its login optional on every form for the auth bypass, #519, though half of one isn't sent), and `signIn` sends it (`url` in `PUT /api/settings/qbittorrent`). Where the address was saved from the app and Kinopeer's own login is on (the server's settings, read only then), the connect screen also offers to change it, from its form, its unreachable state or qBittorrent too old, since Settings isn't reachable until qBittorrent connects. Each check asks anew (`checkAppVersion` in `src/api/sharedAnswers.ts`) and keeps its answer for the page under `APP_VERSION_KEY`, which Settings' qBittorrent check takes while it's fresh (`APP_VERSION_FRESH_MS`, a minute), so Settings opened as the app opens or a tab away asks nothing again; its Test asks anew. A version older than the build's minimum (`requiredQbittorrentVersion()` in `useQbitSession.ts`: `MIN_QBITTORRENT_VERSION` in `src/torrents/qbittorrentVersion.ts`, with what each version adds that Kinopeer needs, or `MIN_WEBUI_QBITTORRENT_VERSION` in the WebUI build) makes the session `unsupported`, and `App` shows the connect screen with `UnsupportedQbittorrent` in place of the form (and its Change for an address saved from the app, as when qBittorrent doesn't answer); differences between supported versions go through that module's pure functions, the version passed in, as with the 4.x pause and resume, which fall back by the answer instead.
