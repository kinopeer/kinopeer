# The WebUI build: Kinopeer as qBittorrent's Alternative WebUI, with no server of its own

What the WebUI build (`browser.md` → The two builds) does without Kinopeer's server. Code that branches on `__WEBUI__` reads it inside a function where it can, so a test stubs the global (`vi.stubGlobal('__WEBUI__', true)`) and needs no import again; a module that reads it as it loads (`appRouter.ts`) is imported again. The pure-logic folders' callers pass in what it decides, as `isSupportedVersion` takes the minimum.

## The transport

Each service the browser calls goes through a transport with two ways to it, and the client's calls and errors are the same on both, so nothing above the client asks which build it is. qBittorrent's is `src/api/qbittorrent/transport.ts`: a `QbittorrentTransport` sends a call (a path under the Web API with its query, a method, a POST's body, a signal) and resolves only with an ok answer, throwing the client's errors (`src/api/qbittorrent/errors.ts`) otherwise. `bridgeTransport` is Kinopeer's bridge (`/qbt/api/v2` with `X-Kinopeer`, the bridge's headers read as The qBittorrent bridge says), and `webuiTransport` is qBittorrent's API on the page's own origin, relative to the page (`api/v2`, so a path a reverse proxy puts qBittorrent under works too, which the routes in the address's fragment leave as the page's), with the session cookie qBittorrent's login gave the browser: a 403 is `UnauthorizedError`, any other refusal `QbittorrentError` with qBittorrent's status. The client's `request` picks by `__WEBUI__` with each call. `unreachable` names the service called in the WebUI build, which has no Kinopeer server to blame. Every call of `src/api/qbittorrent/client.ts` goes through the bridge too, so each is in its `ENDPOINTS` and `EVERY_CALL` (`server.md` → The qBittorrent bridge); the calls only the WebUI build makes go in `src/api/qbittorrent/webui.ts`, which the bridge forwards none of: qBittorrent's login (`logIn`, sent with `fetch` itself, since its 403 is a ban rather than a lost session, and given up after `LOGIN_TIMEOUT_MS`, 15 s, so the form isn't held busy) and the `clientdata` store (`loadClientData`, `storeClientData`, Settings in qBittorrent, below), through `webuiTransport`. TMDB's is `src/api/tmdb/transport.ts`, by path, as its bridge is a plain proxy (#559): a `TmdbTransport` sends a GET to a path under TMDB's API with its query and throws the client's errors (`src/api/tmdb/errors.ts`), `TmdbKeyError` for no key or one TMDB rejected. `bridgeTransport` is `/tmdb` (`server.md` → TMDB and its proxy); `webuiTransport` takes the user's own key from qBittorrent (`getWebuiSettings`) and calls `api.themoviedb.org` with it (`authorize` in `src/api/tmdb/direct.ts`: a v3 key in the query, a v4 token as a bearer token, whose preflight TMDB answers for any origin), else Kinopeer's TMDB proxy without one where it answers the page (`sharedTmdbAvailable`), `__TMDB_PROXY__`, which the build takes as the image does (`tmdbProxy` in `server/main.ts`: the release worker unless `KINOPEER_TMDB_PROXY` or `TMDB_PROXY_URL` names another, `vite.config.ts`), with only `Accept`, which needs no preflight, since the proxy answers none for other headers; else it throws `TmdbKeyError`, so the app asks for a key. A failed read of the key from qBittorrent throws `TmdbKeyReadError` (an abort stays an abort), so `TmdbFailedState` and Settings' TMDB row say qBittorrent didn't answer rather than TMDB, and the failed state starts the shared poll, whose 403 brings back qBittorrent's login. Images come from `image.tmdb.org` in this build (`posterUrl`, `backdropUrl`), which the service worker doesn't cache (it caches `/tmdb-img/*` only), so the browser's own cache keeps them (`image.tmdb.org` answers with a year's `max-age`). Prowlarr's goes by operation rather than by path, as its bridge maps the results (#560): each call of `src/api/prowlarr/client.ts` picks by `__WEBUI__` between the bridge and `src/api/prowlarr/direct.ts`, which reads Prowlarr's address and key from qBittorrent (`getWebuiSettings`) and calls Prowlarr's API with the key in `X-Api-Key` (Prowlarr answers any origin's CORS, its 401 without a key and the header's preflight included), reading its answers through the bridge's own functions (`src/releases/prowlarrResults.ts`, `server.md` → The production server) and throwing the client's errors (`src/api/prowlarr/errors.ts`). A download sends the key in the link's query and no header, so it needs no preflight, and follows no redirect: a redirect (`opaqueredirect`: a magnet link, or the indexer's own link, neither of which the page can read) is handed on as the link itself, `ReleaseSource`'s `link`, which `addRelease` sends qBittorrent as a URL to fetch, unless the release has a magnet link, which goes in its place, since it names the torrent's hash; the add sheet says a link's files come as a magnet link's do, and asks qBittorrent whether it has the torrent by the hash Prowlarr gave with the release (`infoHashOf`). The failing indexers are dated by the device's clock (`failingDirect`, given up after `FAILING_TIMEOUT_MS`, 5 s). A failed read of Prowlarr's address and key from qBittorrent throws `ProwlarrKeyReadError` (an abort stays an abort), as TMDB's does, which `useReleases` gives as `unread`, so the releases show `StoreUnreadState` (`src/screens/`, `TmdbFailedState`'s too: qBittorrent not answering, with the shared poll started, whose 403 brings back qBittorrent's login), and Settings' Prowlarr row and the add sheet say qBittorrent didn't answer.

## Settings in qBittorrent

What the server keeps in its settings file, the WebUI build keeps in qBittorrent's `clientdata` store (5.2 and later), shared by every browser that signs in to that qBittorrent and by any other web interface, so each key has Kinopeer's `kinopeer.` prefix (#558). `loadClientData` asks for the keys named (a GET with `keys` as a JSON array) and gets only those qBittorrent has; `storeClientData` POSTs a JSON object, which qBittorrent merges key by key, a null removing its key; the whole store holds 1 MiB, and a store that would go over it is refused whole with a 409 (`isStoreFull`), all checked against qBittorrent 5.3.0; each call gives up after `CLIENT_DATA_TIMEOUT_MS` (15 s), as a login does; a store given up has normally reached qBittorrent whole already (its body is small), so it may have been taken, and sending it again does no harm. `src/api/settings/webui.ts` keeps a key per setting (`SETTING_KEYS`): the user's own TMDB key, Prowlarr's address and key together (`StoredProwlarr`, since a key belongs to its address), and each download default, so a save sends only the keys it changes and two devices changing different settings don't overwrite each other; a category picked automatically is kept as `""`, not removed, so a device that had picked one doesn't send it back as missing (`loadServerSettings`). The settings client (`src/api/settings/client.ts`) sends `getServerSettings`, the TMDB key's save and forgetting, Prowlarr's save and the download defaults there in this build and answers the same `ServerSettings` (`asServerSettings`), so the screens and `sharedRequests`' `SERVER_SETTINGS_KEY` read one shape on both builds; what only a server has (its login, notifications, an address from its environment, Prowlarr's key of its own) is never in it. The store's answer is shared under `WEBUI_SETTINGS_KEY`, asked anew with each `getServerSettings`; a save reads it first (the page's while it's fresh), so a read can't fail a save qBittorrent took, then merges what it stored into it. TMDB's transport reads the user's own key through `getWebuiSettings` (The transport, above), and `saveWebuiTmdbKey` checks a key with TMDB as the server does (`checkTmdbKey` in `src/api/tmdb/direct.ts`, its `authentication` call within `KEY_CHECK_TIMEOUT_MS`, 15 s), answering `invalid-key` or `unreachable` as the server's route does and storing nothing then; Prowlarr's client reads its address and key the same way, and `saveWebuiProwlarr` checks them together as the server does (`checkProwlarrKey`, shared through `src/releases/prowlarrResults.ts`, within `PROWLARR_CHECK_TIMEOUT_MS`, 15 s), refusing first, as `mixed-content`, a plain HTTP address the page couldn't call from HTTPS (`isMixedContent`, which lets loopback addresses through, as browsers do), which `ProwlarrKeyForm` says on the address field; the form also says in a banner who sees the key (SPEC's decision log, 2026-11-22). TMDB is set up where Kinopeer's TMDB proxy answers the page (`sharedTmdbAvailable`: a build with a proxy and `isPrivateOrigin`, `src/logic/privateOrigin.ts`, the proxy's own rule), else by a key of the user's own, which onboarding then asks for; Prowlarr's address is always the app's to set (in Settings, onboarding's steps and the releases' setup state), checked as the server checks one (`prowlarrAddress`), and onboarding asks for it until it's kept. A store with no room is `SettingsError`'s `store-full`: the key forms say the key wasn't saved, and a download default changed in Settings says it's saved in this browser, not in qBittorrent (`updateAndShareSettings`'s answer), since a load takes the value qBittorrent keeps, if it keeps one, and otherwise sends this browser's again unless it's the default.

## Shipping it

`release.yml` attaches `kinopeer-webui.zip` to every GitHub Release, the same name each time, so `releases/latest/download/kinopeer-webui.zip` is the newest: a `kinopeer-webui/` folder, the one qBittorrent's Alternative WebUI setting names, with the build in its `public/`. A job of its own builds it, with the workflow's read-only permissions, since `npm ci` runs the dev dependencies' install scripts, which the release job, with its write permissions and the registry's login, never runs. What qBittorrent does with the files it serves shapes the build:

- **No policy of its own.** qBittorrent sends an Alternative WebUI `X-Frame-Options: SAMEORIGIN`, `nosniff`, `X-XSS-Protection` and a policy of only `frame-ancestors 'self'`, with `upgrade-insecure-requests` over its own HTTPS, but no `Referrer-Policy`, which it sends only its own interface (`WebApplication::configure`, 5.2 and 5.3). So the build puts `WEBUI_CONTENT_SECURITY_POLICY` (`server/securityHeaders.ts`) and the server's `Referrer-Policy` (`same-origin`) first into `index.html`'s head as `<meta>`s (`webuiPolicyPlugin` in `vite.config.ts`). The policy is the server's, but the page reaches TMDB (its proxy, or `api.themoviedb.org`) and Prowlarr at whatever address the user gives it, over HTTP too when qBittorrent is opened over HTTP on a home network, so `connect-src` takes any address, and images come from `image.tmdb.org`; a browser applies both policies. A `<meta>` can't carry `frame-ancestors`, which qBittorrent's header already says.
- **Strings it replaces.** qBittorrent replaces `${LANG}`, `${CACHEID}` and `QBT_TR(…)QBT_TR[CONTEXT=…]` in every text file it serves (its `translateDocument`), so `npm run build:webui` ends with `scripts/webui/substitutions.ts`, which fails the build on any of them in any file of `dist-webui/`. Checked on qBittorrent 5.2.0 and 5.3.0 in Docker: every file of the build came back byte for byte.
- **The service worker.** Once Kinopeer is turned off in qBittorrent's settings, the same address answers with qBittorrent's own interface, which a worker answering pages from its precache would never show. So in this build `src/sw.ts` registers a route for the app's page alone (`/` and `/index.html`, `WEBUI_PAGES`, since the routes go after the `#`; any other address opened in a tab goes to the network) ahead of the precache's, which would answer `/` with the cached `index.html`. `loadPage` (`src/pwa/swWebui.ts`, apart from workbox with its own test) takes the page from the network and reads the answer (`pageAnswer`, a heuristic whose scope its module states): Kinopeer's page (a success with `KINOPEER_PAGE_MARK`, the `application-name` `<meta>` in `index.html`) is handed on; another page answering here now (a success without the mark, a redirect, any other error) is handed on once the worker has unregistered and deleted its own caches, so qBittorrent's interface shows at once and the next load has no worker, and Kinopeer registers it again whenever it loads; nothing usable (no answer, no whole page in `PAGE_TIMEOUT_MS`, 5 s, the body's read included, a proxy's gateway failure in `GATEWAY_FAILURES`, nginx's and Caddy's 502, 503 or 504 and Cloudflare's 520 to 524 and 530, a body that broke off) opens the precached `index.html` and keeps the worker, so the app can say qBittorrent doesn't answer. As anywhere, the worker runs only over HTTPS or on `localhost` (`browser.md` → PWA). `version.json` and the reload into a new version work as in the server build: qBittorrent serves JSON and HTML with `no-store`.

## Matches in qBittorrent

The torrent-to-title matches (`torrent-state.md` → Torrent-to-title matches) live in qBittorrent's `clientdata` too in the WebUI build, a key per torrent, `kinopeer.match.<info hash>` (`MATCH_KEY_PREFIX` in `src/api/matches/webui.ts`), about 80 bytes each (#561). The matches client (`src/api/matches/client.ts`) sends its three calls there in this build, so `serverMatches.ts` and everything above it read the same `Matches` on both. qBittorrent loads only the keys it's named, or every key, every interface's, and a torrent's key isn't known before it's loaded, so `loadWebuiMatches` asks for every key (`loadClientData()` with none) and keeps those of the prefix that hold a match (`validStoredMatch`). With no server to apply the store's rules, each change (`saveWebuiMatches`, `clearWebuiGuesses`, `pruneWebuiMatches`) loads the matches qBittorrent keeps, applies `src/logic/titleMatches.ts`'s rule to them and stores only the keys it changed, one change of the page at a time (`changeMatches` waits for the one before, as the server's `JsonFile` does), so what another device stored meanwhile stays, unless it stored the same torrent's between the two calls (SPEC's decision log, 2026-11-22). The server's hourly check is the page's: each answer of the poll (`useMainData.ts`) hands `checkMissingMatches` (`serverMatches.ts`) every torrent qBittorrent has, and once the matches are loaded from qBittorrent it has `pruneWebuiMatches` note the missing ones and forget those missing for a week, at most once per `CHECK_INTERVAL_MS` (an hour) per page, so it runs only while something polls. Fix match says where the choice is kept, and that qBittorrent's store had no room for it, in its sheet or its toast (`useChangeTitle`); a guess the store has no room for stays in this browser's cache, as one the server didn't take does.

## What the WebUI build shows

`App` renders `WebuiConnectScreen` (`src/screens/`) in place of `ConnectScreen` and never `SignInScreen`: qBittorrent's own login (a form with a username and a current password, so the browser's password manager fills it, which `logIn` sends and then checks the session again), the session check's who didn't answer and qBittorrent too old, and nothing about an address. The session (`useQbitSession`) takes `requiredQbittorrentVersion()`, 5.2.0 there (`MIN_WEBUI_QBITTORRENT_VERSION`, for `clientdata`). A 403 while polling ends the session as on the server build, so the login shows again when qBittorrent's session ends. What needs Kinopeer's server isn't shown: Settings' Telegram and push cards, its Sign-in section, Change qBittorrent's address and the hint about where addresses are set, and the notify switches (`useNotificationsAvailable` asks nothing and answers false); Find under Prowlarr's address looks from the page (`setup.md` → Find). Settings → About, and `UnsupportedQbittorrent` on the too-old screen, offer the way back to qBittorrent's own interface: `QbittorrentInterfaceDialog` (`src/screens/`) confirms, then `turnOffAlternativeWebui` (`src/api/qbittorrent/webui.ts`) sets qBittorrent's `alternative_webui_enabled` to false and the page replaces itself with qBittorrent's root (`QBITTORRENT_ROOT`), where qBittorrent answers with its own interface and the service worker steps aside (Shipping it, above). The key forms and onboarding's steps say qBittorrent keeps what they save and Prowlarr's address is as this browser reaches it. The texts only this build shows are in `src/i18n/locales/webui/`, under top-level keys of their own (`webui`), which `showLanguage` adds to the language's only in this build, so the server build's language files don't carry them; a test checks both languages have the same keys and that none hides a key of the language's.
