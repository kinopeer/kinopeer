# Routing, the desktop Downloads, toasts and how a screen loads and saves

## Routing

Routing: React Router (`react-router`), which renders a change of address at once rather than in a React transition (`ROUTER_OPTIONS` in `src/lib/routerOptions.ts`, which every router in the tests takes too), since Search's fields take their value from the address and a transition put the older text back between a key and its render (#386). `App.tsx` routes `/` (downloads), `/search`, `/torrent/:hash` (torrent details: `TorrentScreen` on a phone; on desktop a drawer, `TorrentDrawer`, a native modal `<dialog>`, both showing `TorrentDetails`. A link from another page passes it as background in the navigation state (`overPage` in `src/lib/background.ts`; the title page's `TitleDownloads` does), and `App` renders the routes for that background location with `TorrentDrawerOverPage` on top, which closes by going back and tells the sidebar which page is behind. Without a background, as from Downloads or on a direct load, `DownloadsWithDrawer` renders Downloads with the drawer), `/title/:type/:id` (type is `movie` or `tv`, id is the TMDB id; near the page's end `TitleRelated.tsx` shows TMDB's recommendations, else its similar titles, in a `PosterRow`, the Search screen's browse row, and under it the "In downloads" block, `TitleDownloads.tsx`, its section there from the start and filled in once the row has settled (`after`; the row's request is given up after `RELATED_TIMEOUT_MS`, 15 s, through `withTimeout` in `src/logic/`, which the title lookups use too, so a request that stalls doesn't hold the block back), which lists the title's torrents through `useTitleTorrents` in `useTitleMatches.ts` and which the header's badge scrolls to), `/title/:type/:id/releases` (Prowlarr results with quality filters; `src/releases/parseRelease.ts` reads resolution, source, HDR, voice-over, seasons and episodes from release names; searches don't filter by category, because some indexers file every release under "Other"; both title paths render `TitleRoute`: on phones the releases path is `ReleasesScreen`, on desktop it is the title page with `TitleReleases` under the hero, which "Find releases" opens by replacing the title's path, so nothing is searched until it's pressed; the desktop hero's overview is `TitleOverview.tsx`, cut to five lines with Show more while it's clipped (`scrollHeight > clientHeight`, measured again when fonts load or the width changes); the search, filters and sort live once in `src/screens/useReleases.ts`, which searches by `releaseQueries` (`src/releases/releaseQuery.ts`: the original title, and the English name too, from the title's details in English shared as the title page's, when `needsEnglishTitle` says the original has no Latin or Cyrillic letters, #581) and merges the searches with `mergeReleases`, `src/releases/mergeReleases.ts`; a query the user edited, in the address's `q` (`QUERY_PARAM`), is searched alone in their place, through `ReleaseQueryField` (#582) and `useReleases`' `searchBy`, which replaces the entry and keeps `deepLink` in its state, and searches the query already searched again (`isDeepLink` in `src/lib/deepLink.ts`, which the title page and the phone's releases read for Back), since a replaced entry's key is no longer `'default'`; the pure filtering is in `src/releases/filterReleases.ts` (with `filterCounts`, each filter value's faceted count, which the filter chips show through `FilterChip`'s `count`, and `dim` for a value that leaves none, #583), the shared states in `ReleasesBlock.tsx`) and `/settings` behind the tab bar. The screens' `ErrorBoundary` is keyed per screen (`screenKeyOf` in `App.tsx`), so a crash clears on the next one; on desktop a torrent's drawer shares Downloads' key and a title's releases path its title's, so neither remounts the page under it. The router is `AppRouter` (`src/lib/appRouter.ts`): in the server's build a `BrowserRouter`, whose paths `server/static.ts` answers with `index.html`, and in the WebUI build (`browser.md` → The two builds) a `HashRouter`, the routes after the `#` (`/#/title/movie/1`), since qBittorrent serves only the build's own files and a path that isn't one gets its error page. Whatever builds or reads an app path takes the router's (links, `navigate`, `useScrollRestoration`'s history keys, the tabs' places), so it reads the same in both; what takes the window's address keeps the `#` with its route whole: `PROXY_SIGN_IN_PARAM` goes into the page's own query, before the `#`, and the update's reload loads the address as it is. The push notifications' links are paths, sent only by Kinopeer's server, which serves the server's build.

Search's rows before a search are TMDB Discover queries by digital or disc release date and recently aired episodes (`src/search/browseRows.ts`), so they show what's likely on torrents already; search state (`q`, `type`, `year`) lives in the URL; with a year, `searchTitles` searches `/search/movie` and `/search/tv` apart (`/search/multi` has no year parameter) and interleaves them, and a type searches only its own; the results come a page at a time through `useSearchResults` (`src/screens/useSearchResults.ts`, Show more), which keeps each type tab's pages while the query stays and, for Back, the pages loaded in memory by history entry (`location.key`) and search, one place per search, the last `KEPT_SEARCHES` of them (`src/search/searchResults.ts`, with the merging that drops a title seen on an earlier page); the scroll position comes back on Back through `useScrollRestoration` (`src/lib/useScrollRestoration.ts`, position per history entry in sessionStorage, restored once the screen says its content is loaded, since the browser's own restore runs while the page is still short; it tells Back from a new entry by whether a position was saved for it, since under `App`'s `<Routes location>` `useNavigationType()` always reads POP; it also saves the position as the page is hidden or goes away, so a reload comes back to it, adding back the body's margin `holdPage` keeps a pinned page in place with, so a screen left from a modal with a field (Fix match's Enter key or Open again) saves where it really was (#553), and a document loaded afresh forgets what an earlier one saved under the first entry's key, `"default"` in every document).

Each tab's screen (Downloads, Search, Settings) passes its tab's path, and the hook also keeps where the tab was left, its query and scroll, when the screen goes away (`src/lib/tabPlaces.ts`, sessionStorage); the tab bar's and the sidebar's items are `TabLink`s (`src/components/TabBar/TabLink.tsx`), which link to the tab with that query and `TAB_RETURN` state, so the screen they open scrolls back to the tab's place (and Search takes the kept pages of that search, `keptSearch`), and on the tab's own screen scroll it to the top instead. Any other screen change on a forward navigation opens at the top through `useNewScreenAtTop` in `App`, by `screenKeyOf`, so a drawer over a page leaves it alone.

## Desktop Downloads

Desktop Downloads (`useIsDesktop()`): the whole header stays at the top: the title, the totals, the name filter and the select button in one row (while selecting, the selection's count and buttons with the name filter, so Select all takes only what it shows), the offline banner, then the status as a `StatusMenu` (phones keep the chips), a type `Segmented`, the sort as a `SortMenu` and the view; the table's column names sort too (`DownloadRowHeader`), with a direction (`DownloadOrder`, kept with the sort in `downloadsSortDescending`) that `SortDirectionButton` (`src/components/SortDirectionButton`) reverses beside the sort button, on both layouts and in the grid too (the sort button opens the menu on desktop and the sheet on a phone). Sorting is shared with the releases: `SortHeader` (`src/components/SortHeader`) is a sortable column's header in both tables, a button with an arrow and `aria-sort`, and `src/logic/sortOrder.ts` has the order (`SortOrder`, a key and a direction) and its rules over a table of each sort's usual direction (`DOWNLOADS_USUALLY_DESCENDING` in `src/torrents/sort.ts`, `RELEASES_USUALLY_DESCENDING` in `filterReleases.ts`): `usualOrder` for a pick, `clickedOrder` for a column's click, `reversedOrder` for the direction button, `cycledOrder` for the phone's releases chip (the sort the other way, then the next sort), which `useReleases` gives its screens as `pickSort`, `clickSort`, `reverseSort` and `cycleSort`; the list is a table of `DownloadRow`s (columns from a CSS custom property, the title takes what the fixed columns leave; container queries show the size only from a 1240px table, and below 920px move the ETA under the speed, so the title keeps ≥ 200px), the grid is the phone's `DownloadCard`s with a Pause/Resume button on hover. Each layout keeps its own view (`downloadsView`, `downloadsDesktopView`, grid by default). `TorrentActionsSheet` and the sort become `Menu` popovers (`src/components/Menu`) when given an anchor on desktop. The sidebar's downloading count and qBittorrent card (`SidebarStatus`) read the shared poll in `App`; in the icon rail the count is a badge on the icon and the card a narrow column of speeds and free space. The alternative speed limits switch (`useAltSpeedLimits` in `src/torrents/`, taking the caller's `useMainData()` so no second poll starts, with `transfer/toggleSpeedLimitsMode`; its pressed state holds until a poll sent after the switch, by the snapshot's `requestedAt`) is in that card on desktop and in the phone's Downloads title row, one owner per layout. The table's first column (queue positions, or the checkboxes while selecting) shows only while selecting or with the Priority sort when a torrent shown has a queue position or that sort is reversed (so its header can turn it back with nothing queued), via `.has-lead`. On phones only `.downloads-bar` is sticky (the chips, sort and view; the selection row while selecting), under the scrolling title and totals and under the status bar's strip (`.status-strip` in `base.css`, a sticky `::before` the height of the safe area, shared with Search), which keeps the list from showing behind the clock. On desktop the whole `.downloads-head` is sticky and takes the safe area itself, so Downloads turns the strip off there; the table's head row group sticks under the header at its height, which `useHeightVar` (`src/lib/useHeightVar.ts`) keeps in `--downloads-head` on the screen, and the header's menus take `follow` so they stay open while the list scrolls. Search does what phones' Downloads does on both layouts: its title scrolls away and `.search-bar` (the field and the filters) sticks under the strip, the header making no box of its own (`display: contents`).

## Multi-select in Downloads

Multi-select in Downloads: `DownloadsScreen` keeps the selected hashes (null outside selection mode); rows and cards (`DownloadItem`, `DownloadCard`) become checkboxes, and `BulkActionsBar` (pause, resume, delete through `useDeleteTorrents`, whose confirmation takes several torrents) replaces the tab bar, which `App` hides through `onSelectingChange`. Actions apply only to selected torrents the filters show.

## Toasts

Toasts: `ToastProvider` (`src/components/Toast/ToastProvider.tsx`, at the top of `App`, so the sign-in and connect screens have it too) shows them all as a stack of up to `MAX_TOASTS`; screens and hooks call `useToast()` (`useToast.ts`) and its `show` with the translated message, never render `<Toast>` themselves; the provider keeps each toast's time, so the stack moving to another layer doesn't restart it. A toast replaces one with the same `key` (the message by default), and `dismiss(key)` takes a failure back when the action is tried again: the keys shared between places are in `src/screens/toastKeys.ts`, and the alternative speed limits switch goes through `useAltSpeedSwitch` (`src/screens/`), which does this for both its owners. `Sheet`, `Dialog` and `TorrentDrawer` register through `useToastLayer` while open, and the stack is portaled into the top one, since the page outside a modal `<dialog>` is inert. Tests get the provider from `renderWithRouter`; a test that renders with plain `render` passes `wrapper: ToastProvider`.

## Screens and components

Screens live in `src/screens/`, shared UI components in `src/components/` (ported from the design system with the same class names).

## A screen's own requests

A screen or a sheet loads what it shows through `useRequest` (`src/lib/useRequest.ts`): it runs its load for a key, aborts the run for the key before, so a slow answer for an old key never overwrites a newer one, passes the signal on, so an aborted request is cancelled, and runs it again on `retry`. By default each caller asks on its own. With `freshFor` (ms) the request is shared by its key across the page through `sharedRequests` (`src/logic/sharedRequests.ts`, pure logic, which code outside React calls directly): callers that ask while one request is on its way get its answer, a later caller gets the kept answer while it's that fresh, from its first render, and a shared request is cancelled only once no caller waits for it; `retry` sends a new one, whose answer replaces the kept one. An answer the app keeps for the key otherwise (`set`: a save that answers with the server's settings, `saved` in `src/api/settings/client.ts`) reaches every caller showing the key (`follow`), in place of its own request if that's still on its way, since that one may be from before the save, so Settings opened again while a save from an earlier visit was on its way shows what it saved (#545). Only answers are kept, never a failure. Sharing is a caller's choice rather than the default because a key there names the request itself, the same for every caller, while today's keys are each component's own and some loads do more than fetch. The key and the freshness a request is shared with sit beside its client (`APP_VERSION_KEY`, `SERVER_SETTINGS_KEY`, `titleDetailsKey` and `relatedTitlesKey` with `TITLE_FRESH_MS`). A title's details (`useTitleDetails` in `src/screens/`, which the title page and the phone's releases screen both read) and its related titles (`TitleRelated`) are shared for an hour, so a move between the title page and its releases, or back, asks TMDB nothing again. Kept answers stay in memory until the page reloads, a few kilobytes per title opened. Tests start from an empty cache (`src/test-setup.ts`).

A save sent from one of Settings' sheets outlives the sheet the same way a torrent request does (#500), without a torrent: `saves` (`src/logic/saves.ts`, pure logic, one for the page, as `sharedRequests` is, so a save outlives Settings and needs no provider) keeps one save per kind and target in flight (`saveKey`; a second for the target sends nothing), with what it sends, and when it settles offers the outcome to every watcher of its kind, each saying whether it takes it, and `send` says whether one did (`taken`), else the caller says it in a toast. A sheet reads it through `useSaves` (`src/lib/useSaves.ts`): `pending` for a target, from any sheet, so one opened again shows what's sent and sends nothing more, and `send`, and while it's mounted its latest render's `takes` is offered each outcome of its kind: it takes one only while it shows the target. The qBittorrent folders sheet, Telegram's form, the connection forms (`QbittorrentLoginForm`, `ProwlarrKeyForm`, wherever they're shown) and the push card, each with what it sends (the address and the username, never a password or a key), use it; a form that takes a save runs its own caller's next step (`onSaved`, `onForgotten`), so Settings opened again, or a title's releases, follows a save sent from another, and the form that sent it runs it only when none took it. Tests start with nothing in flight (`src/test-setup.ts`).
