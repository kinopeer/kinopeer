# Release checklist

What to check before every release. What a version waits for is in its [milestone](https://github.com/kinopeer/kinopeer/milestones); releasing itself is in [DEVELOPMENT.md](DEVELOPMENT.md) → Releasing.

## Before every release

Go through these for the release PR (the one with the version and the changelog section) and note what was found in its description.

- **The suite itself.** New duplicates between layers (a statement checked twice without a comment saying what the second layer sees); the coverage totals against the threshold (`npm run test:coverage`; raise the threshold when the totals have grown, [TESTING.md](TESTING.md) → Coverage); `npm test` still under its limit on the owner's Mac ([TESTING.md](TESTING.md) → Layers, which says where that time goes) and the `visual` job still around three minutes in CI (155–200 s over `main`'s last ten runs on 2026-11-22), or find what got slow; no `flaky` in the recent `visual` job logs.
- **BuildKit's image.** `release.yml`, `edge.yml` and `ci.yml` pin `moby/buildkit` by digest in `setup-buildx-action`'s `driver-opts`, where Dependabot doesn't look. Take the newest release that isn't an rc from <https://github.com/moby/buildkit/releases>, with its date; when it isn't the pinned version and came out a week ago or more, check that `docker buildx imagetools inspect moby/buildkit:vX.Y.Z` names the same `Digest` as `docker buildx imagetools inspect moby/buildkit:buildx-stable-1` (the image Docker's actions use by default), then put that version and digest into all three in a PR of its own before the release PR, so its `docker` check and the next Edge run try it first. When the two digests differ, Docker hasn't moved `buildx-stable-1` to that release yet: leave the pin as it is until they agree.
- **`docker-compose.yml`.** When it changed since the last release (`git diff v<last version>..main -- docker-compose.yml`), the changelog section says what changed and that a Compose install downloads the file again (README → Install with Docker Compose → Updating).
- **The release workflow's actions.** `release.yml`'s `docker/*` actions run only at a tag, so a version Dependabot moved since the last release first runs there: watch the tag's run, and fix it before the store PR if it fails.
- **By hand, what no layer sees** ([TESTING.md](TESTING.md) → Known blind spots), on `main` as it will be released:
  - On the owner's phone, in Safari on iOS, against Kinopeer Edge built from `main` as the release PR starts from it, which changes no code (the production image behind Umbrel's proxy, since `dev-lan` has no manifest): open Downloads, a title and its releases; drag a sheet closed by its title and swipe behind an open sheet (the page doesn't move); tap a field in Speed limits and in Move files with Downloads scrolled down by a swipe, which collapses Safari's toolbar (the sheet rises above the keyboard, Save visible, the filters and the dimmed backdrop stay); add a release, pause and resume a torrent and change its category, since every call to qBittorrent carries the `X-Kinopeer` header through Umbrel's app_proxy, which no layer runs; check that Share → Add to Home Screen over HTTPS previews Kinopeer's icon rather than a generic tile (#304) and that the installed PWA still opens, that after Umbrel updates Kinopeer the app resumed from the background (not closed from the app switcher) reloads into the new version with the "updated" toast (the page being replaced must already have the update check, which came after 0.6.1: on the first update from an older build, close the app once and check on the next one), and, in it, that the first tap on the field in Move files with Downloads scrolled down doesn't make the page or the sheet jump.
  - Throughout, with Safari's Web Inspector open on Kinopeer Edge (the phone through the Mac's Develop menu): no "Content Security Policy" error in the console (Safari's own "Refused to apply a stylesheet", one per `<select>` on a page, is expected: SPEC's decision log), and the app opening from Umbrel's home screen. A desktop Chromium over plain `http://` also says it ignored the `Cross-Origin-Opener-Policy` header, which applies only over HTTPS: expected too.
  - Umbrel's sign-in lapsing under the installed app (#303): in Web Inspector on Kinopeer Edge opened from the Home Screen, delete the `__Host-UMBREL_APP_SESSION_HTTPS` cookie (Storage → Cookies) on a screen other than Downloads and reload; Umbrel's sign-in opens over the app (with its password if Umbrel's own session is gone too), and the app comes back to that screen, working, with the cookie set for a week.
  - After the Umbrel package updates: go through onboarding, a search and adding a release through Umbrel's app_proxy and HTTPS; add a release over plain `http://` on the LAN, where the info hash from the SHA-1 fallback must match qBittorrent's.
  - The host check (#356) behind Umbrel's gateway, on Kinopeer Edge from a build that has it: point a name outside the check's defaults at the Umbrel on the Mac (a line `<the Umbrel's IP> umbrel-edge.test` in `/etc/hosts`), open `http://umbrel-edge.test:8798`, and see Umbrel's sign-in and then the app rather than "Kinopeer doesn't answer at umbrel-edge.test". It fails when the package's `KINOPEER_ALLOWED_HOSTS: "*"` doesn't reach the server through the gateway. Remove the line afterwards.
  - The Docker Compose install (#358), from the checkout in Docker Desktop on the Mac, with no other install of the file running (it would hold the ports and the network's range): `docker compose -p kinopeer-check -f docker-compose.yml -f docker-compose.build.yml up -d --build` (DEVELOPMENT → Docker), then at `http://localhost:8797` set a password and see Downloads open with no qBittorrent login asked, and Settings show qBittorrent and Prowlarr connected (Prowlarr with no indexers is enough); `docker compose -p kinopeer-check exec prowlarr curl -s http://qbittorrent:8080/api/v2/app/version` answers `Forbidden`, since only Kinopeer's address gets in without a password. Then `docker compose -p kinopeer-check down --volumes`.
  - The image next to a qBittorrent and a Prowlarr of the user's own (#507), installed outside Docker on the Mac (qBittorrent's and Prowlarr's macOS apps, with qBittorrent's Web UI on and a password of its own set): `docker run -d --pull always --name kinopeer-check -p 8797:8080 -v kinopeer-check-data:/data ghcr.io/kinopeer/kinopeer:edge` (Kinopeer Edge's arm64 image, built from `main` as the release PR starts from it), then at `http://localhost:8797` set a password and enter `http://host.docker.internal:8080` with qBittorrent's login and `http://host.docker.internal:9696` with Prowlarr's key, as README → Install next to your own qBittorrent and Prowlarr says, and see Downloads open and Settings show both connected. Before typing each address, press Find (#511) under its field and see `http://host.docker.internal:8080` and `:9696` offered; in a release that changes Find, also start a qBittorrent container on a network Kinopeer's joins (`docker network create kinopeer-check`, both containers with `--network kinopeer-check`, the qBittorrent one named `qbittorrent`) and see `http://qbittorrent:8080` offered. Then `docker rm -f kinopeer-check` and `docker volume rm kinopeer-check-data`. The README's TrueNAS and CasaOS steps are checked again only when they change.
  - The TMDB proxy's cache (#617), when `tmdb-proxy/` changed since the last release and the edge worker has run that change for two days (its answers are kept a day, perhaps two with the cache's tiers): `curl -s -o /dev/null -D - https://tmdb-edge.kinopeer.com/3/configuration` and the same with `-H 'Origin: http://192.168.1.10:8080'`. Only a `cf-cache-status: HIT` shows a kept answer, so ask each again after a `MISS` or `EXPIRED` (the worker's own answer) until it's a `HIT`. It passes when the first's `HIT` has `vary: Origin`, an `etag` of the worker's own (`W/"` and a short code, not TMDB's long hash) and no `last-modified`, and the second's `HIT` has `access-control-allow-origin: http://192.168.1.10:8080` and `access-control-expose-headers: Retry-After`. After the tag, the same on `tmdb.kinopeer.com` two days after the release worker's deploy, which 1.3.0 and later call.
  - qBittorrent's Alternative WebUI (#564), from the checkout in Docker Desktop on the Mac, with Prowlarr's macOS app running, an indexer in it that returns releases for a title you'll search, among them one whose download Prowlarr answers with a redirect rather than a `.torrent` (the indexer's own link, or a magnet link Prowlarr gives only that way), which qBittorrent then fetches itself, and its API key at hand: make the zip as `release.yml` does, but with the edge worker, since the release worker runs the last release until the tag deploys this one (DEVELOPMENT → The Alternative WebUI): `TMDB_PROXY_URL=https://tmdb-edge.kinopeer.com/3 npm run build:webui && rm -rf kinopeer-webui && mv dist-webui kinopeer-webui && zip -qrX kinopeer-webui.zip kinopeer-webui`. Unpack it into an empty folder and follow README → Install as qBittorrent's Alternative WebUI with `docker run -d --name kinopeer-webui-check -p 8080:8080 -e QBT_LEGAL_NOTICE=confirm -v <that folder>:/webui:ro qbittorrentofficial/qbittorrent-nox:5.2.0-1`, its temporary password in `docker logs kinopeer-webui-check`: set Files location to `/webui/kinopeer-webui` in qBittorrent's own web UI at `http://localhost:8080` and Save. Then open `http://localhost:8080` in a private window, which has no qBittorrent session, so Kinopeer's form for qBittorrent's login shows: sign in with qBittorrent's username, `admin`, and its temporary password, then go through onboarding: no TMDB step, since `localhost` gets Kinopeer's key; Find under Prowlarr's address offers `http://localhost:9696`, but enter the Mac's LAN address, `http://<the Mac's IP>:9696`, since qBittorrent fetches some releases' links from inside its container, where `localhost` is the container itself. Search, add that release (its add sheet says its files come as a magnet link's do) and see it in Downloads, then Settings → About → Switch to qBittorrent's interface and confirm, which on `localhost` also has the service worker step aside. It passes when each step works and qBittorrent's own page is back at the end, at once and after a reload. Then `docker rm -f kinopeer-webui-check` and the same with the newest image (`qbittorrentofficial/qbittorrent-nox:latest`), `docker rm -f kinopeer-webui-check` again, and remove `kinopeer-webui/` and the zip from the checkout.
