# Release checklist

What to check before every release, the steps for the day the repository goes public, and what to settle before 1.0, the public release of the app ([SPEC.md](SPEC.md)'s decision log, 2026-10-23). Releasing itself is in [DEVELOPMENT.md](DEVELOPMENT.md) → Releasing.

## Before every release

Go through these for the release PR (the one with the version and the changelog section) and note what was found in its description.

- **The test-gap pile.** List the issues closed since the last release with a `test-gap:*` label, one label at a time: `gh issue list --state closed --label test-gap:uncovered --search "closed:>YYYY-MM-DD"`, and the same for `wrong-layer`, `implementation`, `fake-drift`, `environment`, `silent-test` and `flaky`. Three of one class are a problem of the system, not three accidents; the action per class is in [TESTING.md](TESTING.md) → When we find a bug (three `fake-drift` → compare the fakes with the live services by hand, three `wrong-layer` → rewrite the layer rule, and so on).
- **The suite itself.** New duplicates between layers (a statement checked twice without a comment saying what the second layer sees); the coverage totals against the threshold (`npm run test:coverage`; raise the threshold when the totals have grown, [TESTING.md](TESTING.md) → Coverage); `npm test` still under 20 seconds on the owner's Mac (where that time goes: [TESTING.md](TESTING.md) → Layers) and the `visual` job still around two minutes in CI, or find what got slow; no `flaky` in the recent `visual` job logs.
- **The release workflow's actions.** `release.yml`'s `docker/*` actions run only at a tag, so a version Dependabot moved since the last release first runs there: watch the tag's run, and fix it before the store PR if it fails.
- **By hand, what no layer sees** ([TESTING.md](TESTING.md) → Known blind spots), on `main` as it will be released:
  - On the owner's phone, in Safari on iOS, against Kinopeer Edge built from `main` as the release PR starts from it, which changes no code (the production image behind Umbrel's proxy, since `dev-lan` has no manifest): open Downloads, a title and its releases; drag a sheet closed by its title and swipe behind an open sheet (the page doesn't move); tap a field in Speed limits and in Move files with Downloads scrolled down by a swipe, which collapses Safari's toolbar (the sheet rises above the keyboard, Save visible, the filters and the dimmed backdrop stay); add a release, pause and resume a torrent and change its category, since every call to qBittorrent carries the `X-Kinopeer` header through Umbrel's app_proxy, which no layer runs; check that the installed PWA still opens, that after Umbrel updates Kinopeer the app resumed from the background (not closed from the app switcher) reloads into the new version with the "updated" toast (the page being replaced must already have the update check, which came after 0.6.1: on the first update from an older build, close the app once and check on the next one), and, in it, that the first tap on the field in Move files with Downloads scrolled down doesn't make the page or the sheet jump.
  - Throughout, with Safari's Web Inspector open on Kinopeer Edge (the phone through the Mac's Develop menu): no "Content Security Policy" error in the console (Safari's own "Refused to apply a stylesheet", one per `<select>` on a page, is expected: SPEC's decision log), and the app opening from Umbrel's home screen.
  - After the Umbrel package updates: go through onboarding, a search and adding a release through Umbrel's app_proxy and HTTPS; add a release over plain `http://` on the LAN, where the info hash from the SHA-1 fallback must match qBittorrent's.

## The day the repository goes public

The steps in order, each with who does it and how to check it; a step starts once the one before it checks out. The owner does the clicks in GitHub's and Cloudflare's web UI; a session does what `gh` and a PR can. Once the repository is public, the PR of step 18 removes this section; git history keeps it.

What goes public: the whole history, every PR with its description, comments and head (closed ones too), issues, Discussions, the Actions logs (secrets in them are masked) and the artifacts that haven't expired (14 days).

### While the repository is still private

1. **0.7.2 is released and installed on Umbrel.** The first public version of the code is then a release with its fixes (#270, #292 and the Content-Security-Policy): before it, the fixes would be readable while installs still run 0.7.1. Check: Settings → About on Umbrel shows 0.7.2.
2. **#291 is rebased onto `main` and reviewed again** (a session). It conflicts with `main` already (`CLAUDE.md` → Stack, next to the line #298 changed), and its hunk in this file goes on the rebase, since steps 13 and 14 say what it said. Check: a posted "ready to merge" at its head, CI green.
3. **The maintainer's account** (the owner). Review the personal access tokens, the OAuth and GitHub Apps with access, the SSH and GPG keys, and the organization's webhooks and third-party access; revoke what isn't used. A session's token can't list them.
4. **No real tracker in what goes public** (a session, with `gh`; the owner reads the list of changes first). Rewrite the descriptions of #18, #21, #24, #95, #104, #118, #124, #126, #131, #157 and #255 by `CLAUDE.md` → Conventions, then search every PR's title, description and comments, the issues and Discussions again. The commit history stays as it is: rewriting `main` would break every link to its commits. Check: the second search finds nothing.
5. **A scan for secrets just before** (a session). In a `git clone --mirror` (which brings `refs/pull/*` along), run `gitleaks git --log-opts="--all"` over every branch, tag and pull request head, and search the same history for local addresses, as on 2026-10-28 (gitleaks v8.30.1: no keys or passwords, only placeholders and test values). Expected: only the false positive found then, the path `src/api/qbittorrent/` in `CLAUDE.md` read as a generic API key. A real secret stops the day: revoke it first, then decide what to do with the history.

### Going public

6. **Settings → General → Danger Zone → Change visibility → Public** (the owner).

### Right after

7. **Actions settings** (the owner, Settings → Actions → General), first, since any fork can open a PR that runs our CI from now on: turn on "Require actions to be pinned to a full-length commit SHA" (every workflow pins them since #288); allow only GitHub's own actions and the `docker/*` ones the workflows use; require approval to run workflows for all outside contributors, not only first-time ones. Workflow permissions stay as they are: read-only by default, and no approving of PRs (checked 2026-11-07). Check: `gh api repos/kinopeer/kinopeer/actions/permissions` shows `sha_pinning_required: true` and `allowed_actions: selected`.
8. **Secret scanning and push protection** (the owner, Settings → Advanced Security). Check: Security → Secret scanning lists no alert once the scan of the history is done.
9. **Private vulnerability reporting** (the owner, Settings → Advanced Security). `SECURITY.md` sends reports to Security → Report a vulnerability, which GitHub offers only on a public repository. Check: that link opens the form, not a 404.
10. **CodeQL** (the owner, Settings → Advanced Security → Code scanning → CodeQL analysis → Default), for JavaScript/TypeScript and Actions. It isn't a required check; an alert it raises is a bug like any other ([TESTING.md](TESTING.md) → When we find a bug). Check: its first analysis finishes.
11. **Rulesets** (the owner, Settings → Rules → Rulesets):
    - `main`: block force pushes and deletion; require a pull request, with no approvals required, since the reviews are posted as comments from the owner's account, which can't approve its own PRs; require the `check`, `docker`, `visual` and `smoke` checks, without "Require branches to be up to date", so PRs merged in a row don't each wait for CI again; nobody bypasses it.
    - Tags `v*`: restrict creating, updating and deleting them, with the Repository admin role bypassing, since release tags are pushed from the owner's machine. The `Release` workflow creates no tag (`gh release create --verify-tag`).

    Check: `gh api repos/kinopeer/kinopeer/rulesets` lists both, and an open PR shows the four checks as required.
12. **Allow auto-merge** (the owner, Settings → General). Until the rulesets, `gh pr merge --auto` didn't wait: with nothing blocking the merge it merged right away, even while checks were running, so PRs were merged by hand once every check passed. From here it waits for the four checks.
13. **The `deploy` environment** (the owner): steps 1 and 2 of #291's description, which stay there so the steps live in one place: the environment that only `main` and `v*` tags can use, and its four secrets (a new Cloudflare token, the current TMDB key, a new edge store deploy key next to the old one). It waited until now because a private repository on GitHub Free has no environment secrets or deployment rules.
14. **#291 merges, then the old credentials go**: steps 3 to 6 of its description (the merge on the owner's OK, the rest by the owner). The Edge run after the merge passes, `TMDB proxy key` runs from `main`, the repository's four secrets are deleted, the old Cloudflare token is revoked, the old deploy key leaves the edge store, and the description's steps shrink to a line. Check: Settings → Secrets and variables → Actions lists no repository secret, and `https://tmdb.kinopeer.com/3/configuration` answers 200.
15. **`kinopeer.com` points at the repository** (the owner, in Cloudflare's dashboard), now that a visitor won't get a 404 there. The zone has only the TMDB proxy's hosts and GitHub's verification record, so first add proxied `AAAA` records for `@` and `www` with `100::`, without which Cloudflare doesn't take the request. Then one Single Redirect rule matching exactly `http.host in {"kinopeer.com" "www.kinopeer.com"}` (no wildcard, which would catch the `tmdb` hosts) sends a 302 to `https://github.com/kinopeer/kinopeer` without the path: not a 301, which browsers cache, since a site may replace it later. `kinopeer.org` and `kinopeer.app` can get the same. The repository's Homepage stays empty while the domain is a redirect, since it would lead straight back. Check: `curl -sI https://kinopeer.com` and `https://www.kinopeer.com` answer 302 to the repository, and `https://tmdb.kinopeer.com/3/configuration` still answers 200.

### Checks and loose ends

16. **How the repository looks from outside** (the owner, signed out of GitHub):
    - The social preview: upload `docs/social-preview.png` (1280×640: the icon, the name and the tagline, no TMDB artwork) in Settings → General → Social preview, which a private repository can't take unless it had one before, and check how a link to the repository unfurls.
    - The README's CI and release badges render; they show only once the repository is public.
    - The links in Settings → About (Ideas, a bug report with the version filled in, the repository) and in the README open without a 404, which until now they gave everyone but collaborators.
17. **Links in the Umbrel manifests** (a session; each merges on the owner's OK): `repo` and `website` point at this repository and `support` at its issues, where today `website` and `support` point at the store repositories and `repo` is empty.
    - The Homelab store, `homelab-kinopeer/umbrel-app.yml`, in a PR.
    - The edge store, `homelab-edge-kinopeer/umbrel-app.yml`: the `Edge` workflow writes only `version` and `releaseNotes` there, so the links are the one edit by hand that stays ([DEVELOPMENT.md](DEVELOPMENT.md) → Edge builds).
18. **The docs say the repository is public** (a session, in a PR): [DEVELOPMENT.md](DEVELOPMENT.md) → Releasing drops "the code repository is private for now", this section goes, Before 1.0's "The repository is public" is ticked off, and `git grep -n -i -e private -e 'goes public' -e 'once the repository'` finds nothing else left to change (the decision logs keep their words).

## Before 1.0

What to settle before 1.0. Add an item whenever something comes up that can wait until then; the PR that settles one removes it and says so in its description. The features 1.0 waits for are in [ROADMAP.md](ROADMAP.md).

- [ ] **The repository is public.** The day above is done.
- [ ] **TMDB key.** Decided on 2026-11-04 (SPEC's decision log): Kinopeer's key behind its proxy on Cloudflare Workers, with a key entered in Settings or `TMDB_API_KEY` as overrides; it ships in 0.7. Before the public release: TMDB confirms in writing that the proxy fits its terms (they make the license personal and non-transferable). The README says where TMDB calls go since 0.7. Consider registering that key under a TMDB account of Kinopeer's own rather than the owner's personal one, so misuse isn't tied to a personal account. Decide how the proxy outgrows Cloudflare's Free plan: its 100,000 requests a day are the account's, cache hits included, and over them the workers refuse every call until midnight UTC, so one script looping over a cached URL, or plain growth, stops TMDB for every install without a key of its own. The options are Workers Paid ($5 a month for 10 million requests) or a WAF rate limit on `kinopeer.com`, the workers' domain since the rename, in front of them (beside the custom rule that already lets only the proxy's paths through, `DEVELOPMENT.md` → The TMDB proxy); check the day's counts in Cloudflare's dashboard first. Decide the per-IP limit with it: the worker's own is soft (`DEVELOPMENT.md` → The TMDB proxy), so a strict one is a WAF rule on `kinopeer.com` or a counter in a Durable Object.
- [ ] **Official Umbrel App Store.** The image (`ghcr.io/kinopeer/kinopeer`) and the [Homelab Community App Store](https://github.com/MrShakhov/umbrel-homelab-store) are already public. Submit to getumbrel/umbrel-apps: manifest, icon, gallery screenshots, release notes, multi-arch image pinned by digest.
- [ ] **Prowlarr key from another app's data.** The Umbrel package mounts Prowlarr's config folder read-only to read its API key (the folder, not the file: a file bind mount would keep pointing at the old file after Prowlarr rewrites it). Umbrel's own Prowlarr package links apps the same way (its media-app-configurator mounts other apps' data), but the official App Store review may still question it. The fallback exists: a Prowlarr key entered in Settings → Connections is kept on the server like the TMDB key and wins over `config.xml`, so the mount can be dropped if the review asks, with the README's "Prowlarr needs no setup" changed to say where to enter the key.
- [ ] **Images pinned by digest.** The `Dockerfile`'s `node:24-alpine` moves by tag, in both stages, and `.github/dependabot.yml` has no `docker` ecosystem: pin it by digest and let Dependabot move the digest. The release job also pulls two images by tag and runs them privileged: `tonistiigi/binfmt:latest` (`setup-qemu-action`) and `moby/buildkit:buildx-stable-1` (`setup-buildx-action`'s docker-container driver). Dependabot can't move those, so decide between pinning them by digest, with a manual bump under Before every release, and leaving them as they are, knowingly.
- [ ] **A site on `kinopeer.com`.** The domain redirects to the repository from the day it goes public (step 15 above). Decide whether a landing page replaces it, on GitHub Pages for example (the organization has verified the domain), or the redirect stays. With a site, the repository's Homepage and the organization's profile can point at it, and GitHub then shows the organization as verified, which it does only when the profile's website or email is on a verified domain.
