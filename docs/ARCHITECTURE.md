# Architecture

How Kinopeer is built, area by area: where each part lives, what it does and the rules a change to it follows. What the product does is in [SPEC.md](SPEC.md), running and releasing it in [DEVELOPMENT.md](DEVELOPMENT.md), the tests in [TESTING.md](TESTING.md), and the conventions every PR follows in [CLAUDE.md](../CLAUDE.md), which loads this file into every Claude Code session.

## The server

### The qBittorrent bridge

The browser talks to qBittorrent and Prowlarr only through same-origin routes. `/qbt/api/*` → qBittorrent Web API, served by `server/qbittorrent.ts` (Vite middleware in dev using `QBITTORRENT_URL` from `.env.local`, and the production server). The server always logs in itself (login saved from the app's connect screen via `PUT /api/settings/qbittorrent`, else `QBITTORRENT_USERNAME`/`QBITTORRENT_PASSWORD`), keeps the session and re-logs in on a 403; after one rejected login it stops trying that login at that address (IP-ban protection; a new address or login is tried afresh) and requests go without a session, so qBittorrent's auth bypass still works and otherwise the app asks for a login. Browser cookies never reach qBittorrent. The bridge forwards only the calls `src/api/qbittorrent/` makes, each with its method (`ENDPOINTS` in `server/qbittorrent.ts`, matched on the path as written, so no `..` or encoded path reaches `/auth/*` or the preferences), and only requests with the `X-Kinopeer` header the client sends on every call: it attaches the server's session and rewrites `Origin` and `Referer`, so without that header a form on any other site could act through it, and a page can't add a header to a cross-origin request without a CORS preflight, which the bridge never allows (Vite's own CORS is off in `vite.config.ts`, since in dev and preview it would answer that preflight for any localhost origin before the bridge runs; `vite.config.test.ts` starts both servers from the config to check). The bridge also hands the server's own jobs its session (`qbittorrentBridge().get` and `post`): the matches cleanup and the notifications. A new qBittorrent call in the client goes into `ENDPOINTS` too, and into `EVERY_CALL` in `server/integration/qbittorrent.test.ts`, which doesn't compile without it and checks that each passes the bridge. Of qBittorrent's preferences, which hold its own login and web UI settings, the bridge lets only the default save path through: `BODY_FILTERS` reads an `app/setPreferences` body (16 KiB at most) and sends it on only as a form with one `json`, an object with nothing but a string `save_path`, written anew, and answers anything else 400 without asking qBittorrent, a query on the call among it. Never call those services cross-origin. Each bridge, and the checks behind `PUT /api/settings/tmdb`, `/prowlarr` and `/qbittorrent` (the TMDB key's with TMDB's time limit too), gives its request upstream up once the browser's request has gone before its answer (`abandoned` in `server/abandoned.ts`, taken before the first `await`), so a request the app stopped waiting for doesn't hold a connection to the service until it answers; the shared session's login isn't given up with it, since other requests wait for it too (a login saved from the connect screen is the browser's own attempt, and is). A write to qBittorrent given up that way has normally reached it whole already (its body is small and goes out at once), and the browser that left learns the outcome from the next poll either way.

### TMDB and its proxy

TMDB goes through `/tmdb/*` → `https://api.themoviedb.org/3/*` (`server/tmdb.ts` adds the key, so it never reaches the browser) and images through `/tmdb-img/*` → `https://image.tmdb.org/t/p/*`; a path that `fetch` wouldn't keep as written (dots, encoded dots, a backslash) or with an encoded slash or backslash is refused, since it would lead out of `/3/` or `/t/p/` (#305). Client: `src/api/tmdb/`. The bridge marks every answer with the qBittorrent bridge's `BRIDGE_HEADER`, so the client throws `KinopeerUnreachableError` for a failure without it, something in front of the server answering for it, and `TmdbFailedState` (`src/screens/`, the title page's, Search's and the phone's releases' state for a TMDB call that failed) tells by `unreachable` whether Kinopeer's server or TMDB didn't answer, with Open again where `useMayOpenAgain` says so, or that there's no key (#537). Kinopeer's own key sits behind a Cloudflare Worker, `tmdb-proxy/worker.ts` (`docs/DEVELOPMENT.md` → The TMDB proxy): it answers only the paths the client calls, has Workers Cache keep TMDB's answers (the Cache API does nothing on `workers.dev`) and limits calls per IP, an IPv6 caller by its /64. Two workers, `kinopeer-tmdb-edge` deployed by `edge.yml` and `kinopeer-tmdb` by `release.yml`, both through `tmdb-proxy.yml`, which has no trigger of its own and deploys a worker only when its fingerprint (`tmdb-proxy/fingerprint.ts`) differs from the tag of the version it runs; each answers on a Workers Custom Domain, the release worker on `tmdb.kinopeer.com` and the edge worker on `tmdb-edge.kinopeer.com` (`wrangler.jsonc`'s `routes`, not `workers.dev`), so the deploy token needs Workers Routes on that zone. A new TMDB path in the client needs adding to its `ROUTES` too (and, outside `/3/`, to the WAF rule on `kinopeer.com` that DEVELOPMENT names), and a path is never removed or changed while a released version calls it: a breaking change goes into a new worker. The server sends calls without a key there (`proxyBase` in `server/tmdb.ts`, the address from `tmdbProxy` in `server/main.ts`: `TMDB_PROXY_URL`, else the edge worker baked into edge images and defaulted to by `vite.config.ts`, else the release worker), and `GET /api/settings` says `source: 'shared'` then, so onboarding skips the key step and Settings names Kinopeer's key. It sends no `Authorization` there, which Workers Cache would bypass. A call or an image TMDB (or the proxy) hasn't started answering in `TMDB_TIMEOUT_MS` (15 s, as long as the client's title lookups wait) is given up with a 504, while a body that has started may stream for longer (an image to a slow phone); qBittorrent's and Prowlarr's requests have no such limit, since a Prowlarr search across indexers can rightly take long, apart from `/prowlarr/failing`'s own and the checks behind `PUT /api/settings/qbittorrent` and `/prowlarr` (`ADDRESS_CHECK_TIMEOUT_MS`, 15 s, in `server/settings.ts`, past undici's 10 seconds to connect).

### Why a service didn't answer

When a request to qBittorrent or Prowlarr fails without an answer, `connectionFailure` (`server/connectionFailure.ts`) names why from what `fetch` threw, by the code in its `cause` (the same on Linux and macOS): `name` (the name doesn't resolve), `refused`, `timeout` (undici's time limits, the host unreachable, or the caller's own limit), `http` (an https address on a plain HTTP port), `certificate` (one the server doesn't trust) or `closed` (closed with no answer, or an answer that isn't HTTP), else nothing (#508). The list is `CONNECTION_FAILURES` in `src/api/connectionFailure.ts`, which the server imports only as a type. The checks behind `PUT /api/settings/qbittorrent` and `/prowlarr` send it as `failure` beside `unreachable`; the qBittorrent bridge sends it in `FAILURE_HEADER` (`x-kinopeer-failure`) beside its 502, since its answer is text, and the Prowlarr bridge as `failure` in its JSON. The clients keep it on their errors (`SettingsError`, `QbittorrentError`, `ProwlarrError`), only a cause this app knows (`knownFailure`), read through `failureOf`, and `failureText` (`src/lib/failureText.ts`) says what to check, naming the service, and for qBittorrent its Web UI where nothing listens. It's shown on the forms' address field or banner (`QbittorrentLoginForm`, `ProwlarrKeyForm`), in the connect screen's `UnreachableState` (the session's `failure`), in Settings' connection rows and in the releases' error state (`Releases.failure`), each saying what it said before when there's no cause. The poll doesn't read it. A refusal that does answer is told apart too where it would read as another: `checkQbittorrent` answers `host-refused` when qBittorrent's Host header validation refuses the address's port (`refusesHost` in `server/qbittorrent.ts`: after a login's 401, which qBittorrent 5.3 also gives a wrong password, the version asked without a session gets 401 rather than 403, and only qBittorrent's own 401, `isHostRefusal`: the text `Unauthorized` with the `X-XSS-Protection` qBittorrent puts on every answer and no `WWW-Authenticate`, so another 401 stays `not-qbittorrent` without a login and a wrong login with one, as before), which `PUT /api/settings/qbittorrent` sends as 502 `host-refused` and `QbittorrentLoginForm` says over the form.

### Hints for Kinopeer in a container

`container(env)` (`server/container.ts`, read once in `kinopeerServer`, which takes a faked `ContainerSystem` from the integration stand) is undefined outside a container and under host networking, and otherwise gives two hints (#509), over a `ContainerSystem` the tests fake (files, directories, name lookups, the route out, the interfaces). `inContainer` tells one by `KINOPEER_CONTAINER=1`, which the `Dockerfile` sets, else `/.dockerenv` or `/run/.containerenv`, and `ownNetwork` whether it has a network of its own: under host networking its `/sys/class/net` shows the host's interfaces, one of them backed by a device (`<name>/device`) or a bridge (`<name>/bridge`), where a container's own are veths or macvlans, and then localhost is the host and qBittorrent sees the host's address, so neither hint holds; a doubtful setup reads as the host's network (an empty listing, which only an unreadable `/sys/class/net` gives, among them), and the setups it misreads are SPEC's known limits, not more rules. `hostAddress` is the host as the container reaches it: `host.docker.internal` when it resolves (in `RESOLVE_TIMEOUT_MS`, 2 s), else the default gateway of `/proc/net/route` (`defaultGateway`, which skips a default route with no gateway). `sourceFor(host)` is where qBittorrent at `host` sees Kinopeer come from: the local address a UDP socket connected to its IPv4 address goes out from (`localAddressTo`; a connect sends nothing, and Node hands a failed one's error to its callback), and that interface's subnet, only when the service's address is on it (`sourceOf`), else nothing, and nothing for a loopback address. The checks behind `PUT /api/settings/qbittorrent` and `/prowlarr` add `container` to an `unreachable`, `not-qbittorrent` or `not-prowlarr` refusal for an address on localhost (`isLoopback`, `localhostHint`), with `hostAddress` the same address at the host (`atHost`) when known, and `source` to an `invalid-credentials` for no username; the qBittorrent bridge sets `SOURCE_HEADER` (`x-kinopeer-source`, the address and the subnet with a space between) on qBittorrent's 403 when the server has no login. The clients take only the shapes the server sends (`src/api/containerHints.ts`): `SettingsError.container` and `.source`, and `UnauthorizedError.source`, which the session keeps as `signed-out`'s `source`. `LocalhostHint` and `BypassHint` (`src/screens/ContainerHints.tsx`) show them: the first in `QbittorrentLoginForm` and `ProwlarrKeyForm` where they ask for the address, with Use this address putting the host's in the field, the second over the qBittorrent form, from the session (`ConnectScreen`'s `source`, not while the form asks for another address) until the form's own check answers, then from that check alone. A hint that can't be had (a lookup that throws) leaves the answer as it would be without it.

### Find

Find (#511, `server/find.ts`) has the server look for qBittorrent or Prowlarr for a form: `POST /api/settings/qbittorrent/find` and `/prowlarr/find` in `server/settings.ts` (`findAddresses`), refused as a saved address is (`addressRefusal`: 409 `env-address` or `auth-off`), answer `{ addresses }` (`FoundAddresses`). `findService` tries `candidateHosts` (the usual names in `USUAL`, then what the route passes as near, `localhost` outside a container and `host.docker.internal` with the container's `hostAddress` inside one, then `subnetHosts`: the /24 around each of the server's own private IPv4 addresses (`isPrivate`: RFC 1918's and 100.64.0.0/10), none around a public one or one on loopback, `MAX_SUBNETS` of them) on each of the service's usual ports, `PARALLEL` at a time (`pooled`): `opens` (a TCP connect within `CONNECT_TIMEOUT_MS`), then `identifies` within `IDENTIFY_TIMEOUT_MS`, through `answersAsQbittorrent` (`server/qbittorrent.ts`: a version, or the 403 or Host refusal only qBittorrent gives) and `answersAsProwlarr` (`server/prowlarr.ts`: its sign-in page, so no key leaves the server), each reading only the start of the answer (`textPrefix`, 64 KiB), so a host that streams on a scanned port can't fill the server's memory; an address found by name hides the same port at that name's address. Everything it reads and asks is a `FindSystem`, which the route tests fake, and the integration stand gives the real one with no networks (`NO_NETWORKS` in `server/test/integration.ts`), so no test sweeps the network it runs on; `kinopeerServer`'s `find` option also sets the ports, so the fakes are found on theirs. The search stops when the browser leaves (`abandoned`, taken before the host's lookup). In the app, `FindAddress` (`src/screens/FindAddress.tsx`) sits under the address field of `QbittorrentLoginForm` and `ProwlarrKeyForm` where they ask for one, through `findAddresses` (`src/api/settings/`), and hands the form a picked address as if it were typed and a refusal to say as a save's. SPEC's decision log holds its fixed scope and known limits.

### Server-side settings

Server-side settings: `server/settings.ts` keeps what the user enters in the app (the TMDB key, Prowlarr's key and address, qBittorrent's login and address, and the download defaults) in `$KINOPEER_DATA_DIR/settings.json` (default `./data`, git-ignored; `/data` volume in Docker). Vite's dev server would serve that folder with the rest of the checkout (`dev-lan` to the LAN), so `vite.config.ts` lists it in `server.fs.deny`, by its path and its real path, beside Vite's own defaults, which a list of our own replaces (#476); `vite.config.test.ts` checks both. A data directory under `public/` would still be served, since Vite serves that folder without the check. `GET /api/settings` says only whether each secret is set and where it comes from, and where each service's address comes from (`address`: a saved one in full, since it's no secret and a form edits it; the environment's without its value); `PUT /api/settings/tmdb` checks the key with TMDB, then saves it (`DELETE` forgets it, only when `TMDB_API_KEY` or the proxy would serve TMDB without it, `fallback` in `GET`), and `PUT /api/settings/prowlarr` checks its key with Prowlarr's `system/status` (`DELETE` forgets it, only when the server has a key of its own, `serverKey` in `GET`); `PATCH /api/settings/downloads` merges in the download defaults sent (`downloads` in `GET`, null until one is saved). A saved key wins over `TMDB_API_KEY`. Client: `src/api/settings/`. The page shares one answer of `GET /api/settings` (`getSharedServerSettings` in `src/api/sharedAnswers.ts`, `SERVER_SETTINGS_KEY`, fresh for `SERVER_SETTINGS_FRESH_MS`, a minute) between the download defaults' load, onboarding's TMDB key step and Settings, and every save or forget keeps the settings it answers with in its place (#382). Onboarding asks for the key after qBittorrent connects when the server has none and the proxy is off, then for Prowlarr's address and key when the server has no address for Prowlarr and Kinopeer's own login is on (`setupSteps` in `src/session/useSetupSteps.ts`, `src/screens/TmdbKeyScreen.tsx`, `ProwlarrSetupScreen.tsx` with `ProwlarrKeyForm`'s `askAddress`), each skippable until the next visit; Settings → Connections changes the key, and its sheet (`TmdbKeyForm`, `forget`) goes back to the fallback. Where an address may be saved from the app (none from the environment and Kinopeer's own login on), Settings → Connections changes it with the form that saves it elsewhere, so there's one per service: qBittorrent's through `QbittorrentLoginForm`, the connect screen's, in a sheet that saves through `useQbitSession`'s `signIn` (`App` hands it to `SettingsScreen`), so the app's session follows the new address, and Prowlarr's through `ProwlarrKeyForm` with `askAddress`, each started at the saved address (`initialAddress`). A service's address is the other way round from its secrets: `QBITTORRENT_URL` and `PROWLARR_URL` win over one saved from the app (`qbittorrentAddress`, `prowlarrAddress`), which the bridges, the settings' checks and the matches cleanup read on every call, so a saved one applies at once (the qBittorrent bridge's session is kept per address and login). `PUT /api/settings/qbittorrent` and `/prowlarr` take an address (`url`) beside the login or the key, check them together at it (qBittorrent's login, or its auth bypass with an empty username, then its version through `checkQbittorrent`, so a page that answers every path isn't taken for it), and save both; one is refused while the environment sets that address (409 `env-address`) and with Kinopeer's own login off (409 `auth-off`), since the server then calls whatever address it was sent, and one that isn't http(s), has a login, a query or a fragment in it is refused as `invalid-address` (`parseAddress` in `server/address.ts`). The environment's login and key (`QBITTORRENT_USERNAME`, `PROWLARR_API_KEY`, `PROWLARR_CONFIG_XML`) apply only with the environment's address (`kinopeerServer`), so an address a browser sent gets only a login or key saved from the app.

### Notifications

The server tells the user when a download finishes (`server/notifier.ts`): `startNotifier`, one of `startJobs()`'s jobs beside the matches cleanup, checks every `NOTIFY_INTERVAL_MS` (30 s), and only while a channel says it's `ready()`: with none it asks qBittorrent nothing. A pass asks for the torrents tagged `NOTIFY_TAG` (`kinopeer:notify`, the client's `NOTIFY_TAG` in `src/api/qbittorrent/client.ts`, which the integration test checks is the same) with `torrents/info?tag=` through the bridge's `get` and the server's session, never `sync/maindata`, whose `rid` the browsers' polls share; a finished one (`isFinished`: complete and in a seeding or stopped-after-finishing state) goes out through every ready channel, and the tag comes off through the bridge's `post` (`torrents/removeTags`), so the tag is the "notify once" flag and lasts across restarts. What each channel did with each torrent is kept in memory for the pass after: a channel that answered isn't sent to again, one that didn't is tried again after `RETRY_DELAYS_MS` (30 s, 2 min, then every 10 min) counted from the start of the pass that sent it, or the `retryAfterMs` it threw, counted from its answer as the service counts it, whichever ends later, and one that refused counts as done, with a line in the log. A channel is a `NotifyChannel` (`id`, `ready`, `send`, and `forget`, which the notifier calls for a torrent that lost its tag or went away while it was sent again, so a channel drops what it kept for it), so Web Push sits beside Telegram. The tag is switched from the torrent's page (`useNotifyToggle` in `src/screens/`, `addTags` and `removeTags` on the torrent requests, kind `notify`) and set when adding a release (`AddReleaseSheet`'s switch, starting from the `notify` download default), each shown only while `GET /api/settings` says `notifications` (some channel is set up: `useNotificationsAvailable`), and without it the default adds no tag.

Telegram (`server/telegram.ts`) is a small Bot API client: `botName` (`getMe`), `startedChats` (the chats that sent the bot `/start` among its last 100 pending updates, newest first, or `conflict` when Telegram answers 409 because a webhook or another program takes the bot's updates, which the settings' routes answer as 409 `bot-in-use`) and `sendMessage`, all with `TELEGRAM_TIMEOUT_MS` (15 s); a 429 or a 5xx throws `TelegramUnavailable` with Telegram's `retry_after`, a refusal answers `'rejected'`, and no error carries the token, which is part of the URL. `telegramChannel` (`server/telegramChannel.ts`) sends `finishedText` (`server/notifyText.ts`, with its texts in `server/locales/*.json`, the server's own translation files, so the app's bundle, which never shows them, doesn't carry them) in the language saved with the chat, and records in the settings which part Telegram refused (`refusedPart`: `getMe` tells the token from the chat), as long as the bot and chat are still the ones it sent to; when `getMe` doesn't answer, a refusal already recorded for that bot and chat stands, and otherwise `send` throws, so the notifier sends again and the next refusal says which part. The title comes from `finishedTitle` (`server/finishedTitle.ts`): the torrent's match on the server or its `tmdb:` tag, then TMDB through `tmdbJson` in `server/tmdb.ts` (the key or the proxy, with `TMDB_TIMEOUT_MS`), else the release name alone. The bot's token and chat are kept in `settings.json` (`StoredTelegram`) and set up through `/api/settings/telegram` (`PUT` the token, checked with `getMe`; `GET` and `PUT /chat` find the chat that sent `/start` and save it once the user has seen it, only while the token is the one it was found with; `POST /test`; `GET /check`; `DELETE`); `GET /api/settings` says only the bot's name, the chat's name and kind and which part Telegram refused (`telegram`), never the token. Client: `src/api/settings/`, the form in `src/screens/TelegramForm.tsx`, whose requests (the token, finding the chat, the chat, the test, turning off) go through Settings' saves as one target, kind `telegram`, so one is on its way at a time: the form open takes the outcome, else it's handed to Settings and said in a toast (a chat found then is forgotten).

Web Push (`server/webPush.ts`) is written on `node:crypto`, with no dependency, since the image ships no `node_modules`: `encryptPayload` encrypts a payload as RFC 8291 says (aes128gcm, one record of at most `MAX_PAYLOAD` bytes; its test checks RFC 8291's own example byte for byte), `vapidAuthorization` signs the request with the server's VAPID key (RFC 8292, an ES256 JWT for the push service's origin, valid 12 hours) and `sendPush` sends it with `PUSH_TTL_S` (a day) and `PUSH_TIMEOUT_MS` (15 s), following no redirect, answering `'sent'`, `'gone'` (404 or 410: the subscription is no more) or `'refused'` (a redirect among them), and throwing `PushUnavailable` with the service's `Retry-After` on a 429, a 5xx or no answer; keys it can't encrypt for throw as themselves, before the request, so they aren't taken for a service that didn't answer; no error carries the endpoint, which is the device's secret address. `isPushEndpoint` lets through only an HTTPS address with no port or login on the push services browsers use (Google's, Mozilla's, Apple's, Microsoft's, by the services' own host names, `PUSH_SERVICE_HOSTS`), so a page can't make the server send requests into its own network (SPEC's decision log, 2026-11-20); `PUSH_TEST_ORIGIN` adds the fake service of the tests. `PushStore` (`server/push.ts`) keeps `push.json` in the data directory, read as the server starts (`loadStores` in `server/main.ts`, with the settings and the matches), since the notifier asks it without waiting: the VAPID key pair, made on the first device turned on (only the public key leaves the server), and the subscriptions, one per device (its endpoint, its keys and the language it was turned on in), the newest `MAX_SUBSCRIPTIONS` (50). `pushMiddleware` serves `/api/push` behind Kinopeer's login, JSON bodies only: `GET key`, `PUT subscription` (checked endpoint, and keys `isPushKeys` can encrypt for: a P-256 point and a 16-byte secret; `replaces` swaps a renewed one in and keeps its language) and `DELETE subscription`, both answering the server's settings, which the page keeps in its shared answer (`SERVER_SETTINGS_KEY`), and `POST test`, which sends this device a test notification (404 `unknown-device`, 410 `gone` after forgetting it, 502 `refused`, 503 `unreachable`). `GET /api/settings` says only how many devices get push (`push.devices`). `pushChannel` (`server/pushChannel.ts`) is the second `NotifyChannel`, `ready` while some device is kept: it sends each device `finishedText`'s title and release name under "Download finished" in its own language, with the torrent's page as the notification's address and its hash as its tag; it remembers which devices took a torrent, so a retry goes only to the rest (until the notifier has it `forget` the torrent), forgets a gone one, counts a torrent done when every device took it or refused it (`'rejected'` when none took it), and throws the longest wait a service asked for when one didn't answer.

In the browser, `src/pwa/push.ts` reads whether this device can get push from the browser alone (`pushState`: not a secure context, an iPhone or iPad outside the Home Screen app, no Push API, no service worker, notifications blocked, else off or on by `pushManager.getSubscription`), so Settings asks the server nothing about push when it opens; `turnOnPush` asks for the permission in the tap (as Safari requires), takes the server's key, drops a subscription made for another key and saves the new one in the interface's language, `turnOffPush` has the server forget the device before the browser drops it, and `testPushDevice` sends the test and, when the server answers it doesn't send to the device (`unknown-device`, `gone`), drops the browser's subscription too, so the card shows it off and Turn on subscribes afresh. `usePushDevice` (`src/screens/`) gives Settings → Connections its push card, with what each failure says, its actions sent through Settings' saves (A screen's own requests, below), kind `push`, one target for the device: the card shown again takes the outcome, its state over what the browser said as it showed, else a toast says it. Client: `src/api/push/`.

### Kinopeer's own login

`server/auth.ts` (`kinopeerAuth`) is the first route after the host check and `/healthz` in `kinopeerServer()`, so the production server and Vite's dev and preview servers all have it. With `KINOPEER_AUTH` on (the default; `off` where a login sits in front, as Umbrel's app_proxy does for the package; any other value stops the server), every path `guarded` names (`/api`, `/qbt`, `/prowlarr`, `/tmdb`, `/tmdb-img`, matched as written and as `new URL` reads it, in any case, since routes match one or the other) answers 401 with `X-Kinopeer-Auth: sign-in` or `set-up` until the browser has a session; the app's files, `/healthz` and `/api/auth/*` stay open. The password is `KINOPEER_PASSWORD` when that's set (8 to 256 characters, as one set in the app, else the server doesn't start: `envPassword`; hashed on the first request after a start; a changed one ends every session), else the one the first visitor sets (`POST /api/auth/setup`, 409 once one is set). `auth.json` in the data directory keeps it as a scrypt hash (`hashPassword`, Node's `node:crypto`), with the sessions by the SHA-256 of their token, so the file signs no one in. It's read with the first request the login holds back, not at startup, and only a missing file means no password yet: one it can't read or parse answers 500 `storage` to everything it guards until it can (a strict `JsonFile`), rather than asking for a new password. With the login off, nothing reads or writes it, and the login's own routes answer 409 `auth-off`. A session is a `kinopeer_session` cookie (`HttpOnly`, `SameSite=Strict`, `Secure` over HTTPS or behind a proxy that says so with `X-Forwarded-Proto`), lasting `SESSION_MS` (30 days) from its last use, moved on at most once a day so a session in use isn't written with every request, and never with the TMDB bridges' answers, which pass on TMDB's caching, so a shared cache may keep them (TMDB's images are public), and `MAX_SESSIONS` (100) at most. `PUT /api/auth/password` keeps only the session that changed it, and a sign-in whose password was checked against the hash a change has since replaced starts no session. `LoginThrottle` (`server/loginThrottle.ts`) counts wrong passwords per address (`clientKey`: an IPv6 one by its /64) in memory, each counted before the hash is checked, so requests sent at once count too: five lock the address out for 15 minutes, each next lock twice as long up to a day, and the answer carries `retryAfterMs`. The login's routes take only JSON bodies, which another site's page can't send without a CORS preflight, as the bridges' `X-Kinopeer` check holds. `GET /api/settings` says whether the login is on and where its password comes from (`auth`), so Settings asks nothing more.

In the client, `fetchKinopeer` turns such a 401 into `SignInRequiredError` and sets `signInNeed` (`src/api/auth/signInNeed.ts`, a store of its own outside React, so the clients run without it). `App` renders `SignInScreen` in place of everything else while it's set, and signing in mounts the app afresh, so every screen asks again what was held back. Settings → Sign-in has Change password (`ChangePasswordForm`) and Sign out (`signOut`, which also forgets the page's shared answers, `sharedRequests`). The integration stand (`server/test/integration.ts`) and the smoke stand turn the login off but for their own login tests.

### Prowlarr

Releases come from Prowlarr through `/prowlarr/*`, served by `server/prowlarr.ts` (Vite middleware in dev, and the production server), not a plain proxy: it adds `PROWLARR_API_KEY` and strips it from results, because Prowlarr's download links carry the key. The key (`prowlarrKey` in `server/settings.ts`) is the one saved from Settings → Connections (`ProwlarrKeyForm`), else `PROWLARR_API_KEY`, else read on every request from Prowlarr's `config.xml` at `PROWLARR_CONFIG_XML` (the Umbrel package mounts it). `/prowlarr/search` returns `Release[]`; `/prowlarr/download?token=` returns the `.torrent` or `{ magnet }`; `/prowlarr/status` returns `{ version, indexers }` for the Settings connection check, whose answer About also shows (`SettingsScreen` runs the checks and both read them). `/prowlarr/failing?within=<ms>` names the enabled indexers that failed in that many milliseconds or are on hold (Prowlarr's search doesn't say), which `useReleases` asks once a search answers, without holding its results, for the count's line (`ReleasesCount` in `src/screens/ReleasesBlock.tsx`, which names them on a tap), or a note when there's no count to say it: under the empty state when nothing was found (#401), above the empty state when the filters let nothing through on a phone. A search the server can't send for want of Prowlarr's address or key (`not-configured`), or whose key Prowlarr refuses (`unauthorized`), throws `ProwlarrSetupError`, which `useReleases` gives as the `setup` or `rejected` status (one without the server's code, something in front of the server answering, is `error`); `ProwlarrSetupState` (`src/screens/`) then reads the server's settings (the page's shared answer, asked for only in that state), offers `ProwlarrKeyForm` in a sheet, with the address where the app can set it, as Settings does, and searches again once it's saved (#510). Client: `src/api/prowlarr/`. Browser clients call these routes, and every other route of Kinopeer's, through `fetchKinopeer` (`src/api/fetchKinopeer.ts`): with `credentials: 'same-origin'`, because a proxy in front of Kinopeer (Umbrel's app_proxy) authenticates with cookies, and with `redirect: 'manual'`, because Kinopeer's routes never redirect, so a redirect is that proxy sending the request to its sign-in on another origin once its cookie lapses (#303). Then `startProxySignIn` (`src/pwa/proxySignIn.ts`, started in `main.tsx`, which hands it to the clients through `onProxySignIn`, so they also run without a DOM) loads the screen the app is on again with `PROXY_SIGN_IN_PARAM`, at most once per `SIGN_IN_RETRY_MS`, and takes the parameter out of the address the proxy sends it back to; back from a sign-in it doesn't sign in again until a request is answered without a redirect (`answered`), so a cookie that doesn't stick can't loop. `loadPastTheShell` there is the same load without that limit, for Open again, which `UnreachableState`, `OfflineBanner` and the connect screen offer beside Retry (the second action of `Banner` and `EmptyState`) when `useMayOpenAgain` (`src/lib/unreachable.ts`) says nothing answered for Kinopeer's server (`unreached`, as against `kinopeer`, something answering for it), the device is online and a service worker controls the page: the browser then shows a sign-in or a certificate it no longer trusts (#311). Two actions in a `Banner` go under its text when the banner itself is narrow (a container query on it), with the icon at the title. The connect screen shows `UnreachableState` with the session check's texts (`texts="connect"`) in place of the form when that check got no answer. Server code under `server/` runs in Node; its tests run in the `server` Vitest project (no jsdom).

### The production server

Production: `server/main.ts` is a dependency-free Node server (run as `.ts` through Node's type stripping, so server code must stay erasable TypeScript with `.ts` import paths) that chains the routes `kinopeerServer()` builds (the `server/` middleware and `/healthz`, shared with Vite's dev and preview servers, which also run its `startJobs()`; first `securityHeaders` (`server/securityHeaders.ts`), so every answer has `nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: same-origin`, a `Permissions-Policy` and `Cross-Origin-Opener-Policy`, and no HSTS, since Kinopeer is also opened over plain HTTP; then `hostCheck` (The host check, below); `createApp` and `vite preview`, not the dev server, whose pages run Vite's inline scripts, also send `CONTENT_SECURITY_POLICY` (`contentSecurityPolicy`): only the app's own files, images also as `data:`, no inline script, so the theme applied before first paint is `public/theme.js` rather than inline in `index.html`, and a smoke journey fails on anything it blocks (`e2e/smoke/test.ts`); the qBittorrent bridge answers `no-store`, and the TMDB bridge passes on only JSON from the API and raster images, else `application/octet-stream`), and `server/static.ts` (serves `dist/`, `index.html` for app routes, hashed `/assets/*` cached for a year, everything else incl. `sw.js` revalidated, Brotli/gzip). `Dockerfile` builds it into a `node:24-alpine` image with no `node_modules`; config comes from environment variables only. Installs are supported on Umbrel, where the package lives in the `homelab-kinopeer/` folder of https://github.com/MrShakhov/umbrel-homelab-store, and with `docker-compose.yml` beside qBittorrent's and Prowlarr's images, which lets Kinopeer into qBittorrent without a login (`docs/DEVELOPMENT.md` → Docker), and as the image on its own next to a qBittorrent and a Prowlarr the user runs, whose addresses onboarding asks for (README → Install next to your own qBittorrent and Prowlarr), Unraid's Community Applications template among them (`unraid/kinopeer.xml`, DEVELOPMENT → Docker).

### The host check

`hostCheck` (`server/hostCheck.ts`, #356) answers a request only for the host names Kinopeer is meant to be reached at, against DNS rebinding: a page whose host name its owner points at Kinopeer's address is same-origin with it, so it can send the `X-Kinopeer` header the bridges ask for (above) and read every answer (and Kinopeer's own login's first-run setup and sign-in). What tells such a page apart is its `Host`, its own name. So by default the server answers only at names public DNS never answers for, which no one can register (`isPrivateHost`): an IP address, `localhost` and `*.localhost`, `*.local` (mDNS: `umbrel.local`), `*.onion`, `*.home.arpa`, `*.internal`, and a name of one label (a LAN name, a Docker service). `KINOPEER_ALLOWED_HOSTS` adds names (`kinopeer.example.com`) and domains (`.example.com`), and `*` answers at any name, which the Umbrel package sets, since Umbrel's app gateway, which keeps the `Host`, signs in first and its cookie doesn't go to a rebound name. Behind a reverse proxy the check sees what the proxy sends: a proxy that keeps the `Host` (nginx's `proxy_set_header Host $host`, Caddy's default) or sends the page's name in `X-Forwarded-Host` lets it refuse a rebound name, and each host in `X-Forwarded-Host` must be allowed too, which never lets through a request its `Host` doesn't. One that sends the upstream's address as `Host` and no `X-Forwarded-Host` (nginx's default, `$proxy_host`) hides the page's name: the check sees only the upstream's name, which it allows whenever the proxy works at all (an IP, a name of one label, `localhost`, a `.local` or `.internal` name, or one added to the variable), so behind such a proxy it protects nothing. A `server_name` alone refuses nothing there either, since nginx hands a `Host` that matches none to the port's default server, which with one `server` block is that block; only a catch-all `default_server` that turns unknown names away (`return 444`) does. DEVELOPMENT's row for the variable says to pass `Host` or `X-Forwarded-Host`. A refused request gets a 403 with a plain text naming the host and the variable to set; it's the second route, after the security headers, so it covers `/healthz` and the app's files as well. It runs in `vite` and `vite preview` with the other routes, behind Vite's own `server.allowedHosts`, whose default is stricter (no `.local`).

## Torrents

### The qBittorrent client and torrent requests

qBittorrent Web API client: `src/api/qbittorrent/` (incl. adding torrents, file lists and priorities). The add and move sheets get the categories, the default save path and the preferences that decide category folders through `getSaveLocations`, which reads qBittorrent's version from the session check's answer the page keeps (`subcategoriesUnderParent`: 4.6 puts a subcategory by its whole name under the default save path, 5.0 under its parent with subcategories on, 5.2 always), and `src/torrents/folders.ts` places a category's folder as qBittorrent's `categorySavePath` does.

Settings → qBittorrent folders (`src/screens/FoldersSheet.tsx`) loads the folders when it opens (`getFolders`: the categories and the preferences, the default save path among them, and what a change of either does to the torrents under automatic management in it, failing rather than showing part of them) and saves one through `prepareFolder` (`torrents/setLocation` for no torrents, which has qBittorrent create the folder and answers 409 when it can't; it checks no write access, nor does anything else qBittorrent offers), then `setDefaultSavePath` or `setCategoryFolder` (which sends a category's incomplete-downloads folder back, since qBittorrent before 5.3 resets it otherwise). A save outlives its form and the sheet through Settings' saves (A screen's own requests, below), kind `folder`, by the default save path or the category: one opened again, Settings left and opened again included, is busy with what's sent, and an outcome moves the sheet (back to the list, the failure in the form) only while that folder is shown, else it's a toast, a failure naming the folder or the category (the sheet gone with Settings included), and the list asks qBittorrent again when it's next shown. The folder field and its known folders are `FolderField`, shared with Move files, and what a refusal says is `folderFailure` (`src/screens/folderFailure.ts`), with `categoryFailure` for a category qBittorrent no longer has (409 before 5.2, 404 from it), which isn't a folder it can't create.

Moving files: `src/screens/useMoveTorrent.tsx` gives a screen the Move files sheet and runs the move itself, so its outcome shows as a toast even after the sheet was closed or the screen is gone.

Per-torrent speed limits: `src/screens/useSpeedLimits.tsx` gives a screen the Speed limits sheet in the same shape (a failed save after the sheet was closed is a toast on that screen); the field parsing lives in `src/torrents/speedLimits.ts`, with `ownLimits` and `describeLimits`, which Downloads' `SpeedLimitMark` (`src/screens/SpeedLimitMark.tsx`, the gauge on a row, a table row or a card) and the More menu's Speed limits item read.

Both are built on `useTorrentSheet` (`src/screens/useTorrentSheet.ts`), which keeps which torrent the sheet is open for through `useTorrentOverlay` (`src/screens/useTorrentOverlay.ts`, by hash and `added_on`: closed when that torrent goes away or another with the same hash replaces it, the rule for every overlay a screen opens for one torrent: the More menu, Recheck and the title search in Downloads and the torrent details; the delete confirmation keeps it for each of its torrents) and sends its requests (`send`) through the app's torrent requests (`createTorrentRequests` in `src/torrents/torrentRequests.ts`, its kinds in `REQUEST_KINDS` (`src/torrents/requestKinds.ts`), shared by `TorrentRequestsProvider` in `App`, a store of its own beside the poll's; outside a provider, as in tests, each hook keeps its own): one per kind and torrent at a time, `pending` on every screen until it settles, so a sheet opened again or a sheet of the same kind on another screen (the drawer over Downloads) shows it busy and starts from what's being sent; when it settles every sheet that shows the torrent then closes or keeps the failure (`failure`, what was sent and why, until a sheet opens or sends again), and `send` says whether one did, else the outcome goes to a toast. It's a request manager for every action on a torrent, decided on 2026-10-30, moved step by step, now all of them (the alternative speed limits switch stays out, SPEC's decision log says why). A new sheet for one torrent uses it too.

The force recheck confirmation is such a sheet: `useRecheck` (`src/screens/useRecheck.tsx`) gives a screen `RecheckDialog` and sends the recheck with `expect: withChecking` (`status.ts`).

An action sent from a button or menu item rather than a sheet uses `useTorrentAction` (`src/screens/useTorrentAction.ts`: `busy` and `send` for one kind, and a watcher for a place that shows the torrent and takes the outcome): reannouncing through `useReannounce` (the More menu, with its toasts) and pausing and resuming through `usePauseResume` (`src/screens/usePauseResume.ts`) from a row's button, the More menu (`TorrentActionsSheet`, which watches the torrent it shows: it closes or shows the failure, else a toast keyed `TOAST_KEYS.pauseResume`), the torrent details and the selection's bar (one request for several torrents, without those already in flight).

File priorities go through `useFilePriorities` (`src/screens/useFilePriorities.ts`, used by `TorrentFiles`), one request per file or per folder (its files in one request; `SendOptions.part`, keyed `requestKey(kind, hash, part)`, the files' indexes, read back per file through `inFlightParts`; nothing is sent while one of the files has a change in flight, so a folder is busy while a file under it is and the other way round); it shows what's in flight over the files poll (`useTorrentFiles`, which says when the answer shown was asked for, `requestedAt`, and polls only while the Files section is open, keeping the last answer while it's closed) and keeps what qBittorrent took until a files poll sent after the answer, through a watcher of its own rather than `expect`, since the torrents poll has no files.

The torrent page's Download section (`src/screens/DownloadSettings.tsx`, always open, above Details) switches sequential download and first and last pieces first through `useDownloadToggle` (`src/screens/useDownloadToggle.ts`, kinds `sequential` and `firstLastPieces`, on `useTorrentAction`, whose `pending` gives the value being sent and `holding` whether its expected state is still held): qBittorrent can only flip them, so it reads the torrent with `getTorrents` just before and flips nothing when it's that way already, with an `expect` held for `stateLag`, and the switch stays busy until that hold ends. It changes the category through `useChangeCategory` (`src/screens/useChangeCategory.tsx`, `CategorySheet.tsx`, on `useTorrentSheet`, kind `category`): `categoryChange` (`src/torrents/categoryChange.ts`) says what the change does with the files, moved to the category's folder under automatic management (`auto_tmm`), or left there with automatic management turned off when qBittorrent's preferences say so (`relocateOnCategoryChange` in `getSaveLocations`), an incomplete torrent with a download path (`downloadPath`, a category's `download_path`) moving to a folder it doesn't name, and `withCategory` is the state it expects.

The store is linked to the poll: `TorrentRequestsProvider` sits inside `MainDataProvider` and takes its store, and a request sent with `expect` (`withRunning` in `status.ts` for pause and resume; an `expect` that returns nothing takes the torrent away) polls again when it settles and keeps that state from qBittorrent's answer until a poll sent at that moment or later, or with `hold` that much later (`withExpected`, applied by `useMainData` under the provider, so every screen, count and filter shows it). Pause and resume hold for `stateLag` (`src/torrents/stateLag.ts`): qBittorrent reports their new state only at its next refresh, so the interval is read from its preferences once per page, alongside the first one. Move files and Speed limits still call `refresh` themselves.

`.torrent` files and magnet links are read in the browser (`src/torrents/torrentFile.ts`, `magnet.ts`) to get the info hash and files before adding; the hash goes through `src/torrents/digest.ts`, which uses Web Crypto when the page has it and its own SHA-1/SHA-256 over plain HTTP, where `crypto.subtle` doesn't exist.

Session state: `src/session/useQbitSession.ts` checks `app/version` first, so a working server login or qBittorrent's auth bypass goes straight in without a login form. With no address for qBittorrent the bridge answers 503 marked `BRIDGE_HEADER: no-address` (`NO_ADDRESS`), which the client throws as `NoAddressError` and the session reads as `no-address`: `ConnectScreen` then asks for the address with the login (`QbittorrentLoginForm`, which Settings shares, its login optional on every form for the auth bypass, #519, though half of one isn't sent), and `signIn` sends it (`url` in `PUT /api/settings/qbittorrent`). Where the address was saved from the app and Kinopeer's own login is on (the server's settings, read only then), the connect screen also offers to change it, from its form, its unreachable state or qBittorrent too old, since Settings isn't reachable until qBittorrent connects. Each check asks anew (`checkAppVersion` in `src/api/sharedAnswers.ts`) and keeps its answer for the page under `APP_VERSION_KEY`, which Settings' qBittorrent check takes while it's fresh (`APP_VERSION_FRESH_MS`, a minute), so Settings opened as the app opens or a tab away asks nothing again; its Test asks anew. A version older than `MIN_QBITTORRENT_VERSION` (`src/torrents/qbittorrentVersion.ts`, with what each version adds that Kinopeer needs) makes the session `unsupported`, and `App` shows the connect screen with `UnsupportedQbittorrent` in place of the form (and its Change for an address saved from the app, as when qBittorrent doesn't answer); differences between supported versions go through that module's pure functions, the version passed in, as with the 4.x pause and resume, which fall back by the answer instead.

### Torrent state and the poll

Torrent state: `src/torrents/useMainData.ts` polls `sync/maindata` every 2 s (the app's poll intervals are in `src/torrents/pollIntervals.ts`, which imports nothing, so the requests test reads them by its path: `docs/QUALITY.md` → The requests budget; only while the tab is visible, and right away when the device comes back online; `refresh` polls right away, or once the poll in flight is answered, since that one went out before the change) and merges the incremental deltas (`applyMainData` in `sync.ts`), keeping only the fields of `Torrent`, listed in `TORRENT_FIELDS` beside the merge (a field of `Torrent` missing from the list fails to compile), and a torrent's object while none of those changed: qBittorrent reports `time_active`, `seeding_time`, `reannounce` and `popularity` for most running torrents on each poll. Downloads' rows (`DownloadItem`, `DownloadRow`, `DownloadCard`) are memoized on that, so with hundreds of torrents a poll renders only those that changed; the callbacks the screen hands them keep their identity. A poll unanswered after `POLL_TIMEOUT_MS` (10 s) is aborted and counts as offline; one in flight when the device comes back online or the page becomes visible is dropped and sent again at once, and one in flight when the page is hidden is dropped without counting as offline.

Besides the data's snapshot the store keeps the poll's own state (`PollState`: in flight, offline, `updatedAt`), a separate object handed out as `poll` (`PollSource`), so a request going out renders only what subscribes to it: `PollRing` (`src/screens/PollRing.tsx`), which fills in CSS over the interval from each answer, pulses while one is awaited and is red offline (two half rings that turn behind half-ring windows and an opacity pulse: only `transform` and `opacity` animate, which the compositor runs, since an arc's `stroke-dashoffset` repainted the page every frame, #220; its test checks the keyframes), in the phone's Downloads title row and as `SidebarStatus`'s `indicator` on desktop (a render prop, which gives the rail's ring the connection's status for its tooltip), where it replaced the connection dot.

`App` wraps the screens in `MainDataProvider` (`src/torrents/MainDataProvider.tsx`), so every `useMainData()` under it shares one poll, which runs only while something uses it and keeps the last state between screens, and its rhythm: started again, it waits for what's left of its interval since its last answer (`dueAt`, never longer than the interval, should the clock be set back), so a screen that comes back on a phone asks nothing at once, and `PollRing` mounts filled as far as the time since that answer (#385); a poll that got no answer (it failed, or was dropped as the store stopped or the page was hidden) and a `refresh` while the store is stopped leave nothing to wait for; outside a provider (tests) the hook polls on its own. Never start a second poll for the same data, and no one-off `getMainData` either: qBittorrent keeps one `rid` per session and the server's session is shared, so a `rid=0` outside the poll is a full answer and makes the poll's next answer a full one too. A screen that shows what's in downloads only in passing (the title cards' badge, #460) reads the poll without starting it: `useLastTorrents` (`useMainData.ts`) takes the store's last data through `watch`, which doesn't count as a subscriber, with what the torrent requests expect, as `useMainData` shows it, and hands the screen only what its `select` makes of the torrents, inside the subscription, so a poll that changes nothing the screen shows (by its `same`) renders nothing, and only when the page has none and no poll is asking, asks `torrents/info` once for the page (`oneOffTorrents.ts`): it looks as the screen opens and again each time the poll settles, since a poll in flight as the last screen that polled leaves is dropped unanswered.

When qBittorrent stops answering, screens keep the last state under `OfflineBanner` (its age, actions disabled) or show `UnreachableState` (`src/screens/UnreachableState.tsx`) before the first answer, and both, the poll's ring, the sidebar, the connect screen, Settings' qBittorrent check and a failed add (`AddReleaseSheet`) say who didn't answer: `unreachable` in `src/api/qbittorrent/client.ts` tells Kinopeer's server (a network failure, a sign-in proxy, or a failure without the bridge's `x-kinopeer-bridge` header, which `server/qbittorrent.ts` puts on every answer) from qBittorrent, the poll keeps it as `unreachable` beside `offline` and the session check as `who`, and the texts pick it as an i18next context through `unreachableText` (`src/lib/unreachable.ts`: `noAnswer.qbittorrent_kinopeer` for both of Kinopeer's cases, `unreached` and `kinopeer`); `src/screens/ErrorBoundary.tsx` shows a crash screen with Reload instead of a blank page; `src/torrents/status.ts` maps qBittorrent states to the design's statuses. Sizes, speeds and ETAs go through `src/lib/format.ts`, which keeps its `Intl.NumberFormat`s per language and digits, since building one costs far more than formatting with it. qBittorrent's free space goes through `freeSpace` (`src/torrents/freeSpace.ts`), which treats 0 or less as unknown.

### Adding a release

Adding a release (`src/screens/AddReleaseSheet.tsx`, `FilePicker.tsx`): Kinopeer gets only the `.torrent` (preferred, so files can be picked) or magnet link from Prowlarr, then adds it to qBittorrent itself via `src/releases/addRelease.ts` with the `tmdb:<type>:<id>` tag, the `kinopeer:notify` tag when Notify when finished is on (Notifications, above), category, save path and options. Prowlarr's own download clients are not used. The free space for the warning comes from the shared poll through `useFreeSpace` (`src/torrents/useMainData.ts`), which renders only when that value changes, so the sheet and a long file list don't render on every poll; on a phone that poll runs only while the sheet is open, since nothing else on the releases screen uses it. Skipped files: the torrent is added stopped, those files get priority 0, then it starts. Once the sheet has the torrent's info hash, it asks qBittorrent whether it has it already (`getTorrents` with the torrent's ID, `torrentId` in `src/torrents/sameTorrent.ts`) and holds the form back until it answers, and a refused add (`TorrentRefusedError`: 409 from qBittorrent 5.2, `Fails.` before) asks the same, so the sheet can say whether the torrent is there and open it; not for certain from a magnet link with only a v2 hash (`MagnetLink.v2Only`), which doesn't name a hybrid torrent's ID. After adding, the app goes to `/` with `{ added: title }` in the location state for a toast. The releases list marks the releases qBittorrent has (`inDownloads` in `useReleases`): their info hashes' IDs (`torrentId`) against the torrents `useLastTorrents` has (`heldIds`, compared with `sameIds`, in `sameTorrent.ts`), so it starts no poll, asks `torrents/info` once only when the page has no torrents, and renders on a poll only when the releases it marks change; a marked card or row links to the torrent over the page (`IconLink`, `ButtonLink`) in place of Add.

### Titles in Downloads

Download rows show the TMDB title and poster: `useTitleMatches` (`src/torrents/useTitleMatches.ts`) takes the user's choice from the server, else a `tmdb:<movie|tv>:<id>` torrent tag (Kinopeer adds it when sending a release), else a guess the server keeps, else guesses from the release name (`parseName.ts`) by searching TMDB and saves the guess on the server; that order (`lookupFor`) and the pick among TMDB's results (`pickBest`) are pure logic in `titleLookup.ts`. TMDB is asked `CONCURRENCY` (3) at a time, one run per list and language (`startLookups`): a lookup joins its queue as its torrent comes and leaves it if the torrent goes before its turn, and none is stopped or asked again while the run lasts, which a title arriving would otherwise do with every answer (#239); a failed one (or one TMDB doesn't answer in `LOOKUP_TIMEOUT_MS`, 15 s) is asked again after `RETRY_DELAYS_MS` (30 s, 2 min, then every 10 min), not with the list's changes, and a 429 (`TmdbError.retryAfterMs`, from the `Retry-After` the server passes on) stops the run for that long, or `RATE_LIMIT_WAIT_MS`, then puts its lookup back in line. Titles show as they arrive at most every `SHOW_EVERY_MS` (250 ms), since each time the whole list renders again. Titles and guesses are also cached in localStorage, written at those moments and when the list goes away rather than with every answer: the titles' own data per language, which the server doesn't keep, and the guesses as the fallback without the server (a miss for a day, a title for 30 days), read only when the server has no match; a miss the server keeps (`lookupFor`'s `miss`) gives no title without asking TMDB. Bump `GUESS_VERSION` when guessing changes, so old guesses are redone. The title cards outside Downloads (Search's, `TitleRelated`'s) mark the titles in downloads through `useTitlesInDownloads`, which files `useLastTorrents`' torrents by title with only what's known without TMDB (`torrentsByTitle` in `titleDownloads.ts`: the user's choice, the tag, the server's guess, else the browser's cached guess through `cachedTitle`), so it starts no lookup, and gives each title its mark (`marksByTitle`, the title page header's rule, `downloadsMark`) as `useLastTorrents`' select, with `sameMarks` (the same titles, counts and whole percents, `wholePercent` in `src/logic/`, which `format.percent` uses too) as its `same`, so Search and the title page's related row render on a poll only when a mark changes; `InDownloadsMark` (`src/screens/`) shows it over the poster, a card without one gets none. The Downloads type filter (in `SortSheet.tsx`, not remembered) uses `titleType`: the matched title's type, else the lookup's (a known title, season markers, the category).

### Torrent-to-title matches

Torrent-to-title matches: `server/matches.ts` keeps them by info hash in `$KINOPEER_DATA_DIR/matches.json` (`{ type, id, source: 'user' | 'guess', version }`, or `{ source: 'miss', version }` for a guess that found no title, so no device asks TMDB again: `StoredTitle` and `StoredMiss` in `src/api/matches/types.ts`), not in qBittorrent tags, with no expiry by time (#461). `GET /api/matches`, `PATCH /api/matches` (a guess or a miss never replaces the user's choice, and nothing replaces a match of a newer version of guessing, nor a miss a guess of the same version, `replaces`), `PATCH` with `null` forgets a torrent (`forgetMatches` after deleting it), `DELETE /api/matches` forgets the guesses and misses (Settings → Clear cache). The server checks qBittorrent's torrents every hour (`startMatchesCleanup`, through `qbittorrentBridge().get` with the server's session) and forgets a match once its torrent has been missing for a week (`missingSince`). Client: `src/api/matches/`, shared state in `src/torrents/serverMatches.ts`, which `useServerMatches` (`useServerMatches.ts`) reads (loaded once, guesses saved in batches, the user's choice saved right away by `chooseMatch`). The user picks a title in `src/screens/ChangeTitleSheet.tsx` (TMDB search, given by `useChangeTitle` in `src/screens/useTitleChoice.tsx`, on the request manager: kind `title`, one save per torrent), saved through `chooseTitle` in `useTitleMatches.ts` as the user's choice, the title already shown too; nothing asks whether a guess is right (SPEC's decision log, 2026-11-13). It opens from `TorrentActionsSheet` (the row's and the torrent screen's More menu: Fix match, or Match title without a title); when no title was found, the torrent screen's More has a dot (`IconButton`'s `dot`, whose text is the button's accessible description; on a glass button it's the same light teal in both themes, elsewhere it follows the theme) and the menu's Match title is in the accent (`MenuItem`'s `highlight`, `.ks-row-btn.is-highlight` in the phone sheet), both reusable for anything else worth pointing at. Both data files go through `server/jsonFile.ts` (atomic writes, one at a time).

### A screen's own requests

A screen or a sheet loads what it shows through `useRequest` (`src/lib/useRequest.ts`): it runs its load for a key, aborts the run for the key before, so a slow answer for an old key never overwrites a newer one, passes the signal on, so an aborted request is cancelled, and runs it again on `retry`. By default each caller asks on its own. With `freshFor` (ms) the request is shared by its key across the page through `sharedRequests` (`src/logic/sharedRequests.ts`, pure logic, which code outside React calls directly): callers that ask while one request is on its way get its answer, a later caller gets the kept answer while it's that fresh, from its first render, and a shared request is cancelled only once no caller waits for it; `retry` sends a new one, whose answer replaces the kept one. An answer the app keeps for the key otherwise (`set`: a save that answers with the server's settings, `saved` in `src/api/settings/client.ts`) reaches every caller showing the key (`follow`), in place of its own request if that's still on its way, since that one may be from before the save, so Settings opened again while a save from an earlier visit was on its way shows what it saved (#545). Only answers are kept, never a failure. Sharing is a caller's choice rather than the default because a key there names the request itself, the same for every caller, while today's keys are each component's own and some loads do more than fetch. The key and the freshness a request is shared with sit beside its client (`APP_VERSION_KEY`, `SERVER_SETTINGS_KEY`, `titleDetailsKey` and `relatedTitlesKey` with `TITLE_FRESH_MS`). A title's details (`useTitleDetails` in `src/screens/`, which the title page and the phone's releases screen both read) and its related titles (`TitleRelated`) are shared for an hour, so a move between the title page and its releases, or back, asks TMDB nothing again. Kept answers stay in memory until the page reloads, a few kilobytes per title opened. Tests start from an empty cache (`src/test-setup.ts`).

A save sent from one of Settings' sheets outlives the sheet the same way a torrent request does (#500), without a torrent: `saves` (`src/logic/saves.ts`, pure logic, one for the page, as `sharedRequests` is, so a save outlives Settings and needs no provider) keeps one save per kind and target in flight (`saveKey`; a second for the target sends nothing), with what it sends, and when it settles offers the outcome to every watcher of its kind, each saying whether it takes it, and `send` says whether one did (`taken`), else the caller says it in a toast. A sheet reads it through `useSaves` (`src/lib/useSaves.ts`): `pending` for a target, from any sheet, so one opened again shows what's sent and sends nothing more, and `send`, and while it's mounted its latest render's `takes` is offered each outcome of its kind: it takes one only while it shows the target. The qBittorrent folders sheet, Telegram's form, the connection forms (`QbittorrentLoginForm`, `ProwlarrKeyForm`, wherever they're shown) and the push card, each with what it sends (the address and the username, never a password or a key), use it; a form that takes a save runs its own caller's next step (`onSaved`, `onForgotten`), so Settings opened again, or a title's releases, follows a save sent from another, and the form that sent it runs it only when none took it. Tests start with nothing in flight (`src/test-setup.ts`).

## In the browser

### The two builds

One source, two builds (`buildTarget` in `vite.config.ts`): `npm run build` into `dist/`, the app Kinopeer's server serves, and `npm run build:webui` (Vite's mode `webui`) into `dist-webui/public/`, the Alternative WebUI that qBittorrent serves itself, with no Kinopeer server (#360 and its milestone). qBittorrent's Alternative WebUI folder is `dist-webui/`: it serves the files under its `public/` folder, and once signed in those under `private/` first, which the build has none of. A request for `/` that finds no `public/index.html` there turns the Alternative WebUI off in qBittorrent's settings (in `qbittorrent-nox`), and any other path that isn't a file is a 500, which is why the routes go after the `#`. Code branches on `__WEBUI__` (`src/webui.d.ts`), a constant the build defines as it does `__APP_VERSION__`, so each bundle drops the other's branch and the server's build doesn't grow for the WebUI; a pure module doesn't read it (Pure logic, below), its caller passes in what it needs. The tests run with it false; a test of the WebUI's branch stubs the global (`vi.stubGlobal`) and imports the module again, as `src/lib/appRouter.test.tsx` does. So far the WebUI build differs only in its router (Routing, above). CI's `check` job builds both, and the size budget counts the server's.

### Preferences

Preferences live in `src/settings/settings.ts` (localStorage, `useSettings`, `useTmdbLanguage`; `initSettingsSync`, started in `main.tsx` like `initLanguage`, reads them again when another tab saves them; the release filters and sort are checked when read). TMDB language, list or poster grid, the sort in Downloads (`src/torrents/sort.ts`) and the release filters and sort are per browser (`useReleases` starts a search from the remembered filters through `startingFilters` in `filterReleases.ts`, which sets aside what the results don't meet, alone or together; `ReleasesBlock` names what's set aside with Forget). The download defaults (category per type, start paused, sequential, first and last pieces first, notify when finished) are also kept on the server: `useSettings` loads them once per page (`loadServerSettings`) and the server's win, a change is saved to both, a default the server doesn't have yet is sent from the browser that changed it, and without the server the browser's copy applies. Connection settings stay on the server: service addresses in its environment, else in its settings file when saved from the app, and the TMDB key and the qBittorrent login in its settings file. The theme (`src/theme/theme.ts`, `useTheme`) and the interface language (`src/i18n/language.ts`, `useLanguage`) are their own per-browser stores, each `'system'` by default and following the system's (the browser's languages, `languagechange`) while that's chosen; change the language through `setLanguagePreference`, not `i18n.changeLanguage`, so the choice is saved and the language's texts are loaded first. The texts aren't in the main bundle: `showLanguage` (`src/i18n/language.ts`) imports a language's file the first time the page shows it, then switches, and the last language asked for wins over one still loading; it resolves to false when the file can't be loaded, and `useLanguage`, which the places that switch use (Settings, `Preferences` on the sign-in and connect screens), then says so in a toast in the language still shown; `main.tsx` waits for the first one before rendering, so neither the keys nor the other language flash. The size budget counts one language file, the heaviest ([QUALITY.md](QUALITY.md) → The size budget), and the requests budget counts none, as with the rest of the build's files.

### PWA

PWA: `vite-plugin-pwa` builds the manifest (in `vite.config.ts`) and the service worker from `src/sw.ts` (injectManifest, own tsconfig `tsconfig.sw.json`, which also compiles its smoke test `src/sw.test.ts`). It precaches the app shell, serves `index.html` for app routes except a load with `PROXY_SIGN_IN_PARAM`, which has to reach the sign-in proxy (above, Prowlarr), caches `/tmdb-img/*` posters and never caches `/qbt`, `/prowlarr` or `/tmdb`; those rules live in `src/pwa/swRoutes.ts`, apart from workbox, with their own test. A new version activates right away. Open pages keep working because the app loads as one bundle, with one exception: each language's texts are a chunk of their own (`language-<code>-<hash>.js`, named by `chunkFileName` in `vite.config.ts`), loaded when the page shows that language (#492). They're precached with the shell, so either language opens offline, but the new version's precache drops the old ones, so a page an update left behind can't load the other language: `showLanguage` then calls the update check (`startUpdateChecks` registers it with `onLanguageUnavailable`), which reloads it into the new version when the server has one, and otherwise the page keeps the language it shows and the switch says so in a toast (`useLanguage`). No other lazy chunk: a new one would have the same problem. An open page reloads into it through `startUpdateChecks` (`src/pwa/updates.ts`, started in `main.tsx`): at startup and on every return to the foreground it compares `__APP_VERSION__` with `/version.json` (written by `versionFilePlugin` in `vite.config.ts`, not precached), and when they differ and no `dialog` is open and no field has focus it has the service worker take over first (over HTTPS) and reloads, once per version per session; `UpdatedToast` in `App` then names the new version. The service worker is off in `npm run dev`; try it with `npm run build && npm run preview`. Icons: SVG sources in `scripts/icons/`, PNGs rendered by `scripts/render-icons.mjs`. The touch icon iOS takes for the Home Screen goes into the built `index.html` as a `data:` URL (`inlineTouchIconPlugin` in `vite.config.ts`, from the file index.html's `<link>` names in `public/`): iOS fetches a linked one in a process of its own, which got nothing over Umbrel's HTTPS (#304). Service workers need HTTPS (or localhost); umbrelOS 2.0 serves apps over HTTPS with its own certificate, and Kinopeer sets up nothing for it. Over plain HTTP there is no `crypto.subtle` either, so hashing goes through `src/torrents/digest.ts`. The service worker also shows the server's push notifications (`push`), opens a tapped one's page in an open window of Kinopeer's or a new one (`notificationclick`), and saves a subscription the browser renewed in place of the old (`pushsubscriptionchange`): that logic is `src/pwa/swPush.ts`, apart from the worker's globals, with its own test.

## Pure logic

Parsing, filtering and computations, the rules Kinopeer applies to its data, live in modules that depend on neither React nor the platform, so they are tested without an environment and can move between the browser, the server and other clients. They are every module in `src/releases/`, `src/search/`, `src/torrents/` and `src/logic/` (logic that more than one area shares, such as the sort order, `withTimeout` and the shared requests) but the tests, the hooks (`use` and a capital letter: `useMainData.ts`) and the providers (`MainDataProvider.tsx`, `TorrentRequestsProvider.tsx`), which keep React's state beside the logic. Code that needs React or the browser goes into such a hook with the state it keeps, as `useTitleMatches.ts` holds the title lookups and their localStorage cache over the rules in `titleLookup.ts`, and `useServerMatches.ts` reads the store in `serverMatches.ts`; any other component goes into `src/components/` or `src/screens/`, since a `.tsx` in those folders is checked as the rest. oxlint holds the boundary in the override of `.oxlintrc.json` for those folders, whose cases are in `src/logic/pureModules.test.ts`, so a new file there is checked from the start:

- `no-restricted-imports` refuses React, React DOM, React Router and react-i18next, even for a type, and every Node built-in: each name Node's `builtinModules` lists, its subpaths and its `node:` form. It also refuses a hook, a screen or a component (a module named `use` and a capital letter, matched with its case, anything under `screens/` or `components/`), which brings React in, unless only its types are imported.
- `no-undef` refuses every global but the language's own and the ones the override's `globals` names, which every platform has: `fetch` with `Headers`, `Request` and `Response`, `AbortController`, `URL`, `TextEncoder`, Web Crypto's `crypto`, the timers, `queueMicrotask`, `structuredClone` and `console`. It reads `typeof` too, so `typeof window !== 'undefined'` is refused as well. So `window`, `document`, `localStorage`, `navigator`, `process`, `Buffer` and the rest of the browser and Node are refused, and so is a constant the build defines, such as `__APP_VERSION__`: the caller passes in what it needs. `no-restricted-globals` refuses `globalThis`, through which any of them could be read.
- `react/react-in-jsx-scope` refuses JSX, which React's automatic runtime would otherwise compile without an import.
- i18next itself and the app's API clients stay allowed.

What the rule doesn't see is left to review. It reads a module's own imports only, so one that imports a module outside these folders that uses React or the browser passes: `src/lib/format.ts`, which some of them import a type from, uses React. A pure helper that sits beside the one component or service it serves (`sheetDrag.ts` by `Sheet`, `isTabOn.ts` by `TabBar`, `swRoutes.ts` by the service worker) is outside those folders and isn't checked, and neither are the pure modules of `src/lib/` that serve the interface (`cx.ts`, `breakpoints.ts`, `links.ts`). A hook or a provider may use React by design, so neither is checked.
