# Architecture

How Kinopeer is built, area by area: where each part lives, what it does and the rules a change to it follows. What the product does is in [SPEC.md](SPEC.md), running and releasing it in [DEVELOPMENT.md](DEVELOPMENT.md), the tests in [TESTING.md](TESTING.md), and the conventions every PR follows in [CLAUDE.md](../CLAUDE.md), which loads this file into every Claude Code session.

## The server

### The qBittorrent bridge

The browser talks to qBittorrent and Prowlarr only through same-origin routes. `/qbt/api/*` → qBittorrent Web API, served by `server/qbittorrent.ts` (Vite middleware in dev using `QBITTORRENT_URL` from `.env.local`, and the production server). The server always logs in itself (login saved from the app's connect screen via `PUT /api/settings/qbittorrent`, else `QBITTORRENT_USERNAME`/`QBITTORRENT_PASSWORD`), keeps the session and re-logs in on a 403; after one rejected login it stops trying (IP-ban protection) and requests go without a session, so qBittorrent's auth bypass still works and otherwise the app asks for a login. Browser cookies never reach qBittorrent. The bridge forwards only the calls `src/api/qbittorrent/` makes, each with its method (`ENDPOINTS` in `server/qbittorrent.ts`, matched on the path as written, so no `..` or encoded path reaches `/auth/*` or the preferences), and only requests with the `X-Kinopeer` header the client sends on every call: it attaches the server's session and rewrites `Origin` and `Referer`, so without that header a form on any other site could act through it, and a page can't add a header to a cross-origin request without a CORS preflight, which the bridge never allows (Vite's own CORS is off in `vite.config.ts`, since in dev and preview it would answer that preflight for any localhost origin before the bridge runs; `vite.config.test.ts` starts both servers from the config to check). A new qBittorrent call in the client goes into `ENDPOINTS` too, and into `EVERY_CALL` in `server/integration/qbittorrent.test.ts`, which doesn't compile without it and checks that each passes the bridge. Never call those services cross-origin. Each bridge, and the checks behind `PUT /api/settings/tmdb`, `/prowlarr` and `/qbittorrent` (the TMDB key's with TMDB's time limit too), gives its request upstream up once the browser's request has gone before its answer (`abandoned` in `server/abandoned.ts`, taken before the first `await`), so a request the app stopped waiting for doesn't hold a connection to the service until it answers; the shared session's login isn't given up with it, since other requests wait for it too (a login saved from the connect screen is the browser's own attempt, and is). A write to qBittorrent given up that way has normally reached it whole already (its body is small and goes out at once), and the browser that left learns the outcome from the next poll either way.

### TMDB and its proxy

TMDB goes through `/tmdb/*` → `https://api.themoviedb.org/3/*` (`server/tmdb.ts` adds the key, so it never reaches the browser) and images through `/tmdb-img/*` → `https://image.tmdb.org/t/p/*`; a path that `fetch` wouldn't keep as written (dots, encoded dots, a backslash) or with an encoded slash or backslash is refused, since it would lead out of `/3/` or `/t/p/` (#305). Client: `src/api/tmdb/`. Kinopeer's own key sits behind a Cloudflare Worker, `tmdb-proxy/worker.ts` (`docs/DEVELOPMENT.md` → The TMDB proxy): it answers only the paths the client calls, has Workers Cache keep TMDB's answers (the Cache API does nothing on `workers.dev`) and limits calls per IP, an IPv6 caller by its /64. Two workers, `kinopeer-tmdb-edge` deployed by `edge.yml` and `kinopeer-tmdb` by `release.yml`, both through `tmdb-proxy.yml`, which has no trigger of its own; each answers on a Workers Custom Domain, the release worker on `tmdb.kinopeer.com` and the edge worker on `tmdb-edge.kinopeer.com` (`wrangler.jsonc`'s `routes`, not `workers.dev`), so the deploy token needs Workers Routes on that zone. A new TMDB path in the client needs adding to its `ROUTES` too (and, outside `/3/`, to the WAF rule on `kinopeer.com` that DEVELOPMENT names), and a path is never removed or changed while a released version calls it: a breaking change goes into a new worker. The server sends calls without a key there (`proxyBase` in `server/tmdb.ts`, the address from `tmdbProxy` in `server/main.ts`: `TMDB_PROXY_URL`, else the edge worker baked into edge images and defaulted to by `vite.config.ts`, else the release worker), and `GET /api/settings` says `source: 'shared'` then, so onboarding skips the key step and Settings names Kinopeer's key. It sends no `Authorization` there, which Workers Cache would bypass. A call or an image TMDB (or the proxy) hasn't started answering in `TMDB_TIMEOUT_MS` (15 s, as long as the client's title lookups wait) is given up with a 504, while a body that has started may stream for longer (an image to a slow phone); qBittorrent's and Prowlarr's requests have no such limit, since a Prowlarr search across indexers can rightly take long, apart from `/prowlarr/failing`'s own.

### Server-side settings

Server-side settings: `server/settings.ts` keeps what the user enters in the app (the TMDB key, the Prowlarr key, the qBittorrent login and the download defaults) in `$KINOPEER_DATA_DIR/settings.json` (default `./data`, git-ignored; `/data` volume in Docker). `GET /api/settings` says only whether each secret is set and where it comes from; `PUT /api/settings/tmdb` checks the key with TMDB, then saves it (`DELETE` forgets it, only when `TMDB_API_KEY` or the proxy would serve TMDB without it, `fallback` in `GET`), and `PUT /api/settings/prowlarr` checks its key with Prowlarr's `system/status` (`DELETE` forgets it, only when the server has a key of its own, `serverKey` in `GET`); `PATCH /api/settings/downloads` merges in the download defaults sent (`downloads` in `GET`, null until one is saved). A saved key wins over `TMDB_API_KEY`. Client: `src/api/settings/`. Onboarding asks for the key after qBittorrent connects when the server has none and the proxy is off (`src/session/useTmdbSetup.ts`, `src/screens/TmdbKeyScreen.tsx`); Settings → Connections changes it, and its sheet (`TmdbKeyForm`, `forget`) goes back to the fallback.

### Prowlarr

Releases come from Prowlarr through `/prowlarr/*`, served by `server/prowlarr.ts` (Vite middleware in dev, and the production server), not a plain proxy: it adds `PROWLARR_API_KEY` and strips it from results, because Prowlarr's download links carry the key. The key (`prowlarrKey` in `server/settings.ts`) is the one saved from Settings → Connections (`ProwlarrKeyForm`), else `PROWLARR_API_KEY`, else read on every request from Prowlarr's `config.xml` at `PROWLARR_CONFIG_XML` (the Umbrel package mounts it). `/prowlarr/search` returns `Release[]`; `/prowlarr/download?token=` returns the `.torrent` or `{ magnet }`; `/prowlarr/status` returns `{ version, indexers }` for the Settings connection check, whose answer About also shows (`SettingsScreen` runs the checks and both read them). `/prowlarr/failing?within=<ms>` names the enabled indexers that failed in that many milliseconds or are on hold (Prowlarr's search doesn't say), which `useReleases` asks once a search answers, without holding its results, for the note above them. Client: `src/api/prowlarr/`. Browser clients call these routes, and every other route of Kinopeer's, through `fetchKinopeer` (`src/api/fetchKinopeer.ts`): with `credentials: 'same-origin'`, because a proxy in front of Kinopeer (Umbrel's app_proxy) authenticates with cookies, and with `redirect: 'manual'`, because Kinopeer's routes never redirect, so a redirect is that proxy sending the request to its sign-in on another origin once its cookie lapses (#303). Then `startProxySignIn` (`src/pwa/proxySignIn.ts`, started in `main.tsx`, which hands it to the clients through `onProxySignIn`, so they also run without a DOM) loads the screen the app is on again with `PROXY_SIGN_IN_PARAM`, at most once per `SIGN_IN_RETRY_MS`, and takes the parameter out of the address the proxy sends it back to; back from a sign-in it doesn't sign in again until a request is answered without a redirect (`answered`), so a cookie that doesn't stick can't loop. `loadPastTheShell` there is the same load without that limit, for Open again, which `UnreachableState`, `OfflineBanner` and the connect screen offer beside Retry (the second action of `Banner` and `EmptyState`) when `useMayOpenAgain` (`src/lib/unreachable.ts`) says nothing answered for Kinopeer's server (`unreached`, as against `kinopeer`, something answering for it), the device is online and a service worker controls the page: the browser then shows a sign-in or a certificate it no longer trusts (#311). Two actions in a `Banner` go under its text when the banner itself is narrow (a container query on it), with the icon at the title. The connect screen shows `UnreachableState` with the session check's texts (`texts="connect"`) in place of the form when that check got no answer. Server code under `server/` runs in Node; its tests run in the `server` Vitest project (no jsdom).

### The production server

Production: `server/main.ts` is a dependency-free Node server (run as `.ts` through Node's type stripping, so server code must stay erasable TypeScript with `.ts` import paths) that chains the routes `kinopeerServer()` builds (the `server/` middleware and `/healthz`, shared with Vite's dev and preview servers, which also run its `startJobs()`; first `securityHeaders` (`server/securityHeaders.ts`), so every answer has `nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: same-origin`, a `Permissions-Policy` and `Cross-Origin-Opener-Policy`, and no HSTS, since Kinopeer is also opened over plain HTTP; `createApp` and `vite preview`, not the dev server, whose pages run Vite's inline scripts, also send `CONTENT_SECURITY_POLICY` (`contentSecurityPolicy`): only the app's own files, images also as `data:`, no inline script, so the theme applied before first paint is `public/theme.js` rather than inline in `index.html`, and a smoke journey fails on anything it blocks (`e2e/smoke/test.ts`); the qBittorrent bridge answers `no-store`, and the TMDB bridge passes on only JSON from the API and raster images, else `application/octet-stream`), and `server/static.ts` (serves `dist/`, `index.html` for app routes, hashed `/assets/*` cached for a year, everything else incl. `sw.js` revalidated, Brotli/gzip). `Dockerfile` builds it into a `node:24-alpine` image with no `node_modules`; config comes from environment variables only. Installs are supported on Umbrel only; the package lives in the `homelab-kinopeer/` folder of https://github.com/MrShakhov/umbrel-homelab-store.

### Versions, release images and edge builds

Releases: semver in `package.json` (Vite injects it as `__APP_VERSION__`, shown in Settings → About), notes in `CHANGELOG.md`. A `v*` tag runs `.github/workflows/release.yml`: multi-arch image to `ghcr.io/kinopeer/kinopeer` and a GitHub Release. Every push to `main` that changes what goes into the image runs `.github/workflows/edge.yml`: an arm64 `edge` image with the commit in its version (`KINOPEER_COMMIT`, `0.6.0+abc1234`), which it pins in the edge store's Kinopeer Edge app, so the owner's Umbrel offers it as an update (`docs/DEVELOPMENT.md` → Edge builds). Add user-facing changes to `CHANGELOG.md` under the next version as they land.

## Torrents

### The qBittorrent client and torrent requests

qBittorrent Web API client: `src/api/qbittorrent/` (incl. adding torrents, file lists and priorities). The add and move sheets get the categories, the default save path and the preferences that decide category folders through `getSaveLocations`, and `src/torrents/folders.ts` places a category's folder as qBittorrent's `categorySavePath` does.

Moving files: `src/screens/useMoveTorrent.tsx` gives a screen the Move files sheet and runs the move itself, so its outcome shows as a toast even after the sheet was closed or the screen is gone.

Per-torrent speed limits: `src/screens/useSpeedLimits.tsx` gives a screen the Speed limits sheet in the same shape (a failed save after the sheet was closed is a toast on that screen); the field parsing lives in `src/torrents/speedLimits.ts`, with `ownLimits` and `describeLimits`, which Downloads' `SpeedLimitMark` (`src/screens/SpeedLimitMark.tsx`, the gauge on a row, a table row or a card) and the More menu's Speed limits item read.

Both are built on `useTorrentSheet` (`src/screens/useTorrentSheet.ts`), which keeps which torrent the sheet is open for through `useTorrentOverlay` (`src/screens/useTorrentOverlay.ts`, by hash and `added_on`: closed when that torrent goes away or another with the same hash replaces it, the rule for every overlay a screen opens for one torrent: the More menu, Recheck and Change title in Downloads and the torrent details; the delete confirmation keeps it for each of its torrents) and sends its requests (`send`) through the app's torrent requests (`createTorrentRequests` in `src/torrents/torrentRequests.ts`, its kinds in `REQUEST_KINDS` (`src/torrents/requestKinds.ts`), shared by `TorrentRequestsProvider` in `App`, a store of its own beside the poll's; outside a provider, as in tests, each hook keeps its own): one per kind and torrent at a time, `pending` on every screen until it settles, so a sheet opened again or a sheet of the same kind on another screen (the drawer over Downloads) shows it busy and starts from what's being sent; when it settles every sheet that shows the torrent then closes or keeps the failure (`failure`, what was sent and why, until a sheet opens or sends again), and `send` says whether one did, else the outcome goes to a toast. It's a request manager for every action on a torrent, decided on 2026-10-30, moved step by step, now all of them (the alternative speed limits switch stays out, SPEC's decision log says why). A new sheet for one torrent uses it too.

The force recheck confirmation is such a sheet: `useRecheck` (`src/screens/useRecheck.tsx`) gives a screen `RecheckDialog` and sends the recheck with `expect: withChecking` (`status.ts`).

An action sent from a button or menu item rather than a sheet uses `useTorrentAction` (`src/screens/useTorrentAction.ts`: `busy` and `send` for one kind, and a watcher for a place that shows the torrent and takes the outcome): reannouncing through `useReannounce` (the More menu, with its toasts) and pausing and resuming through `usePauseResume` (`src/screens/usePauseResume.ts`) from a row's button, the More menu (`TorrentActionsSheet`, which watches the torrent it shows: it closes or shows the failure, else a toast keyed `TOAST_KEYS.pauseResume`), the torrent details and the selection's bar (one request for several torrents, without those already in flight).

File priorities go through `useFilePriorities` (`src/screens/useFilePriorities.ts`, used by `TorrentFiles`), one request per file or per folder (its files in one request; `SendOptions.part`, keyed `requestKey(kind, hash, part)`, the files' indexes, read back per file through `inFlightParts`; nothing is sent while one of the files has a change in flight, so a folder is busy while a file under it is and the other way round); it shows what's in flight over the files poll (`useTorrentFiles`, which says when the answer shown was asked for, `requestedAt`, and polls only while the Files section is open, keeping the last answer while it's closed) and keeps what qBittorrent took until a files poll sent after the answer, through a watcher of its own rather than `expect`, since the torrents poll has no files.

Deleting goes through `useDeleteTorrents` (`src/screens/useDeleteTorrents.tsx`), which gives a screen `DeleteTorrentDialog` for a row's torrent, the selection or the torrent details, watches the torrents it shows, sends with an `expect` that returns nothing (the torrents are gone until a poll), forgets their matches, says it in a toast and tells the screen (`onDeleted`) only while it's still there.

The torrent page's Download section (`src/screens/DownloadSettings.tsx`, always open, above Details) switches sequential download and first and last pieces first through `useDownloadToggle` (`src/screens/useDownloadToggle.ts`, kinds `sequential` and `firstLastPieces`, on `useTorrentAction`, whose `pending` gives the value being sent and `holding` whether its expected state is still held): qBittorrent can only flip them, so it reads the torrent with `getTorrents` just before and flips nothing when it's that way already, with an `expect` held for `stateLag`, and the switch stays busy until that hold ends. It changes the category through `useChangeCategory` (`src/screens/useChangeCategory.tsx`, `CategorySheet.tsx`, on `useTorrentSheet`, kind `category`): `categoryChange` (`src/torrents/categoryChange.ts`) says what the change does with the files, moved to the category's folder under automatic management (`auto_tmm`), or left there with automatic management turned off when qBittorrent's preferences say so (`relocateOnCategoryChange` in `getSaveLocations`), an incomplete torrent with a download path (`downloadPath`, a category's `download_path`) moving to a folder it doesn't name, and `withCategory` is the state it expects.

The store is linked to the poll: `TorrentRequestsProvider` sits inside `MainDataProvider` and takes its store, and a request sent with `expect` (`withRunning` in `status.ts` for pause and resume; an `expect` that returns nothing takes the torrent away) polls again when it settles and keeps that state from qBittorrent's answer until a poll sent at that moment or later, or with `hold` that much later (`withExpected`, applied by `useMainData` under the provider, so every screen, count and filter shows it). Pause and resume hold for `stateLag` (`src/torrents/stateLag.ts`): qBittorrent reports their new state only at its next refresh, so the interval is read from its preferences once per page, alongside the first one. Move files and Speed limits still call `refresh` themselves.

`.torrent` files and magnet links are read in the browser (`src/torrents/torrentFile.ts`, `magnet.ts`) to get the info hash and files before adding; the hash goes through `src/lib/digest.ts`, which uses Web Crypto when the page has it and its own SHA-1/SHA-256 over plain HTTP, where `crypto.subtle` doesn't exist.

Session state: `src/session/useQbitSession.ts` checks `app/version` first, so a working server login or qBittorrent's auth bypass goes straight in without a login form.

### Torrent state and the poll

Torrent state: `src/torrents/useMainData.ts` polls `sync/maindata` every 2 s (the app's poll intervals are in `src/torrents/pollIntervals.ts`, which imports nothing, so the requests test reads them by its path: `docs/QUALITY.md` → The requests budget; only while the tab is visible, and right away when the device comes back online; `refresh` polls right away, or once the poll in flight is answered, since that one went out before the change) and merges the incremental deltas (`applyMainData` in `sync.ts`), keeping only the fields of `Torrent`, listed in `TORRENT_FIELDS` beside the merge (a field of `Torrent` missing from the list fails to compile), and a torrent's object while none of those changed: qBittorrent reports `time_active`, `seeding_time`, `reannounce` and `popularity` for most running torrents on each poll. Downloads' rows (`DownloadItem`, `DownloadRow`, `DownloadCard`) are memoized on that, so with hundreds of torrents a poll renders only those that changed; the callbacks the screen hands them keep their identity. A poll unanswered after `POLL_TIMEOUT_MS` (10 s) is aborted and counts as offline; one in flight when the device comes back online or the page becomes visible is dropped and sent again at once, and one in flight when the page is hidden is dropped without counting as offline.

Besides the data's snapshot the store keeps the poll's own state (`PollState`: in flight, offline, `updatedAt`), a separate object handed out as `poll` (`PollSource`), so a request going out renders only what subscribes to it: `PollRing` (`src/screens/PollRing.tsx`), which fills in CSS over the interval from each answer, pulses while one is awaited and is red offline (two half rings that turn behind half-ring windows and an opacity pulse: only `transform` and `opacity` animate, which the compositor runs, since an arc's `stroke-dashoffset` repainted the page every frame, #220; its test checks the keyframes), in the phone's Downloads title row and as `SidebarStatus`'s `indicator` on desktop (a render prop, which gives the rail's ring the connection's status for its tooltip), where it replaced the connection dot.

`App` wraps the screens in `MainDataProvider` (`src/torrents/MainDataProvider.tsx`), so every `useMainData()` under it shares one poll, which runs only while something uses it and keeps the last state between screens; outside a provider (tests) the hook polls on its own. Never start a second poll for the same data, and no one-off `getMainData` either: qBittorrent keeps one `rid` per session and the server's session is shared, so a `rid=0` outside the poll is a full answer and makes the poll's next answer a full one too.

When qBittorrent stops answering, screens keep the last state under `OfflineBanner` (its age, actions disabled) or show `UnreachableState` (`src/screens/UnreachableState.tsx`) before the first answer, and both, the poll's ring, the sidebar, the connect screen, Settings' qBittorrent check and a failed add (`AddReleaseSheet`) say who didn't answer: `unreachable` in `src/api/qbittorrent/client.ts` tells Kinopeer's server (a network failure, a sign-in proxy, or a failure without the bridge's `x-kinopeer-bridge` header, which `server/qbittorrent.ts` puts on every answer) from qBittorrent, the poll keeps it as `unreachable` beside `offline` and the session check as `who`, and the texts pick it as an i18next context through `unreachableText` (`src/lib/unreachable.ts`: `noAnswer.qbittorrent_kinopeer` for both of Kinopeer's cases, `unreached` and `kinopeer`); `src/screens/ErrorBoundary.tsx` shows a crash screen with Reload instead of a blank page; `src/torrents/status.ts` maps qBittorrent states to the design's statuses. Sizes, speeds and ETAs go through `src/lib/format.ts`, which keeps its `Intl.NumberFormat`s per language and digits, since building one costs far more than formatting with it. qBittorrent's free space goes through `freeSpace` (`src/torrents/freeSpace.ts`), which treats 0 or less as unknown.

### Adding a release

Adding a release (`src/screens/AddReleaseSheet.tsx`, `FilePicker.tsx`): Kinopeer gets only the `.torrent` (preferred, so files can be picked) or magnet link from Prowlarr, then adds it to qBittorrent itself via `src/releases/addRelease.ts` with the `tmdb:<type>:<id>` tag, category, save path and options. Prowlarr's own download clients are not used. The free space for the warning comes from the shared poll through `useFreeSpace` (`src/torrents/useMainData.ts`), which renders only when that value changes, so the sheet and a long file list don't render on every poll; on a phone that poll runs only while the sheet is open, since nothing else on the releases screen uses it. Skipped files: the torrent is added stopped, those files get priority 0, then it starts. After adding, the app goes to `/` with `{ added: title }` in the location state for a toast.

### Titles in Downloads

Download rows show the TMDB title and poster: `src/torrents/titleMatches.ts` takes the user's choice from the server, else a `tmdb:<movie|tv>:<id>` torrent tag (Kinopeer adds it when sending a release), else a guess the server keeps, else guesses from the release name (`parseName.ts`) by searching TMDB and saves the guess on the server. TMDB is asked `CONCURRENCY` (3) at a time, one run per list and language (`startLookups`): a lookup joins its queue as its torrent comes and leaves it if the torrent goes before its turn, and none is stopped or asked again while the run lasts, which a title arriving would otherwise do with every answer (#239); a failed one (or one TMDB doesn't answer in `LOOKUP_TIMEOUT_MS`, 15 s) is asked again after `RETRY_DELAYS_MS` (30 s, 2 min, then every 10 min), not with the list's changes, and a 429 (`TmdbError.retryAfterMs`, from the `Retry-After` the server passes on) stops the run for that long, or `RATE_LIMIT_WAIT_MS`, then puts its lookup back in line. Titles show as they arrive at most every `SHOW_EVERY_MS` (250 ms), since each time the whole list renders again. Titles and guesses are also cached in localStorage, written at those moments and when the list goes away rather than with every answer. Bump `GUESS_VERSION` when guessing changes, so old guesses are redone. The Downloads type filter (in `SortSheet.tsx`, not remembered) uses `titleType`: the matched title's type, else the lookup's (a known title, season markers, the category).

### Torrent-to-title matches

Torrent-to-title matches: `server/matches.ts` keeps them by info hash in `$KINOPEER_DATA_DIR/matches.json` (`{ type, id, source: 'user' | 'guess', version }`), not in qBittorrent tags. `GET /api/matches`, `PATCH /api/matches` (a guess never replaces the user's choice), `PATCH` with `null` forgets a torrent (`forgetMatches` after deleting it), `DELETE /api/matches` forgets the guesses (Settings → Clear cache). The server checks qBittorrent's torrents every hour (`startMatchesCleanup`, through `qbittorrentBridge().get` with the server's session) and forgets a match once its torrent has been missing for a week (`missingSince`). Client: `src/api/matches/`, shared state in `src/torrents/serverMatches.ts` (loaded once, guesses saved in batches, the user's choice saved right away by `chooseMatch`). The user changes a title in `src/screens/ChangeTitleSheet.tsx` (TMDB search, given by `useChangeTitle`) or confirms a guess in `MatchPrompt.tsx` or the More menu (`useConfirmTitle`), both in `src/screens/useTitleChoice.tsx` on the request manager (kind `title`, one save per torrent) and saving through `chooseTitle` in `titleMatches.ts`; `isGuessed` tells whether to ask. They open from `TorrentActionsSheet` (the row's and the torrent screen's More menu) and the torrent screen. Both data files go through `server/jsonFile.ts` (atomic writes, one at a time).

## Screens

### Routing

Routing: React Router (`react-router`). `App.tsx` routes `/` (downloads), `/search`, `/torrent/:hash` (torrent details: `TorrentScreen` on a phone; on desktop a drawer, `TorrentDrawer`, a native modal `<dialog>`, both showing `TorrentDetails`. A link from another page passes it as background in the navigation state (`overPage` in `src/lib/background.ts`; the title page's `TitleDownloads` does), and `App` renders the routes for that background location with `TorrentDrawerOverPage` on top, which closes by going back and tells the sidebar which page is behind. Without a background, as from Downloads or on a direct load, `DownloadsWithDrawer` renders Downloads with the drawer), `/title/:type/:id` (type is `movie` or `tv`, id is the TMDB id; its "In downloads" block, `TitleDownloads.tsx`, lists the title's torrents through `useTitleTorrents` in `titleMatches.ts`; at the page's end `TitleRelated.tsx` shows TMDB's recommendations, else its similar titles, in a `PosterRow`, the Search screen's browse row), `/title/:type/:id/releases` (Prowlarr results with quality filters; `src/releases/parseRelease.ts` reads resolution, source, HDR, voice-over, seasons and episodes from release names; searches don't filter by category, because some indexers file every release under "Other"; both title paths render `TitleRoute`: on phones the releases path is `ReleasesScreen`, on desktop it is the title page with `TitleReleases` under the hero, which "Find releases" opens by replacing the title's path, so nothing is searched until it's pressed; the desktop hero's overview is `TitleOverview.tsx`, cut to five lines with Show more while it's clipped (`scrollHeight > clientHeight`, measured again when fonts load or the width changes); the search, filters and sort live once in `src/screens/useReleases.ts` with the pure filtering in `src/releases/filterReleases.ts`, the shared states in `ReleasesBlock.tsx`) and `/settings` behind the tab bar. The screens' `ErrorBoundary` is keyed per screen (`screenKeyOf` in `App.tsx`), so a crash clears on the next one; on desktop a torrent's drawer shares Downloads' key and a title's releases path its title's, so neither remounts the page under it. `server/static.ts` falls back to `index.html` for these paths.

Search's rows before a search are TMDB Discover queries by digital or disc release date and recently aired episodes (`src/search/browseRows.ts`), so they show what's likely on torrents already; search state (`q`, `type`, `year`) lives in the URL; with a year, `searchTitles` searches `/search/movie` and `/search/tv` apart (`/search/multi` has no year parameter) and interleaves them, and a type searches only its own; the results come a page at a time through `useSearchResults` (`src/screens/useSearchResults.ts`, Show more), which keeps each type tab's pages while the query stays and, for Back, the pages loaded in memory by history entry (`location.key`) and search, one place per search, the last `KEPT_SEARCHES` of them (`src/search/searchResults.ts`, with the merging that drops a title seen on an earlier page); the scroll position comes back on Back through `useScrollRestoration` (`src/lib/useScrollRestoration.ts`, position per history entry in sessionStorage, restored once the screen says its content is loaded, since the browser's own restore runs while the page is still short; it tells Back from a new entry by whether a position was saved for it, since under `App`'s `<Routes location>` `useNavigationType()` always reads POP; it also saves the position as the page is hidden or goes away, so a reload comes back to it, and a document loaded afresh forgets what an earlier one saved under the first entry's key, `"default"` in every document).

Each tab's screen (Downloads, Search, Settings) passes its tab's path, and the hook also keeps where the tab was left, its query and scroll, when the screen goes away (`src/lib/tabPlaces.ts`, sessionStorage); the tab bar's and the sidebar's items are `TabLink`s (`src/components/TabBar/TabLink.tsx`), which link to the tab with that query and `TAB_RETURN` state, so the screen they open scrolls back to the tab's place (and Search takes the kept pages of that search, `keptSearch`), and on the tab's own screen scroll it to the top instead. Any other screen change on a forward navigation opens at the top through `useNewScreenAtTop` in `App`, by `screenKeyOf`, so a drawer over a page leaves it alone.

### Desktop Downloads

Desktop Downloads (`useIsDesktop()`): the whole header stays at the top: the title, the totals, the name filter and the select button in one row (while selecting, the selection's count and buttons with the name filter, so Select all takes only what it shows), the offline banner, then the status as a `StatusMenu` (phones keep the chips), a type `Segmented`, the sort as a `SortMenu` and the view; the table's column names sort too (`DownloadRowHeader`), with a direction (`DownloadOrder`, kept with the sort in `downloadsSortDescending`) that `SortDirectionButton` (`src/components/SortDirectionButton`) reverses beside the sort button, on both layouts and in the grid too (the sort button opens the menu on desktop and the sheet on a phone). Sorting is shared with the releases: `SortHeader` (`src/components/SortHeader`) is a sortable column's header in both tables, a button with an arrow and `aria-sort`, and `src/lib/sortOrder.ts` has the order (`SortOrder`, a key and a direction) and its rules over a table of each sort's usual direction (`DOWNLOADS_USUALLY_DESCENDING` in `src/torrents/sort.ts`, `RELEASES_USUALLY_DESCENDING` in `filterReleases.ts`): `usualOrder` for a pick, `clickedOrder` for a column's click, `reversedOrder` for the direction button, `cycledOrder` for the phone's releases chip (the sort the other way, then the next sort), which `useReleases` gives its screens as `pickSort`, `clickSort`, `reverseSort` and `cycleSort`; the list is a table of `DownloadRow`s (columns from a CSS custom property, the title takes what the fixed columns leave; container queries show the size only from a 1240px table, and below 920px move the ETA under the speed, so the title keeps ≥ 200px), the grid is the phone's `DownloadCard`s with a Pause/Resume button on hover. Each layout keeps its own view (`downloadsView`, `downloadsDesktopView`, grid by default). `TorrentActionsSheet` and the sort become `Menu` popovers (`src/components/Menu`) when given an anchor on desktop. The sidebar's downloading count and qBittorrent card (`SidebarStatus`) read the shared poll in `App`; in the icon rail the count is a badge on the icon and the card a narrow column of speeds and free space. The alternative speed limits switch (`useAltSpeedLimits` in `src/torrents/`, taking the caller's `useMainData()` so no second poll starts, with `transfer/toggleSpeedLimitsMode`; its pressed state holds until a poll sent after the switch, by the snapshot's `requestedAt`) is in that card on desktop and in the phone's Downloads title row, one owner per layout. The table's first column (queue positions, or the checkboxes while selecting) shows only while selecting or with the Priority sort when a torrent shown has a queue position or that sort is reversed (so its header can turn it back with nothing queued), via `.has-lead`. On phones only `.downloads-bar` is sticky (the chips, sort and view; the selection row while selecting), under the scrolling title and totals and under the status bar's strip (`.status-strip` in `base.css`, a sticky `::before` the height of the safe area, shared with Search), which keeps the list from showing behind the clock. On desktop the whole `.downloads-head` is sticky and takes the safe area itself, so Downloads turns the strip off there; the table's head row group sticks under the header at its height, which `useHeightVar` (`src/lib/useHeightVar.ts`) keeps in `--downloads-head` on the screen, and the header's menus take `follow` so they stay open while the list scrolls. Search does what phones' Downloads does on both layouts: its title scrolls away and `.search-bar` (the field and the filters) sticks under the strip, the header making no box of its own (`display: contents`).

### Multi-select in Downloads

Multi-select in Downloads: `DownloadsScreen` keeps the selected hashes (null outside selection mode); rows and cards (`DownloadItem`, `DownloadCard`) become checkboxes, and `BulkActionsBar` (pause, resume, delete through `useDeleteTorrents`, whose confirmation takes several torrents) replaces the tab bar, which `App` hides through `onSelectingChange`. Actions apply only to selected torrents the filters show.

### Toasts

Toasts: `ToastProvider` (`src/components/Toast/ToastProvider.tsx`, in `App`) shows them all as a stack of up to `MAX_TOASTS`; screens and hooks call `useToast()` (`useToast.ts`) and its `show` with the translated message, never render `<Toast>` themselves; the provider keeps each toast's time, so the stack moving to another layer doesn't restart it. A toast replaces one with the same `key` (the message by default), and `dismiss(key)` takes a failure back when the action is tried again: the keys shared between places are in `src/screens/toastKeys.ts`, and the alternative speed limits switch goes through `useAltSpeedSwitch` (`src/screens/`), which does this for both its owners. `Sheet`, `Dialog` and `TorrentDrawer` register through `useToastLayer` while open, and the stack is portaled into the top one, since the page outside a modal `<dialog>` is inert. Tests get the provider from `renderWithRouter`; a test that renders with plain `render` passes `wrapper: ToastProvider`.

### Screens and components

Screens live in `src/screens/`, shared UI components in `src/components/` (ported from the design system with the same class names).

## In the browser

### Preferences

Preferences live in `src/settings/settings.ts` (localStorage, `useSettings`, `useTmdbLanguage`; `initSettingsSync`, started in `main.tsx` like `initLanguage`, reads them again when another tab saves them; the release filters and sort are checked when read). TMDB language, list or poster grid, the sort in Downloads (`src/torrents/sort.ts`) and the release filters and sort are per browser (`useReleases` starts a search from the remembered filters through `startingFilters` in `filterReleases.ts`, which sets aside what the results don't meet, alone or together; `ReleasesBlock` names what's set aside with Forget). The download defaults (category per type, start paused, sequential, first and last pieces first) are also kept on the server: `useSettings` loads them once per page (`loadServerSettings`) and the server's win, a change is saved to both, a default the server doesn't have yet is sent from the browser that changed it, and without the server the browser's copy applies. Connection settings stay on the server: service addresses in its environment, the TMDB key and the qBittorrent login in its settings file. The theme (`src/theme/theme.ts`, `useTheme`) and the interface language (`src/i18n/language.ts`, `useLanguage`) are their own per-browser stores, each `'system'` by default and following the system's (the browser's languages, `languagechange`) while that's chosen; change the language through `setLanguagePreference`, not `i18n.changeLanguage`, so the choice is saved.

### PWA

PWA: `vite-plugin-pwa` builds the manifest (in `vite.config.ts`) and the service worker from `src/sw.ts` (injectManifest, own tsconfig `tsconfig.sw.json`, which also compiles its smoke test `src/sw.test.ts`). It precaches the app shell, serves `index.html` for app routes except a load with `PROXY_SIGN_IN_PARAM`, which has to reach the sign-in proxy (above, Prowlarr), caches `/tmdb-img/*` posters and never caches `/qbt`, `/prowlarr` or `/tmdb`; those rules live in `src/pwa/swRoutes.ts`, apart from workbox, with their own test. A new version activates right away (no lazy chunks, so open pages keep working). An open page reloads into it through `startUpdateChecks` (`src/pwa/updates.ts`, started in `main.tsx`): at startup and on every return to the foreground it compares `__APP_VERSION__` with `/version.json` (written by `versionFilePlugin` in `vite.config.ts`, not precached), and when they differ and no `dialog` is open and no field has focus it has the service worker take over first (over HTTPS) and reloads, once per version per session; `UpdatedToast` in `App` then names the new version. The service worker is off in `npm run dev`; try it with `npm run build && npm run preview`. Icons: SVG sources in `scripts/icons/`, PNGs rendered by `scripts/render-icons.mjs`. The touch icon iOS takes for the Home Screen goes into the built `index.html` as a `data:` URL (`inlineTouchIconPlugin` in `vite.config.ts`, from the file index.html's `<link>` names in `public/`): iOS fetches a linked one in a process of its own, which got nothing over Umbrel's HTTPS (#304). Service workers need HTTPS (or localhost); umbrelOS 2.0 serves apps over HTTPS with its own certificate, and Kinopeer sets up nothing for it. Over plain HTTP there is no `crypto.subtle` either, so hashing goes through `src/lib/digest.ts`. Push notifications aren't planned.
