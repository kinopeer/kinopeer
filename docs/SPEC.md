# Product spec

What Kinopeer does and why, as of version 1.2.0. Update it in the same PR that changes the behavior; add new decisions to the log at the end.

## Goal

Find a movie or a series, pick a release and download it without leaving Kinopeer. If a flow makes you switch to another app (a tracker's website, qBittorrent's own web UI), that's a gap to close.

## Who it's for

The owner of a home server running umbrelOS with the qBittorrent and Prowlarr apps; Docker, where Kinopeer's compose file brings both; or Docker next to a qBittorrent and a Prowlarr they already run, on that machine or elsewhere (TrueNAS, CasaOS and Unraid among them). The main device is a phone, then a computer. The interface is in Russian and English.

## What Kinopeer doesn't do

- Play or stream video.
- Automate downloads: no watchlists, RSS or automatic search for new episodes. That's Sonarr and Radarr; Kinopeer is for picking a specific release by hand.
- Pick a season on the series page: a series is searched by name, and the seasons and episodes you want are picked in the file list.
- Manage a media library: no scanning, metadata or artwork, no moving into a library's folders. Naming a movie's or a series' files for a media server, in place, is the one exception (Torrent and Adding, below; decision log, 2026-11-23).
- Store tracker logins or get around site protection: trackers are set up in Prowlarr. Jackett is not supported.
- Collect analytics.
- Install other than on Umbrel, with Docker Compose, as its image next to a qBittorrent and a Prowlarr of the user's own (Unraid's template among them), or as qBittorrent's Alternative WebUI (decision log, 2026-11-22), for now: no catalog entry for TrueNAS or CasaOS, no native installer, no Helm chart (decision log, 2026-11-21).
- Group a series' torrents into one card in Downloads: the title page lists a title's torrents instead (decision log, 2026-10-24). Revisit only if that turns out not to be enough.
- Set up HTTPS itself (decision log, 2026-10-25).
- Notify about anything but a finished download. A finished download is told in Telegram, through a bot of the user's own, and as a push notification on the devices that turned them on (Notifications, below).
- Run as a hosted service for other people's qBittorrent (decision log, 2026-10-24): browsers keep a public HTTPS page away from a home-network qBittorrent unless it is set up by hand for CORS and HTTPS, and a server in the middle would hold other people's logins and keys.
- Show a row of what's popular on the user's trackers in Search (decision log, 2026-11-05).

## Platform

The `homelab-kinopeer` package from the Homelab App Store runs on port 8797, depends on the qBittorrent and Prowlarr apps and works without setup. The browser only talks to the Kinopeer server, on the same origin; the server talks to qBittorrent, Prowlarr and TMDB and keeps every secret to itself. Umbrel's login protects Kinopeer, so the package turns Kinopeer's own login off; elsewhere Kinopeer asks for a password of its own (First launch). The server answers only at host names a website can't point at Kinopeer's address (IP addresses, `localhost`, `.local`, `.onion`, names of one label and a few other private ones) and at the ones its environment adds; on Umbrel, whose login comes first, at any name.

Elsewhere, `docker-compose.yml` runs Kinopeer on port 8797 beside qBittorrent and Prowlarr, each in a container of its own; qBittorrent lets Kinopeer's container in without a password and asks everyone else for one, and Kinopeer reads Prowlarr's key from its config, so Kinopeer's own password is the only thing to set (README → Install with Docker Compose).

Kinopeer's image also runs on its own next to a qBittorrent and a Prowlarr the user already runs, in Docker, installed on the machine, on another computer or on a seedbox: onboarding asks for their addresses, as the Kinopeer server reaches them, with qBittorrent's login and Prowlarr's key, or the environment sets them (README → Install next to your own qBittorrent and Prowlarr). TrueNAS (a custom app from YAML) and CasaOS and ZimaOS (a custom app from a Compose file) install it that way, with the platform's own qBittorrent and Prowlarr apps, and so does Unraid, from its Apps tab through the template in `unraid/kinopeer.xml`, which Community Applications lists: port 8797, `/data` in `/mnt/user/appdata/kinopeer`, Kinopeer running as Unraid's `nobody:users` (99:100), and the addresses left for onboarding, whose Find looks on Unraid's Docker network.

| Setting | Where it's kept | Set by |
| --- | --- | --- |
| qBittorrent and Prowlarr addresses | Server environment, else `/data/settings.json` | The Umbrel package; elsewhere the environment, or onboarding and Settings where it sets none and Kinopeer's own login is on |
| Prowlarr API key | `/data/settings.json`, else environment, else Prowlarr's `config.xml` | The Umbrel package, or Settings |
| qBittorrent login | `/data/settings.json`, else environment | The connect screen |
| TMDB key | `/data/settings.json`, else environment | Onboarding or Settings |
| Kinopeer's password (not on Umbrel) | Environment (`KINOPEER_PASSWORD`), else `/data/auth.json`, only as a hash | The environment, else the first visitor; Settings changes one set in the app |
| Download defaults (categories, start paused, sequential, first and last pieces first, notify when finished) | `/data/settings.json`; a copy in the browser | Settings |
| qBittorrent's default save path and its categories' folders | qBittorrent | Settings, or qBittorrent itself |
| Host names the server answers at, besides the private ones | Server environment (`KINOPEER_ALLOWED_HOSTS`) | The Umbrel package (any) |
| Theme, interface language, TMDB language | Browser | Settings |
| Downloads view and sort | Browser | Downloads |
| Release filters and sort | Browser | Releases |
| Torrent-to-TMDB matches | `/data/matches.json`; titles and posters cached in the browser | Guessed automatically; the torrent menu |

In the WebUI build, which has no Kinopeer server, qBittorrent keeps the TMDB key of the user's own, Prowlarr's address and key, the download defaults and the torrent-to-TMDB matches, a key each (a match a key per torrent) in its store for web interfaces, and there's no qBittorrent address or login to keep. The page calls TMDB itself: with the user's own key, checked with TMDB before it's kept, straight to TMDB, else through Kinopeer's TMDB proxy where it answers the page, and Prowlarr itself, at the address and with the key qBittorrent keeps, the key checked with Prowlarr before it's kept. The form that asks for Prowlarr's key says that the browser calls Prowlarr with it, so anyone with qBittorrent's login, a browser extension or a release's link can see it, and advises keeping Prowlarr on the home network, on HTTPS where it can be; it refuses a plain HTTP address for Prowlarr while qBittorrent is opened over HTTPS, which the browser would block, unless the address is on this device (decision log, 2026-11-22).

The browser's preferences follow other tabs: a change saved in one tab applies to the tabs already open, as the interface language does, so a tab's next change doesn't undo it.

A torrent's match is forgotten when the torrent is deleted from Kinopeer. For torrents deleted elsewhere, the server checks qBittorrent's list every hour and forgets a match once its torrent has been missing for a week, so a qBittorrent that answers with an empty list after a restart, or a torrent added back, loses nothing. In the WebUI build the page makes that check, from the list Downloads' refresh gets, at most once an hour, so only while Downloads, a torrent's page or, on desktop, the sidebar is open, and once a screen that shows titles (Downloads, a torrent's page, Search, a title page) has loaded the matches on that page and that load succeeded: a page that has opened only Settings checks nothing, and neither does one whose last read of them failed, until the matches are read from qBittorrent again.

## Screens

### Navigation and layout

- Phones and tablets (narrower than 1024px): a tab bar at the bottom with Downloads, Search and Settings. On a tablet, screens sit in a centered column 760px wide and the tabs stay over it.
- Desktop (1024px and wider, the design system's breakpoint): a sidebar on the left with the Kinopeer logo and the same three destinations, in place of the tab bar. From 1100px it is 248px wide with labels; between 1024 and 1100px it is a 76px rail of icons, the labels kept for screen readers. Screens take the rest of the window. Until their own desktop layouts land in 0.4 they keep the 760px column, centered in that space.
- Each tab (Downloads, Search, Settings) comes back as it was left: at its scroll position, and Search with its last query (the text, the type and the year), whether it's opened from the tab bar or the sidebar. The position comes back once the screen's content is in. Pressing the tab of the screen already shown scrolls it to the top, smoothly (at once for a user who asked for less motion), and Search keeps its query. On a screen inside a tab (a torrent on a phone, under Downloads) the first press goes back to the tab's screen where it was left, the second to the top. Opening any other screen (a title, a torrent on a phone, another tab never opened before) starts it at the top, and so does an address opened afresh; Back, Forward and a reload bring a tab's screen back to where it was. Downloads' filters and selection still start over when it's left.
- Selecting downloads puts the bulk bar in place of the tab bar on a phone; on desktop the sidebar stays and the bulk bar sits at the bottom of the screen beside it.
- On desktop the sidebar also counts the torrents downloading next to Downloads and, at the bottom, shows qBittorrent's version, total speeds and free space, or that it doesn't answer, and a switch for qBittorrent's alternative speed limits. In the icon rail the count is a badge on the Downloads icon, and the status a narrow column at the bottom: the ring that shows qBittorrent's refresh (green, red while it doesn't answer; see Downloads), then the download and upload speeds and the free space, each number over its unit, and the speed limits switch as a turtle icon.
- Short confirmations and failures are toasts above the tab bar (on desktop, at the bottom of the page beside the sidebar): up to three at once, stacked with the newest at the bottom, each gone after 4 seconds, the oldest pushed out by a fourth. The same message again replaces its toast rather than adding one, and a failure goes as soon as the action is tried again (pausing or resuming, the alternative speed limits switch). While a sheet, a dialog or the torrent drawer is open, toasts show inside it, so one from the page behind (a move or a save that failed after its sheet was closed, a reconnect) isn't hidden behind the backdrop and screen readers still announce it; in a phone's bottom sheet they show at the top of the screen, clear of its footer. Taps go through a toast to what's under it.
- Sheets slide up from the bottom on a phone. On desktop the same sheets are modals in the middle of the window, over a dimmed backdrop that covers the sidebar too: 600px wide and as tall as their content, or 680 × 720px for long lists (picking files, changing a title), which on a phone take the full height. Confirmations (deleting torrents) are 440px wide with their buttons on the right. Every sheet has one close button at the end of its title row, the same on a phone and on desktop, and confirmations have their own buttons. Escape and a click on the backdrop close them too; on a phone so does dragging a sheet down by its top (the grabber and the title row), which closes it once dragged far enough or flicked, and otherwise springs it back (the file picker, a step of adding a release, goes back to the add sheet, as Escape and its close button do, beside its own Back). On a touch screen the page behind a sheet or a confirmation doesn't scroll (not on a touch laptop whose main pointer is its trackpad, where hiding the scrollbar would shift the page). As a sheet opens, focus goes to its first control but the close button, so a form sheet opens on its first field. Focus stays inside and returns to what opened them.

### First launch

1. Kinopeer's own login, where it's on (installs without a login in front; not on Umbrel). Until a browser is signed in, the server answers nothing but the app's own files and the sign-in. The first visitor sets the password (8 to 256 characters, typed twice) and is signed in; when someone else set it a moment before, the screen says so and asks for that password, and when the password was reset on the server since the sign-in screen opened, the screen says so and asks to set one; when the login was turned off on the server since then, the next try opens the app. With `KINOPEER_PASSWORD` on the server there's no setup: the screen asks for that password. Each browser signs in once and stays signed in for 30 days from its last visit. Five wrong passwords from one address lock it out for a quarter of an hour, each lockout after that twice as long, up to a day, and the screen says how long to wait. A session that ends while the app is open (signed out on this device, the password changed on another, 30 days unused) brings the sign-in screen back, and signing in returns to the screen the app was on.
2. Kinopeer asks qBittorrent for its version. If the server is already signed in (the package's login or a saved one) or qBittorrent lets the network in without a password, there's no login form. A qBittorrent older than 4.6.0, the oldest Kinopeer works with, gets a screen of its own in place of the app, before or after the login: it names the version, says Kinopeer needs 4.6.0 or later and to update qBittorrent, with Try again, and Change qBittorrent address where the address was saved from the app (step 3), since another qBittorrent may be the one meant.
3. Otherwise, the qBittorrent login form. The server tries a password once and doesn't retry after a rejection: qBittorrent bans the IP for an hour after five failures. When the server has no address for qBittorrent (none in its environment, none saved), the form asks for the address first, as the Kinopeer server reaches qBittorrent. The login is optional, with or without the address: left empty, qBittorrent's auth bypass has to let the server in, else the form asks for a login, so Connect with no login checks again once the bypass is on. Half a login isn't sent: a password needs a username, and a username a password. The server checks the address and the login together and saves both. With Kinopeer's own login off, the server refuses an address from the app, and the form says to set `QBITTORRENT_URL` on the server. When the address was saved from the app and qBittorrent doesn't answer there, or asks for a login, the screen offers Change qBittorrent address, with the saved one to edit and Cancel to go back, since a wrong address is one reason; an address from the environment is changed there.
4. The "Connect TMDB" step: a v3 API key or a v4 read access token, checked with TMDB before it's saved. It can be skipped; search then asks for the key later. It shows only when the server has no key and Kinopeer's TMDB proxy is turned off (`TMDB_PROXY_URL` set empty): otherwise TMDB works with Kinopeer's own key from the start, and a key of the user's own is optional, in Settings.
5. The "Connect Prowlarr" step: Prowlarr's address, as the Kinopeer server reaches it, and its API key, checked together with Prowlarr and saved. It shows only when the server has no address for Prowlarr and Kinopeer's own login is on, so the server would save one. It can be skipped; everything but finding releases works without Prowlarr, and the releases screen says what's missing. A skipped step comes back the next time the app is opened, as the TMDB step does.

In the WebUI build, which qBittorrent serves itself (decision log, 2026-11-22), there's no Kinopeer login and no address to ask for: a browser without qBittorrent's session (none yet, or it ended, an hour unused by default) gets qBittorrent's own login, a username and a password the browser's password manager fills, which says a wrong login, qBittorrent's ban and qBittorrent not answering; signed in, the app checks qBittorrent's version, and anything older than 5.2.0 gets the too-old screen. Then the Connect TMDB step, only where Kinopeer's own key doesn't serve the page (it's on a public address, where Kinopeer's TMDB proxy doesn't answer it) and qBittorrent keeps no key of the user's own, and the Connect Prowlarr step, its address as this browser reaches it and its key, checked together with Prowlarr, until qBittorrent keeps them; each is skippable as above, and what they save qBittorrent keeps for every device that signs in to it (decision log, 2026-11-22, settings in qBittorrent).

On desktop these steps show their form in a card centered in the window, without the sidebar.

### Downloads

- Every qBittorrent torrent, refreshed every 2 seconds while the tab is visible.
- A small ring shows that refresh: it fills over the 2 seconds until the next one, stays full and pulses while qBittorrent's answer is awaited, and turns red while qBittorrent doesn't answer; screen readers hear when the data was last updated, as does a tooltip. On a phone it sits right after the Downloads title, apart from the buttons on the right, so it reads as the data's state rather than a control; on desktop it's at the top of the sidebar's qBittorrent card, before the connection, and at the top of the icon rail's column, whose tooltip also names qBittorrent's version, as the dot's did. Not on a phone's Search or Settings, which don't refresh the torrents. With reduced motion the ring doesn't fill or pulse.
- A turtle button switches qBittorrent's alternative speed limits on and off (on a phone in the title row; on desktop it's in the sidebar). It's highlighted while they apply, whether switched here or in qBittorrent itself, shows the new state as soon as it's pressed (until qBittorrent's next answer), says so in a toast when qBittorrent didn't take the switch, and is off while qBittorrent doesn't answer. The limits themselves are set in qBittorrent.
- A row shows the TMDB poster and title, status, progress, speed, time left and queue position, and a gauge when the torrent has a speed limit of its own, with an arrow for each direction that has a limit, whatever the torrent is doing now; screen readers hear the limits. On a phone a download's speed and time left have a row of their own under the status, and so does the gauge, next to the speed when there is one (a seed's speed moves there with it): the status's row has no room for it next to a "done / total" size. The alternative and global limits aren't the torrent's and don't show it. The title comes from the user's choice, else the `tmdb:<movie|tv>:<id>` tag, else a guess from the release name. Guesses are saved on the server, a guess that found no title too, so every device shows the same and each torrent is guessed once; the server keeps them with no expiry, until guessing itself changes, Settings → Clear cache, or the torrent goes. TMDB is asked once per title while the list is open; a title it doesn't give (offline, TMDB down, no answer in 15 seconds) is asked again after 30 seconds, 2 minutes, then every 10 minutes, and when TMDB or Kinopeer's proxy asks to slow down (429), nothing is asked until the wait it names (10 seconds when it doesn't).
- A list or a poster grid (status and progress over the poster, percent and speed or size under it; the limits' gauge next to the status, since the line under the poster has no room for it). The list is the default on a phone and the grid on desktop; each layout remembers its own choice in the browser.
- On desktop the list is a table: queue position (a column only with the Priority sort, when some torrent shown has one or while that sort is reversed; in selection mode it holds the checkboxes), poster, title and release, progress, status, speed (with the limits' gauge, next to its dash when there's no speed), time left, size, then Pause or Resume and More. A click anywhere on a row opens its details (in selection mode, selects it); the row is one link, its title, with the buttons on top. The title takes the room the other columns leave, so it grows with the window. The size column shows only in a wide window (about 1550px and up), where the title still has about 355px; narrower, it goes, and narrower still the time left moves under the speed, so the title keeps at least 200px. The grid is wider, and a poster shows Pause or Resume in its corner on hover. The name filter always shows in the header and narrows rather than wrapping. Under it, on one row at every desktop width: the filters on the left, the status as a button with the picked status and its count ("All statuses 15", "Seeding 13") and the type (All, Movies, Series); the sort, its direction button and the view on the right. The status, the sort and a row's More open as menus next to their button rather than sheets, and their button closes them again; the status menu lists each status with its count. While another status is picked and some torrents have errors, the status button has a small red dot (and says so to screen readers), so errors don't go unnoticed. Phones keep the status chips.
- Filters by status and name, total speeds, free space.
- While the list scrolls, the controls stay at the top. On a phone that's the bar with the status chips, the sort and the view (and the name field while it's open), with the selection's count and buttons in it while selecting; the title, the totals and the offline banner above it scroll away. While selecting the totals hide with the title, so the selection's row is on top in the title's place (under the offline banner while it shows), as on desktop. On desktop the whole header stays: the title and the totals with the name filter and the select button in one row, the offline banner, then the status, the type, the sort and the view, with the table's column names right under it. While selecting, the selection's count and buttons take the title's row, and the name filter stays there, so Select all takes only what it shows.
- A type filter: All, Movies or Series. A torrent's type is its title's; a torrent without a title yet counts as a series when its name has season or episode markers, or by its qBittorrent category ("Movies", "TV Shows"), and otherwise shows only under All. The status chips (the status menu on desktop) count within the type. A badge with the type sits next to the sort while it isn't All. Like the status filter, the type lasts while the screen is open, and Reset filters resets it too.
- Sorting: Priority (qBittorrent's queue order, the default), Date added (newest first), Name (A to Z by the title the row shows), Progress (most first), Status (what needs attention first: Error, Downloading, Checking, Queued, Paused, Seeding, Completed), Size (largest first), Speed (fastest download first, then upload; torrents neither downloading nor seeding, which show no speed, go last), ETA (soonest done first; torrents without a time left go last). Ties keep the queue order. The queue position on the poster shows only with Priority. The sort and the type are picked in the "Sort & filter" sheet, opened by the sort button; the sort is remembered in the browser. Beside the sort button, on a phone as on desktop, a direction button reverses the order and shows which way it is, so the poster grid, which has no column names, can be reversed too. On desktop the table's column names sort too: a click on the title, progress, status, speed, time left or size sorts by it in that sort's usual direction, the next click reverses it (Z to A, least progress, what's done first, smallest, slowest, latest done); the queue position ("#"), shown with the queue order, reverses that order (from its last position), and stays while it's reversed, also once nothing is queued, so a click can turn it back. Torrents without a queue position, a speed or a time left stay last either way. The sorted column shows an arrow. The sort menu stays, also for Date added, which has no column; a pick there, the current sort included, is that sort in its usual direction. The direction is remembered with the sort, on a phone too; a pick in the phone's sheet, like one in the menu, is that sort in its usual direction.
- Selection: the Select button in the header turns rows and cards into checkboxes (tapping anywhere on one toggles it) and puts Pause, Resume and Delete in place of the tab bar. The header shows how many are selected, with Cancel and "Select all" ("Deselect all" once everything shown is selected). Only the torrents the filters show count, so a filter never leaves hidden ones selected. Delete asks once for all of them, with the same "Also delete files" box and the total downloaded size. After an action the selection ends; if qBittorrent doesn't answer, it stays. Selecting is off while qBittorrent is unreachable.
- Row menu: pause or resume, reannounce, force recheck, speed limits (the torrent's own under the item), details, the title's page, Fix match (Match title for a torrent with no title), move the files, delete with or without files. Reannounce tells the trackers about the torrent right away instead of at the next interval, with a toast; it's on only for a torrent that's downloading or seeding: qBittorrent doesn't announce a paused, queued, checking or errored one (it stops a torrent in error), so the toast would be untrue. Force recheck asks first, since it reads all the downloaded data again and the torrent shows as Checking until it's done, then says so in a toast, and the torrent shows Checking as soon as qBittorrent took it, until the next update says otherwise; it's off while the torrent is already being checked and while a magnet link has no metadata yet (fetching it, or added paused or queued), since there's no data to check. An item that's off says why under its label. A reannounce, recheck or delete on its way for a torrent shows busy in every menu and confirmation for it, on any screen, so it can't be sent twice (while a delete is on its way, nothing else can be sent for the torrent from its menu or its details): a menu or confirmation closed meanwhile and opened again shows it busy (a delete confirmation for several torrents, when one of them is being deleted). How it went is said where the torrent is shown then (a menu stays open with the failure, a confirmation closes or shows the failure), else in a toast, which trying again takes back. A delete says it went through in a toast wherever it was sent from, and the torrents are gone from every screen as soon as qBittorrent took it, until the next update says otherwise; the torrent screen it was sent from goes to Downloads, unless the user left it meanwhile. The menu, and a confirmation or sheet it opens, close when the torrent goes away or another torrent with the same hash replaces it (deleted and added again elsewhere), so none acts on the torrent that replaced it; the torrent screen's do too.
- Pausing and resuming, from a row's button (desktop), the More menu, the torrent's details or the selection's bar: while a pause or resume is on its way for a torrent, each of those that shows the torrent shows it busy, wherever it was sent from (a row's button under the drawer, the drawer's button over Downloads), so it isn't sent twice. Once qBittorrent took it, the torrent shows its new status right away (Paused, or Completed when finished; Downloading or Seeding; with nothing moving either way) everywhere, the counts and filters included, and Kinopeer asks qBittorrent again. qBittorrent reports a torrent's new status only at its next refresh (its Refresh interval, 1.5 seconds by default), so the new status stays for that interval and half a second more; the first answer after that has the final word, even if qBittorrent disagrees. Kinopeer reads the interval from qBittorrent's preferences alongside the first pause or resume on a page; when qBittorrent answers that pause before its preferences, it holds for the default. The selection's bar sends one request for all the selected torrents but those with a pause or resume already on its way. The More menu stays open while its request is on its way, then closes, or says why it failed under its items; elsewhere a failure is a toast, which the next try takes back.
- Statuses: Downloading (the only one in the accent color), Seeding, Paused, Completed, Queued, Checking, Error.

### Torrent

- On a phone, a screen of its own. On desktop, a drawer on the right over the page it was opened from (Downloads, or the title page's "In downloads"), which stays as it was behind it, with its scroll, filters, selection and searched releases: Escape, Close or a click outside closes it and goes back to that page, with focus back on the row or card. The address is the torrent's either way. Over the title page, deleting the torrent closes the drawer and the title page drops it from "In downloads", and the More menu's movie or series page of that same title just closes the drawer. A shared link or a fresh load of the torrent's address opens the drawer over Downloads, and closing it goes to Downloads.
- Pause, resume, delete; progress, time left, ratio. The More button opens the same menu as the row, with reannounce and force recheck.
- The title's poster and name, with the release name under it. A title matched from the release name shows as any other: nothing asks whether it's right, and Fix match in the More menu corrects it. When no title was found, More has a small static dot in a light teal of the accent, on the phone page and in the desktop drawer (More is dark glass in both themes, so the dot is the same in both, as its icon is), and screen readers hear why ("This torrent isn't matched to a movie or series"); in its menu Match title is in the accent too. The dot doesn't show while the title is still being looked up, and goes once a title is chosen; nothing remembers it was seen, so it stays until the torrent has a title. It sits on the button, out of the page's flow, so nothing moves when it comes; the poster stays the plain placeholder.
- Changing the title: Fix match in the More menu, or Match title for a torrent with no title (in the accent, wherever the menu opens: the torrent's page and drawer, whose More then has its dot, and a Downloads row, whose More has none), opens a TMDB search headed Title match («Сопоставление»), the same whether the torrent has a title or not, with the release name under it; it starts from the name read from the release, with All, Movies and Series; the current title comes first and is marked. Picking a title saves it on the Kinopeer server (in qBittorrent in the WebUI build) as the user's choice, which wins over the tag and any guess; picking the title already shown keeps it that way, so a right guess stays when guessing changes. A save on its way for a torrent shows busy wherever the torrent's title can be chosen (the title search opened again shows the pick being saved), on any screen, so it can't be sent twice; a toast says it was saved, and a failure is said in the title search that shows the torrent then, else in a toast.
- Speed limits: download and upload limits of this torrent in MB/s (up to 2147, the most qBittorrent stores), in a sheet of their own (a menu can't hold a form); an empty field means no limit. While the torrent has a limit of its own, Remove limits drops both at once, saved as Save saves (busy, failure and toast alike), and isn't offered while a save is on its way. The menu item is off while qBittorrent is unreachable; an open sheet keeps its fields but can't save until qBittorrent answers, and goes away with its torrent (or when another torrent with the same hash replaces it). While the limits are being saved the fields can't be changed, since the sheet closes once they're saved. The sheet can be closed meanwhile. Opened again for that torrent, on that screen or another (the drawer over Downloads), it shows the save still going, with the limits being saved in its fields (Save stays off, so they aren't sent twice), then closes once they're saved or says they weren't; otherwise a failure comes as a toast, on whatever screen is open by then.
- Download, a section that's always open, under Pause and Delete: the category, which opens a sheet to change it, and, until the torrent is complete, switches for sequential download and first and last pieces first, and, while a notification channel is set up (Notifications, below), Notify when finished. Once it's complete the switches go, since they only change how the rest downloads, and the notification has nothing left to wait for. Each switch shows its new value while it's being sent and is off meanwhile, on every screen, and keeps the value once qBittorrent took it until qBittorrent reports it, staying off for that time, since a tap back then would read the old value and flip nothing; a failure is a toast. The Category sheet lists no category and qBittorrent's categories (and the torrent's own, if it's no longer among them). For a torrent under automatic management, each category shows the folder its files would move to, and a note under the list says what happens for the one picked: qBittorrent moves the files there (for an incomplete torrent kept in a download path, "Keep incomplete torrents in" or the category's own, the note says the files move to the category's folder without naming it, and no folders are shown for those categories), they're in that folder already, or, when qBittorrent's settings say not to relocate, it switches the torrent to manual mode and the files stay; for a torrent in manual mode the note says the files stay. Save is off until another category is picked and while qBittorrent is unreachable. After Save a toast says where the files are moving, or that the category changed; the status shows Checking while qBittorrent moves them, as after Move files. The sheet follows the same rules as Speed limits and Move files for a change on its way: it can be closed, opened again with the category being sent, and a failure is said in the sheet that shows the torrent, else in a toast. Everything in the section is off while qBittorrent is unreachable or the torrent is being deleted.
- Details and Files are sections that open and close by their title, both closed when the page opens. Files shows how many files there are next to its title once it has been opened, and keeps the number when closed again; while it's closed the file list isn't asked for.
- Files as a tree, as in the torrent, without regrouping, but without the torrent's single root folder; sorted by name, numbers by value. Priorities: Skip, Normal, High, for a file or a folder; a folder's sets every file under it in one request and shows Mixed while they differ (the torrent's root folder, which isn't shown, has none). A priority change on its way shows what's being sent and can't be changed again meanwhile, nor can the folders above its files or the files under its folder (the other files and folders can), also when the page was left and opened again; once qBittorrent took it, the files keep it until the next update of the list says otherwise, also when Files was closed meanwhile and opened again. A failure is said above the list, else in a toast (also when Files was closed before qBittorrent answered).
- Speeds, speed limits (only those that are set), seeds and peers, save path, date added, info hash, trackers. The category is in Download.
- Moving the files: "Move files…" in the More menu opens a sheet with the folder, starting at the current one, and the folders qBittorrent already knows as chips: its default save path and each category's folder, placed as qBittorrent places them (a relative path or none under the default save path, a subcategory without a path under its parent's folder as the version of qBittorrent puts it (decision log, 2026-11-19), the name made a valid folder name). The folder has to be a full path (from `/`, or from a drive on Windows): qBittorrent would check a relative one, or one starting with `~`, against its own working directory, so the field says so and Move stays off. Move hands the folder to qBittorrent, which creates it if needed and moves the files in the background; a toast says where they're going. The torrent keeps its category, but qBittorrent turns off automatic management for it, so the category no longer decides its folder; the sheet says so. If qBittorrent can't create the folder, the sheet says so and stays open; a folder that's there but read-only is taken, as qBittorrent from 4.5.2 takes it, and the torrent then fails in Downloads (decision log, 2026-11-22). The sheet can be closed while the move is being sent, and the screen left: a failure then comes as a toast, on whatever screen is open by then. While the move is being sent the folder can't be changed, since the sheet closes once it's sent. Opened again for that torrent meanwhile, on that screen or another (the drawer over Downloads), the sheet shows it busy, with the folder being sent in its field (Move stays off, so the move isn't sent twice), and then closes or says why it failed; a retry then sends that folder. Move is off while qBittorrent is unreachable, and the sheet closes if the torrent goes away.
- Clear messages for disk errors and missing files.
- Naming for a media server, for a torrent matched to a movie: "Name for a media server" in the More menu, after Move files, opens a sheet with what would change, the folder and each file whose own name changes, old over new: the torrent's folder becomes `Title (Year)` and its main video `Title (Year).ext`, and the files named after the video (subtitles, an .nfo) keep what follows its name (`Title (Year).ru.forced.srt`). The title is the one the app shows, in its TMDB language, with what file systems and media servers don't take left out (`:` becomes ` - `). The main video is the largest video; when its path has "sample" as a word nothing is named, and a smaller video with the word is a sample, which doesn't count as a second one; every other file keeps its name and its place under the folder, and a torrent of one file, or of files without a folder, gets a folder. The sheet doesn't name, and says why, a torrent with no video, with a second video over a quarter of the main one's size (a movie's parts or versions: which to name is unclear) or with a disc's folders (`BDMV`, `VIDEO_TS`), which players read as they are; files named so already are said to be. Nor does it name a torrent while another torrent qBittorrent lists is in the folder naming would use, in this one's save path (letters' case aside), and it says which: the two would share files. qBittorrent renames the files in place and keeps seeding them: nothing moves to another folder, which is Move files' job. "Restore original names" in the same sheet, shown when a name under the torrent's folder differs from the torrent's own (a folder alone that differs is how qBittorrent's content layouts place a torrent, not a rename), renames every file back to the names in the torrent's metadata (qBittorrent's export of the .torrent), however they were renamed, in Kinopeer or elsewhere; when qBittorrent can't give the metadata, the sheet says the names can't be restored. The item is off while qBittorrent is unreachable, the torrent is being deleted or it has no metadata yet. The renames follow the same rules as Speed limits for a change on its way: the sheet can be closed, opened again with the renames being sent, and a failure, after which some files may be renamed, is said in the sheet that shows the torrent, which reads the names again a second later, once qBittorrent has applied the renames it took, else in a toast; a toast says once they're done. While renames are on their way, the sheet sends nothing more, and neither "Restore original names" nor Back changes what it shows; a sheet opened again then shows what's being sent, the renames themselves, naming or the way back.
- For a torrent matched to a series, the same item and sheet name its episodes: the show's folder `Show (Year)` (the year it first aired), each season in `Season 01` (`Season 00` for specials), each episode `Show (Year) S01E01.ext`, a file of several `S01E01-E02`, and the files named after an episode's video in its folder (subtitles, audio) keep what follows its name. An episode is read from a video's own name (`S01E01`, `S01E01E02`, `S01E01-E02`, `S01E01-02`, `1x01`), or from an episode marker (`E01`, `Ep 01`, `Episode 1`, `Серия 1`, `1 серия`) with its season from the video's folders, its name or, for a video in no folder of the torrent's, the torrent's name (`Season 1`, `Сезон 1`, `1 сезон`, `S01`), every one of them naming the same single season. A video whose episode can't be read that way, whose seasons disagree, whose name reads two different episodes or a range across two seasons (`2x07-3x08`), or that reads an episode another video reads too keeps its name, and the sheet lists it under "Episode not read"; a sample keeps its name and isn't listed. Every other file keeps its name, in a season's folder: the torrent's own season folder (`Season 1/`, `S01/`) becomes `Season 01/`, a torrent of one season puts the rest in that season's folder, and one of several seasons leaves it in the show's folder. The sheet lists each file, and each video whose episode isn't read, by its path below the torrent's folder, which tells seasons apart, and a title made only of what a name can't take gives `Show`. When no episode can be read the sheet says so and names nothing; so it does when naming would put two files in one place (a file of the torrent's folder and one of its season folder of the same name) or a file where another one is now, letters' case aside, and when some of the torrent's files are in the show's folder and some aren't, as a rename that stopped partway leaves them; with no video or a disc's folders it says so as for a movie. Seasons downloaded apart share the show's folder, so the sheet doesn't refuse because another torrent is in it, as for a movie, but because one has a file where naming would put one of this one's, or a file where naming needs a folder or the other way round (letters' case aside): it reads the files of the torrents in the show's folder, in this one's save path, when it opens, each placed under its own save path, so a torrent saved in the show's folder itself counts, and when one has such a file, or its files can't be read, it names nothing and says which torrent is there. Restore and a change on its way work as for a movie.

### Search

Movies and series from TMDB with a type filter. An empty search shows rows of titles that are likely on torrents already, in good quality, rather than what's in cinemas:

- "New on digital": movies out on digital or disc in the last 60 days, first released (often at a festival) no more than about 18 months ago, most popular first.
- "New episodes": scripted series and miniseries with an episode aired in the last 14 days, most popular first (talk shows, news and reality are left out).
- "Best of the year": movies out on digital or disc in the last year (first released no more than about 18 months ago), rated by at least 300 people, best rated first.

A release date in any country counts, up to the current day anywhere. The type filter hides the rows of the other type. A row whose query fails or comes back empty is left out, heading and all. When the type picked has no rows left, Search shows the error if its rows failed and a note that there's nothing to suggest if TMDB had nothing; both have Try again. A wrong key shows the key screen, even if some rows load. The query and type live in the page URL, and Back from a title (or the Search tab, see Navigation and layout) returns to the results at the same scroll position.

While there's a query, a year field stands beside the type tabs: four digits search only movies released and series first aired that year (a year from 1870 to ten years ahead; fewer digits search without one, and four digits out of that range mark the field invalid and are ignored). It lives in the URL as `year`, with the query and type. With a year and All, the movies and the series each keep TMDB's order for the query and are interleaved by popularity. With nothing found for that year, the empty state offers to clear the year rather than the query. The rows before a search don't use it, so the field is hidden without a query, and emptying the query (with the clear button or by deleting it) clears the year too, to start over. On phones narrower than 360px the tabs are tighter, so the field keeps its room on their row.

The results of a search: All searches movies and series together; Movies or Series searches TMDB for that type alone, so a tab picked for the first time searches again; picked again for the same query, it shows the pages it loaded, without asking TMDB. A query typed again searches again. Above them, TMDB's count for the whole search, worded as an estimate ("About 1,296 results"): TMDB's search for both types counts the people it finds too, which Search leaves out. With a year and All, it's the movies' count and the series' added up. Under them, Show more loads TMDB's next page and adds it to the list, until there are no more pages (TMDB stops at page 500); a title that already came on an earlier page is left out, since results can shift between pages. While a page loads the button is busy; when it fails, a note with Try again takes its place and what's loaded stays (a wrong key shows the key screen instead, as on the first page). A page still loading when the tab or the query changes is dropped, and asked for again on the next Show more. With a year and All, the movies and the series go page by page together, and once one of them has no more pages the other goes on alone. Back from a title, or the Search tab, shows the pages that were loaded at once, without asking TMDB again, at the same scroll position. They're kept in the page's memory for the last ten searches the screen showed, one place per search, so after a reload (or many searches later) Back starts again from the first page.

While the page scrolls, the search field, the type tabs and the year stay at the top, and the title scrolls away on both layouts, as in Downloads on a phone. What scrolls off the top passes under the status bar's strip, not behind the clock.

A title already in qBittorrent says so on its card, in the rows and in the results: a badge over the poster's top corner with a download icon and the title page's figure: one torrent's progress ("41%"), or the count of several ("3"); a screen reader reads the title page's words ("In downloads · 41%"). It counts only torrents whose title is known without asking TMDB: the user's choice, the tag Kinopeer adds with a release, a guess the server keeps or one this browser has cached; a torrent nobody has guessed yet (Downloads guesses it on its next visit) marks no card. The torrents come from Downloads' refresh, which runs while Downloads, a title page or, on desktop, the sidebar is open, and Search doesn't start it: on a phone the cards show what it last had on this page, which may be a little behind, or, when Search is the first screen opened, the list qBittorrent gives once. Without an answer from qBittorrent no card is marked; without the server's matches the cards go by the tags and this browser's guesses, as Downloads does then.

On desktop the screen fills the window beside the sidebar: the search field up to 640px wide, rows of larger posters (with a thin scrollbar for a mouse) and results in a grid as wide as the window.

### Title

Poster, year, runtime or number of seasons and episodes, rating, overview, and a "Find releases" button.

- "In downloads": at the end of the page, under the recommendations, a card for each of this title's torrents (by the same match the downloads list shows: the user's choice, the tag or a guess), newest first. A card shows the season and episodes read from the release name ("S02 E01–05") and the resolution, the release name, progress, status, speed and size, and opens the torrent screen. Hidden when there are none, and when qBittorrent doesn't answer before the first refresh. It shows once the recommendations row has loaded (or failed, or come back empty, or not answered in 15 seconds, when it's given up), so the row doesn't push it down as it comes; a tap on the badge before then takes the page to where it will show.
- "Recommendations": at the end of the page, a row of posters from TMDB's recommendations for the title, of the same type, each opening its title page. When TMDB has no recommendations (usually a little-known title), the row shows TMDB's similar titles and is called "Similar titles". Hidden while it loads, when TMDB fails and when both lists are empty: it's an extra, and the rest of the page doesn't wait for it, apart from "In downloads" under it. A title in the row that's already in qBittorrent has the badge Search's cards have (see Search). On desktop it's under the releases once they're searched.
- A badge in the header, above the title: "In downloads · 41%" for one torrent, "In downloads · 3" for several. A tap scrolls the page down to "In downloads". It comes in above the title without moving it.
- The way back: the torrent's menu (in Downloads and on the torrent screen) has "Movie page" or "Series page".
- Desktop: a wide hero over the blurred poster (poster, title, original name, year and runtime or seasons, rating and genres in one line, the overview), with "Find releases" in it and the series hint beside the button. The poster stays at the top, by the title, however long the overview is; an overview longer than five lines is cut there, with "Show more" under it that opens the rest in place (and "Show less"). "In downloads" cards sit side by side at the end of the page, under the releases and the recommendations. Opening the page sends no request to Prowlarr: pressing "Find releases" searches and shows the releases under the hero, scrolled to, and the address becomes the releases one. That address opens the page with the releases searched, starting at them with no scroll animation. Back leaves the page, whether or not the releases were searched; pressing the button again scrolls back to them.

### Releases

- The query is the original title, plus the year for a movie. No category filter: some indexers file everything under "Other".
- When the original title is in a script indexers don't list it by (Korean, Japanese, Chinese, Thai…: no Latin or Cyrillic letters in it), the title is searched by its English name from TMDB too, with the same year, and both searches' releases show as one list, an indexer's release both found shown once (by its info hash, else the guid Prowlarr gives it; not by its download link, which Prowlarr encrypts afresh for each search), while the same torrent from two indexers stays two rows, as one search lists it. The search waits for the English name; if TMDB doesn't give it, the original alone is searched, and Try again asks TMDB for it again, then searches anew. Filters picked for the title stay through Try again. If either search fails, the list says the search failed rather than show part of it. An indexer with releases from either search answered, for the count's line. An original in Latin or Cyrillic script is searched by that name alone.
- The query is shown in a field above the filters, on the phone's releases screen and on the desktop title page's releases. Editing it searches nothing until it's submitted (Enter, or the keyboard's search key), since a search asks every indexer; then the releases are searched by that text alone, as written, with no year added and no English name. The edited query is kept in the address (`?q=`), so Back to the releases and a reload keep it, and another title, opened without it, starts from its own built query: it isn't remembered between titles. Submitting it replaces the address's entry, so Back leaves the releases rather than going through the queries. Reset query, shown while the query is edited, brings the built query back; so does submitting the built query or an empty one. Submitting the query already searched searches it again, once its search has settled. On a phone the field scrolls away under the title bar, while the bar and the filter chips stay pinned. The field shows the original's query while unedited, though a title in another script is searched by its English name too. Filters picked for the title stay through a new query.
- Resolution, source, HDR, audio and seasons are read from the release name. A resolution written as a number wins over a UHD or 4K marker ("UHD BDRip 1080p" is 1080p). HDRip is a source of its own, not BDRip: it's an HD rip, usually of a WEB or HDTV source. A theater rip (a camera in the cinema, a telesync or a telecine: CAMRip, HDCAM, TS, TC and their spellings) is a source too, shown as "CAM" in English and «Экранка» in Russian on the release and in the filter, after every other source. A bare "CAM" isn't one, since a film is called that; nor is a note that only the audio comes from one ("Звук с TS", "Звук: TS", "TS Audio"), an MPEG transport stream ("MPEG-TS"), or a file's lowercase ".ts" extension; and a name that also states a real source keeps that one.
- Filters: resolution, audio, source, minimum seeds, indexer. Sort by seeds, size or date, each most, largest or newest first; a direction button beside the sort reverses it. Picking a sort gives it in that usual direction, the current sort included.
- Each filter value shows how many releases the list would show with that value picked alone in its filter, the other filters as they are ("1080p 24", in tabular figures), on the phone's filters sheet and in the desktop popovers alike: what's picked in the value's own filter doesn't change its count, so picking a second resolution adds the releases its count says. The counts follow the filters the search applies, so a remembered filter set aside counts for nothing, and Not stated counts the releases that don't state the value. A release with several voice-overs counts under each. A value that would leave none is dimmed, not hidden, and can still be picked.
- Much of what indexers name doesn't state the resolution, the source or the voice-over. Each of those three filters then has a value of its own, Not stated (a name with only subtitles states no audio), offered when some release found lacks the value; picking 1080p alone still shows only 1080p releases, and picking Not stated beside it adds the ones that don't say. Not stated is remembered and set aside like any other value. Among a filter's options, under its name, it says just "Not stated"; on the filter's button, the removable chips and the note on filters set aside, where the filter's name isn't next to it, it says which: "Resolution not stated", "Source not stated", "Audio not stated".
- The next title's search starts from the filters and the sort picked last, remembered in the browser; the indexer starts unpicked. A remembered filter none of the releases found meets (a resolution, audio or source they don't have, a minimum of seeds none reaches) is set aside for that search, so it doesn't hide every release, and applies again to the next title. If the rest still match no release together, filters give way one at a time: the seeds, then the source, the audio, and the resolution last; one that turns out not to be in the way comes back. The filters set aside are named above the list ("Remembered filters not applied: 2160p") with Forget, which forgets just those. Changing a filter remembers it, keeping its remembered values that were set aside; picking Any seeds while a remembered minimum is set aside (so Any is what shows) keeps that minimum. Clear all and Reset forget the filters but keep the sort. A releases list open in another tab follows filters saved here until a filter is picked in it.
- When indexers fail, the line with the count of releases says how many didn't answer ("24 of 24 releases · 1 indexer didn't answer"), and a tap on that part names them under it. With nothing found, a quiet note under the empty state, below its Try again, says it with the names, so nothing above it moves as it comes; with nothing the filters let through on a phone (where the count isn't shown then), the note is above that empty state. Prowlarr's search answers with what the other indexers found and says nothing about the rest, so once the search answers Kinopeer asks Prowlarr which enabled indexers failed since the search started or are on hold after earlier failures (which its search skips). The results don't wait for that answer: it's said when it comes, in the count's line, so nothing is pushed down, and if the question fails or takes over 5 seconds nothing is said. Prowlarr dates an indexer's last failure from any client's query (Sonarr, Radarr, its own indexer tests), not only this search's, so an indexer with releases in these results is left out: it answered this search. The window is the time since the search started, at most ten minutes; on a phone that sleeps during the search it can come out shorter (Safari's clock pauses), so a failure early in the search may go unnamed. An indexer with no releases that failed only for another client's query during the search is still named: the status Prowlarr keeps can't tell the two apart. Kinopeer doesn't say why an indexer failed: Prowlarr's API keeps only when it failed, and the reason stays in Prowlarr's logs.
- The indexer's name on a release (the card, the table row and the add sheet) links to the release's page on the tracker, in a new tab, for what Kinopeer doesn't show: the description, screenshots, comments. Plain text when the indexer gives no page, or one that isn't an http or https address.
- A release qBittorrent already has, found by the info hash its indexer gives, opens the torrent in place of Add: on a phone the card's add button is a check, on desktop the row's Add is "In downloads", and either opens the torrent as the add sheet's button does (its screen on a phone, its panel over the page on desktop). The list goes by the torrents the page has already (the downloads list's last refresh, else one question to qBittorrent per page), so a torrent added since on another device isn't marked; the add sheet still asks qBittorrent and says so. A release whose indexer gives no hash isn't marked, nor the release of a hybrid torrent whose indexer gives only its v2 hash, since qBittorrent knows that torrent by its v1 hash; a release of the same title with another hash isn't the same torrent and stays addable.
- When Kinopeer's server has no address or key for Prowlarr, the screen says Prowlarr isn't set up, and when Prowlarr rejects the server's key, that it didn't accept it. Either way it offers the form Settings → Connections has (Set up Prowlarr, or Change Prowlarr key), in a sheet over the screen: with the address where the app can set it (behind Kinopeer's own login, with no address from the server's environment), else the key alone. Once Prowlarr takes what was entered, the search runs again. With Kinopeer's own login off and no address on the server, only the server can set it, and the screen says so with nothing to press.
- A release name is clipped to two lines. On a phone a tap shows the whole name; on desktop the whole name is a tooltip on hover, and the name isn't a button.
- Phone: a screen of its own with a back button; the filters are in a sheet and releases are cards. The row of filter chips is there from the start: while the search runs it shows skeleton chips, as the list shows skeleton cards, and when there's nothing to filter (nothing found, Prowlarr not set up or not answering, the title not found) its room stays, empty, so what's said instead doesn't move up. The sort's chip comes first, right after Filters: a press turns the current sort the other way, and the next press goes on to the next sort in its usual direction (most seeds, fewest, largest, smallest, newest, oldest).
- Desktop: on the title page (see Title). The sort with its direction sits in the section's heading row, to the right of "Releases" and the count, and works from the start of the search; it isn't shown with nothing to sort. Under it, a bar that stays at the top while scrolling holds a chip per filter, each opening its values in a popover (Escape or a click outside closes it). The bar is there from the start: while the search runs the filters are skeleton chips; with nothing to filter its room stays, empty. Picked filters show as removable chips with "Clear all". Releases are a table: release name with season and quality badges, audio, size, seeds, peers, indexer, age and Add. The Size, Seeds and Age columns' names sort too, as in Downloads: a click sorts by the column (Age by the date) in its usual direction, the next click reverses it, and the sorted column shows an arrow; the sort beside the heading shows the same sort and direction. Below 1400px the audio badges move under the name.

### Adding

- Kinopeer gets only the `.torrent` (preferred, so files can be picked) or the magnet link from Prowlarr and adds it to qBittorrent itself. Prowlarr's own download clients aren't used.
- In the WebUI build, where the page asks Prowlarr itself, a release Prowlarr answers with a redirect (a magnet link, or the indexer's own link), which the page can neither follow nor read, goes to qBittorrent as Prowlarr's link, which qBittorrent follows itself. Its files come as a magnet link's do: all of them, skipped later on the torrent's page. Whether qBittorrent has it already is checked by the hash Prowlarr gave with the release, when it gave one (for certain by a v1 hash), and Prowlarr's magnet link goes in its place when the release has one. qBittorrent takes such a link before it has fetched it, so an add it can't fetch isn't said: the sheet says that a torrent that doesn't show up in downloads is one qBittorrent couldn't fetch, and to try another release.
- Options: category (the default from Settings, else a qBittorrent category with a matching name such as Movies or TV Shows), save path, start paused, sequential, first and last pieces first, add to the top of the queue, and, while a notification channel is set up (Notifications, below), Notify when finished, from its default in Settings.
- File selection and a free space check. With skipped files, the torrent is added stopped, the skipped files get priority 0, then it starts. A magnet link downloads every file.
- When what's selected (the chosen files, or the release's size for a magnet link) is larger than qBittorrent's free space, the sheet warns with how much is missing. A `.torrent` that can't be read gets no warning, since its size is only Prowlarr's figure. When qBittorrent reports 0 or less free space, which means it can't tell, the sheet and the file picker show no free space and no warning, like Downloads; the sidebar on desktop shows `—` for it, as before qBittorrent first answers. The free space comes with the regular update of qBittorrent's state, so it and the warning stay current while the sheet is open. It doesn't block adding: space can be freed before the download finishes, and qBittorrent reports the free space of its default save path only, so a save path on another disk may have room.
- Free up space, next to the warning in the add sheet and the file picker, opens a step of the sheet (full height on a phone): qBittorrent's torrents with what each has on disk (the part of its selected files it has), to pick and delete with their files, through the same confirmation as Downloads, which says the files go rather than asking. The list starts with the largest on disk, sorted by size on disk, date added or ratio, each way, under the names Downloads and the torrent page give them; the sort is remembered in this browser apart from Downloads' sort. ### Offline and errors

- qBittorrent stops answering: the last state stays under a banner with its age, actions are disabled, retries are automatic. A refresh that gets no answer in 10 seconds counts as qBittorrent not answering. When the device comes back online or the page comes back to the foreground, a refresh still waiting for its answer is given up and sent again at once, rather than waited for; a page that goes to the background gives up its refresh without counting it as a failure, and refreshes on return.
- Before the first answer: a "qBittorrent isn’t answering" screen. On the connect screen, when the session check gets no answer, the same screen takes the login form's place (in its card on desktop), since there's no one to sign in to; a sign-in that fails for want of an answer says so over the form, so what was typed stays.
- Who isn't answering: Kinopeer's own server (or the way to it: the network, Umbrel's proxy) or qBittorrent behind it. The connect screen, the banner, the screen before the first answer, the poll's ring, the sidebar and Settings' qBittorrent check and a failed add say "Kinopeer" when the request got no answer at all, Umbrel's login wanted it, or something in front of the server answered for it, and "qBittorrent" when the server answered that qBittorrent doesn't, or the request took too long (the server waits for qBittorrent). The same goes for TMDB and Prowlarr: the title page, Search, the releases, adding a release when its torrent can't be fetched, Fix match and Settings' Prowlarr and TMDB checks say "Kinopeer" in the same cases and the service's name when the server answered for it; Settings' Telegram check says "Kinopeer" only when the request got no answer at all or Umbrel's login wanted it (#566).
- Why qBittorrent or Prowlarr isn't answering, where Kinopeer's server can tell, and what to check: the name in the address doesn't resolve (check it, or use the IP address); nothing listens on the port (check that the service is running, the port, and that the service, for qBittorrent its Web UI, takes connections from the network and not only from 127.0.0.1); nothing answered in time (a firewall, or the wrong host); an https address on a port that answers in plain HTTP (start it with http://); a certificate the server doesn't trust (use the http:// address); the connection closed with no answer (check the port and http:// or https://). And when qBittorrent refuses the address before any login, which its Host header validation does when the Web UI is published on another port of the host (`18080:8080`), the qBittorrent form says that, not that the login is wrong, and what to change: the port, the names in its Server domains, or the validation itself. It's said where a person setting up looks: on the address field or over the form when a check of an address, a login or a key fails, in the connect screen's "qBittorrent isn't answering", in Settings' connection checks, and on a title's releases when Prowlarr isn't answering. Elsewhere (the banner over the last state, the poll's ring, the sidebar) the app says only who isn't answering, as before. A check of an address, a login or a key gives up after 15 seconds without an answer.
- Kinopeer in a container with a network of its own (its own image says it's in a container, as do Docker's and Podman's marks), where two setup mistakes are common. A container sharing the host's network (`--network host`) gets neither hint, as outside a container: localhost there is the host, and qBittorrent sees the host's address. It's told by an interface backed by a device (a network card) or a bridge (Docker's, Podman's), so a doubtful setup gets no hints, one whose `/sys/class/net` can't be read among them: a wrong hint costs more than a missing one, and the form still says why the service didn't answer. Inside a container of its own, an address on `localhost` or `127.0.0.1` leads into the container, not to the computer it runs on: when a form's address on it doesn't answer, or answers as something else (Kinopeer's own port is qBittorrent's default, 8080), the form says so and offers the host's address as Kinopeer's container reaches it (`host.docker.internal` where it resolves, else the container's default gateway) with Use this address, or says to enter the host's address or the service's container name when the server doesn't know the host's. And when qBittorrent asks for a login the server has none for, the connect screen (and the form, until its own check answers otherwise, and not while changing the address) says to set a password in qBittorrent and enter its login, as README does, and only as the other way names the address qBittorrent sees Kinopeer at and its network's subnet for qBittorrent's auth bypass, saying that it lets in everything else from that subnet too. That part is said only where qBittorrent is on the container's own network, the host included, since past it requests leave with the host's address, which the hint would name wrongly.
- Find, under the address field wherever a form asks for qBittorrent's or Prowlarr's address (the connect screen, onboarding's Prowlarr step, Settings → Connections, a title's releases), only where the app can save that address, so behind Kinopeer's own login: Kinopeer's server looks for the service where it usually is and lists the addresses that answered as it, one tap each to put one in the field, which the form then checks as any address it's sent. It looks only when Find is pressed and takes a few seconds at most: at the names the usual images and stacks give the service's container (`qbittorrent`, `qbittorrentvpn` and `gluetun` for qBittorrent, `prowlarr`), then outside a container at `localhost` and inside one at `host.docker.internal` and the host as the container reaches it, then at every address of the /24 around each of the server's own private IPv4 addresses (RFC 1918's and 100.64.0.0/10), up to four of them, and none around a public one, where the neighbours are other people's machines, each on the services' default ports (qBittorrent 8080 and 8181, Prowlarr 9696). Something that takes the connection counts only when it answers as the service: qBittorrent by its version, or by asking for its login as only qBittorrent does, or by refusing the address with its Host header validation; Prowlarr by its sign-in page, so no key goes to an address that isn't Prowlarr yet. - A screen crashes: an error screen with a Reload button.

### App (PWA)

Manifest and icons; the service worker keeps the app shell available offline and caches posters, and never caches qBittorrent, Prowlarr or TMDB data. An app left open, a tab or the app on the Home Screen resumed from the background, checks for a new version when it starts and whenever it comes back to the foreground, and reloads into it when no sheet or dialog is open and no field has focus (otherwise on the next return), then says in a toast which version it was updated to; over HTTPS it first waits for the new service worker to take over, so the reload isn't answered with the old shell. The service worker needs HTTPS, so it doesn't run over plain HTTP on the home network; umbrelOS 2.0 serves Kinopeer over HTTPS too, with Umbrel's own certificate, and Kinopeer sets up nothing for it. Everything else, reading `.torrent` files included, works over plain HTTP. In the WebUI build the service worker takes the page from qBittorrent first and keeps the cached app only for when qBittorrent doesn't answer (no whole page in 5 seconds, or a proxy in front of it saying so): once Kinopeer is turned off in qBittorrent's settings, qBittorrent's own interface shows at the next load, and the service worker removes itself. Umbrel's login in front of Kinopeer keeps the browser signed in with a cookie for a week from the last page load through it; when a request comes back redirected to that login, Kinopeer loads the screen it's on through it (Umbrel asks for its password only when its own session is gone too) and comes back to that screen. Where nothing answered for Kinopeer's own server, the device is online and a service worker answers the page (so over HTTPS, never over plain HTTP), Open again beside Retry loads the screen past the service worker, with one hint, the same everywhere, on when to use it, so the browser can show what it waits on: Umbrel's sign-in, or its warning about a certificate it no longer trusts (Umbrel renews its certificate every month, and a browser that accepted the old one through its warning doesn't trust the new one).
