# Development

How to run Kinopeer locally, how the server is configured and how a release goes out. The architecture is mapped in [ARCHITECTURE.md](ARCHITECTURE.md), an area a file in [`.claude/rules/architecture/`](../.claude/rules/architecture/), the CI in [`.claude/rules/ci.md`](../.claude/rules/ci.md), the conventions in [CLAUDE.md](../CLAUDE.md).

## Requirements

Node.js 22.18+ (the tests need 22.22.2+, 24.15+ or 26+, jsdom's range) and qBittorrent with the Web UI on. Release search needs Prowlarr. Development needs no TMDB key: metadata comes from TMDB through Kinopeer's TMDB proxy, and the dev server and the README screenshots use its edge worker (The TMDB proxy, below); a key in `.env.local` or entered in the app goes to TMDB directly instead. A branch that adds a TMDB path is the exception: the edge worker answers 404 for a path it hasn't deployed, so until the branch merges it needs a key of your own, or `TMDB_PROXY_URL` at a local `wrangler dev` (The TMDB proxy, below). A qBittorrent login is needed only when qBittorrent's auth bypass is off, and the app's connect screen asks for it.

## Running

```sh
cp .env.example .env.local   # set QBITTORRENT_URL and PROWLARR_URL, or enter them in the app
npm install
npm run dev        # http://localhost:5173
npm test           # tests (Vitest)
npm run test:coverage  # the same with a coverage report
npm run lint       # linter (oxlint)
npm run typecheck  # type check
npm run build      # production build into dist/
npm run build:webui  # the Alternative WebUI build into dist-webui/public/, failing on a string qBittorrent would replace: point qBittorrent's Alternative WebUI at dist-webui/ (docs/ARCHITECTURE.md → The two builds)
npm run size       # the build's size against its budgets (docs/QUALITY.md)
npm run test:requests  # each screen's requests on opening and each move's between screens against their budgets, and each screen's layout shift on a phone and on desktop, after a build (docs/QUALITY.md, docs/TESTING.md)
npm start          # production server over dist/
npm run test:visual  # screenshot tests in Docker (docs/TESTING.md)
```

The screenshot tests keep the container's `node_modules` in a Docker volume per checkout, so worktrees can run them at once; a volume goes away by itself once its checkout's folder does ([TESTING.md](TESTING.md) → Screenshot tests).

The dev server has the same routes as production: `/qbt`, `/prowlarr`, `/tmdb`, `/tmdb-img`, `/api/settings`. CI runs every check of [Before pushing](#before-pushing) on every PR whatever the change (the tests with coverage, whose totals land in the job summary), and also builds the Alternative WebUI; the budgets (the build's size, each screen's requests on opening and each move's between screens, each screen's layout shift on a phone and on desktop) run in its `performance` job (`npm run size` and `npm run test:requests`, [QUALITY.md](QUALITY.md) → The size budget and The requests budget, [TESTING.md](TESTING.md) → The layout shift test), runs the screenshot tests, the smoke journeys and the WebUI's smoke journeys through a real qBittorrent ([TESTING.md](TESTING.md) → The WebUI's smoke journeys), and builds and smoke-tests the Docker image. `npm run test:mutants` runs locally before a PR is marked ready, and in CI on every push to a ready PR's head, cancelling a run for an older one ([TESTING.md](TESTING.md) → A test that can fail). The service worker is off in `npm run dev`: try it with `npm run build && npm run preview`.

### Before pushing

This is the list of what to run before pushing, which [CLAUDE.md](../CLAUDE.md) and [CONTRIBUTING.md](../CONTRIBUTING.md) point to. Always: `npm run lint`, `npm run typecheck`, `npm run test:coverage` (the tests with the coverage threshold), `npm run build` and `npm run size` (the build against its size budgets). Then, when the change touches it:

- `npm run test:requests` (each screen's requests on opening and each move's between screens against their budgets, and each screen's layout shift on a phone and on desktop, after the build) when a screen's data or what it loads changes;
- `npm run test:smoke` (the smoke journeys in Chromium) when a flow changes;
- `npm run test:smoke:webui` (the WebUI's smoke journeys through a real qBittorrent, in Docker) when the WebUI build's login, its calls to qBittorrent or what it keeps in qBittorrent change;
- `npm run test:visual` (in Docker) when the UI changes.

`npm run guard` shows what the checks guard will mark in the PR ([QUALITY.md](QUALITY.md) → What it marks).

## Server configuration

The server reads environment variables (from `.env.local` in development). Whatever is entered in the app is saved to `$KINOPEER_DATA_DIR/settings.json` and wins over the environment.

| Variable | Default | Purpose |
| --- | --- | --- |
| `QBITTORRENT_URL` | none | qBittorrent Web UI address; wins over one saved from the app. Without it, the app asks for the address on its connect screen and Settings changes it, behind Kinopeer's own login (`KINOPEER_AUTH` on); with the login off it's required |
| `QBITTORRENT_USERNAME`, `QBITTORRENT_PASSWORD` | none | Optional default login; qBittorrent's auth bypass needs none, and without these the app asks for one. A login entered in the app wins. Used only with `QBITTORRENT_URL`, never at an address saved from the app; without it the server says at startup that they're ignored |
| `PROWLARR_URL` | none | Prowlarr address; wins over one saved from the app. Without it, onboarding asks for the address with the key, behind Kinopeer's own login, and can skip it; Settings changes it |
| `PROWLARR_API_KEY` | none | Prowlarr API key; a key entered in the app wins. Used only with `PROWLARR_URL`, never at an address saved from the app; without it the server says at startup that it's ignored |
| `PROWLARR_CONFIG_XML` | none | Path to Prowlarr's `config.xml` to read the key from when neither a key entered in the app nor `PROWLARR_API_KEY` is set (the Umbrel package does this); like `PROWLARR_API_KEY`, only with `PROWLARR_URL`, and without it named at startup as ignored |
| `TMDB_API_KEY` | none | Fallback TMDB key, not needed with the proxy (development included); a key entered in the app wins |
| `TMDB_PROXY_URL` | the release worker, `https://tmdb.kinopeer.com/3` (edge images and the dev server: the edge worker, from `KINOPEER_TMDB_PROXY`) | Kinopeer's TMDB proxy for calls without a key (The TMDB proxy, below); empty turns it off, and the app asks for a key. `npm run build:webui` bakes it (or `KINOPEER_TMDB_PROXY`) into the WebUI bundle at build time, the release worker by default, not the dev server's edge worker. The integration and smoke tests set it empty or to the worker in front of their fake. |
| `TMDB_API_URL` | `https://api.themoviedb.org/3` | TMDB's API address; the integration and smoke tests point it at a fake |
| `TMDB_IMAGE_URL` | `https://image.tmdb.org/t/p` | TMDB's image address, the same way |
| `TELEGRAM_API_URL` | `https://api.telegram.org` | Telegram's Bot API address, for notifications (ARCHITECTURE → Notifications); the integration tests point it at a fake. The server has to reach it for Telegram notifications to work |
| `PUSH_TEST_ORIGIN` | (none) | A push service's origin the server sends Web Push to besides the browsers' own (ARCHITECTURE → Notifications), for the tests' fake service only; any http(s) origin. Leave it unset elsewhere. The server has to reach the browsers' push services (Google's, Mozilla's, Apple's, Microsoft's) for push notifications to work |
| `KINOPEER_DATA_DIR` | `./data` (`/data` in the image) | Where `settings.json`, `matches.json`, `auth.json` (the login's password hash and sessions) and `push.json` (the push notifications' key pair and devices) are kept; the dev server refuses to serve it (`server.fs.deny` in `vite.config.ts`), unless it's under `public/`, which Vite serves without that check |
| `KINOPEER_ALLOWED_HOSTS` | none | Host names the server answers at besides IP addresses, `localhost`, `*.local`, `*.onion`, `*.home.arpa`, `*.internal` and names of one label: names (`kinopeer.example.com`) and domains of your own with every name under them (`.example.com`: two labels or more, and not a shared dynamic DNS or hosting domain such as `.duckdns.org`, under which anyone can register a name; a domain of one label, such as `.lan`, is ignored with a warning, so list its names: `kinopeer.lan`), separated by commas or spaces; `*` answers at any name (the Umbrel package, whose gateway signs in first). Others get a 403 that names the variable (`docs/ARCHITECTURE.md` → The host check). A reverse proxy in front has to pass the name the page was opened at: keep `Host` (nginx: `proxy_set_header Host $host`) or send `X-Forwarded-Host`; nginx's default sends the upstream's address and no `X-Forwarded-Host`, so the check sees only that |
| `KINOPEER_AUTH` | `on` | Kinopeer's own login (ARCHITECTURE → Kinopeer's own login): `off` only where something in front asks for a login, as the Umbrel package does behind Umbrel's. Any other value stops the server, so a typo never leaves it open. The integration tests and the smoke journeys turn it off but for their own login tests |
| `KINOPEER_PASSWORD` | none | Kinopeer's password, in place of one set in the app, which can't change it then: 8 to 256 characters, as one set in the app, else the server doesn't start, since a longer sign-in is refused unsent. Changing it signs every browser out; removing it keeps its password until it's changed in the app |
| `PORT`, `HOST` | `8080`, `0.0.0.0` | Where the production server listens |
| `KINOPEER_CONTAINER` | none (`1` in the image) | Says the server runs in a container, beside Docker's `/.dockerenv` and Podman's `/run/.containerenv`, for the setup hints of a container (`docs/ARCHITECTURE.md` → Hints for Kinopeer in a container) |
| `KINOPEER_DIST` | `../dist` | What the production server serves |

The dev server has the login on too, so the first page you open asks you to set a password, which it keeps in `./data/auth.json`; `KINOPEER_AUTH=off` in `.env.local` turns it off. A forgotten password: stop the server, delete `auth.json` from the data directory and start it again, and the next visitor sets a new one; setting `KINOPEER_PASSWORD` and restarting works too. Either signs every browser out. On Umbrel the login is off, so there's nothing to reset.

## Docker

The image is built from `Dockerfile` (`node:24-alpine`, pinned by digest, no `node_modules`). `/healthz` answers `ok` while the server runs.

`docker-compose.yml` is the install the README describes, which an install downloads from its release (`release.yml` attaches it to each GitHub Release), so the file always goes with an image that's out: Kinopeer's released image at its major version's tag (`:1`, which `release.yml` pushes with each release, so a new major moves the file's tag too), beside qBittorrent's and Prowlarr's images at `latest`, which an install follows with `docker compose pull`, so they aren't pinned by digest as CI's images are. A script in qBittorrent's `entrypoint` runs it, on every start, as the owner of the downloads folder (`stat` on `/downloads`), so the files are the person's with nothing to set; a folder root owns (one Docker made because it was missing, and every bind mount on Docker Desktop, which gives the files to the person anyway) gets 1000:1000 rather than qBittorrent as root, and `PUID` and `PGID` in `.env` each override their half of it, which the README names only for rootless Docker and Podman (`0`, which they map to the person). On qBittorrent's first start the same script writes the settings the image would write itself, plus an auth bypass for Kinopeer's fixed address alone (`172.30.97.10/32` on the file's own network, outside the `ip_range` Docker gives the other containers their addresses from, so none of them can take it), so Kinopeer gets in without a login while qBittorrent has no password but the temporary one it makes up on every start; settings that exist are left alone. `docker-compose.test.ts` runs that script and checks what ties the services together (the address and the range, the ports, Prowlarr's config mounted read-only, the image's tag against `package.json`'s major version, the release's asset); starting it in Docker is checked by hand ([RELEASE_CHECKLIST.md](RELEASE_CHECKLIST.md)).

Unraid's Community Applications installs the image through `unraid/kinopeer.xml`, with CA's `ca_profile.xml` at the repository's root, where CA's submission requires it. CA rereads the template from `main`, so a change merged there reaches Unraid's Apps tab with CA's next catalog build, and a release needs no change to it: its `:1` tag moves with each release, as the Compose file's does. So the template describes the released `:1`, not `main`'s code: a template change that relies on behavior no release has yet stays a draft until `release.yml` has pushed that release's `:1`, since the release PR merges before the tag and a ready PR merges once the deputy approves it; and the template's first submission to CA waits for 1.2.0, the first `:1` with Find (#511), which the template's Overview and qBittorrent's address description promise, and the container hints (#509). `unraid/template.test.ts` is the check of every change to it, in CI: its port and data folder against the `Dockerfile`'s `EXPOSE` and `VOLUME`, each variable one the server reads, the real server started with the template's defaults, its icon on `main`, its licence `package.json`'s and its Requires marked as CA links them; `unraid/xml-files.test.ts` checks its screenshots on `main`, since Stryker's sandbox has no `docs/`, and that the repository has no other XML file, since CA clones the repository and reads every XML file in it as a template (its feed lists other repositories' Android manifests as "Not an unRaid Application"). Nothing checks it on Unraid itself (`docs/TESTING.md` → Known blind spots). Listing it in CA is the owner's step, after 1.2.0's tag, and #512 stays open until CA lists it, moved to the next milestone at 1.2.0's release (Releasing, step 5): CA's submission form, where its Validate and Scan check the repository. CA's application policies (https://forums.unraid.net/topic/87144) ask the maintainer to confirm GitHub's 2FA, which is on for the `kinopeer` organization, and renaming or moving the repository can get its listing removed.

TrueNAS's apps catalog installs the released image through an entry in TrueNAS's own repository, [truenas/apps](https://github.com/truenas/apps), in `ix-dev/community/kinopeer` (its community train, added by [truenas/apps#6683](https://github.com/truenas/apps/pull/6683)). TrueNAS's maintainers keep it: the entry pins an exact version by digest, and their Renovate bot opens the PR that moves it after each release, so a release needs no step for it. A change to what the entry sets (a new option in its install form, another port or user) is a PR to `truenas/apps`, which their CI and maintainers review; the README's TrueNAS section names the form's options, so it changes with it. Nothing in this repository checks the entry. What it relies on is the server's `PORT`, `KINOPEER_DATA_DIR`, `KINOPEER_PASSWORD`, `QBITTORRENT_URL` and `PROWLARR_URL`, the `/healthz` healthcheck, and running as any non-root user (568:568 by default). A release that changes any of these needs the entry changed too ([RELEASE_CHECKLIST.md](RELEASE_CHECKLIST.md)). The entry pins the released image by digest, so its change goes into Renovate's PR for that release, or onto it, rather than ahead of it; otherwise the release keeps the old setting working for one version.

To check a build against real qBittorrent and Prowlarr, `docker-compose.build.yml` runs the image built from the checkout in place of the released one:

```sh
docker compose -p kinopeer-check -f docker-compose.yml -f docker-compose.build.yml up -d --build
```

`-p kinopeer-check` keeps its containers and volumes apart from an install of the same file on the machine (both would be the `kinopeer` project), but not its ports and network range: with such an install running, `up` fails with "port is already allocated" or "Pool overlaps", so stop it first (`docker compose stop` in its folder). Downloads go into `./downloads` in the checkout, which git ignores, unless `DOWNLOADS_DIR` says otherwise; so does a `.env` there, which the dev server reads too. `docker compose -p kinopeer-check down --volumes` removes the containers, the network and the volumes, and leaves `./downloads`.

## The Alternative WebUI

`npm run build:webui` builds the Alternative WebUI into `dist-webui/public/` (ARCHITECTURE → The WebUI build). To try it, point a qBittorrent 5.2.0 or later at `dist-webui/` as the README's [Install as qBittorrent's Alternative WebUI](../README.md#install-as-qbittorrents-alternative-webui) says, with the folder's absolute path (or its path in qBittorrent's container), and reload qBittorrent's address after each build; that section also has the way back to qBittorrent's own interface. The build bakes in the TMDB proxy as the [`TMDB_PROXY_URL` row](#server-configuration) says, the release worker by default, which runs what the last release deployed and answers only pages on private origins, so a release's zip on a `localhost` qBittorrent gets TMDB without a key. A build of `main` may call what that worker doesn't have yet: build it with `TMDB_PROXY_URL=https://tmdb-edge.kinopeer.com/3` on the command line, which wins over `.env.local`, for the edge worker `edge.yml` deploys from `main` (`TMDB_PROXY_EDGE` in `server/main.ts`), or enter a key of your own. `npm run test:smoke:webui` runs its journeys through a real qBittorrent in Docker ([TESTING.md](TESTING.md) → The WebUI's smoke journeys), and each release attaches the build as `kinopeer-webui.zip` (Releasing, below).

## Releasing

First go through [RELEASE_CHECKLIST.md](RELEASE_CHECKLIST.md) → Before every release (the suite's health, the checks by hand); the release PR notes what it found.

1. In a PR, set `version` in `package.json` and `package-lock.json` (`npm version 0.2.0 --no-git-tag-version`) and add a `## 0.2.0 - YYYY-MM-DD` section to `CHANGELOG.md`. Update the "as of version" line at the top of `docs/SPEC.md` too.
2. After it merges, tag `main` and push the tag: `git tag v0.2.0 && git push origin v0.2.0`.
3. The `Release` workflow builds `ghcr.io/kinopeer/kinopeer` for `linux/amd64` and `linux/arm64` (for 1.1.0 the tags `1.1.0`, `1.1`, `1` and `latest`), without the GitHub Actions cache (any job on `main` can write to it, and the release image goes to every install) and without QEMU, since the `Dockerfile`'s runtime stage runs nothing on the target platform, and creates a GitHub Release with that version's changelog section, the image digest and `docker-compose.yml`, which the README's Compose install downloads from the latest release, and `kinopeer-webui.zip`, the Alternative WebUI, built in a read-only job of its own (`docs/ARCHITECTURE.md` → Shipping it). Then it deploys the `kinopeer-tmdb` worker from the tag (The TMDB proxy, below). It fails if the tag doesn't match `package.json` or the changelog has no section for the version.
4. Wait for the `Release` workflow's `proxy` job to pass and for `https://tmdb.kinopeer.com/3/configuration` to answer 200 (the release image calls that worker, and nothing before the tag tries it: Kinopeer Edge calls the edge worker). Then update the Umbrel package (below); TrueNAS's catalog follows by itself (above).
5. Close the version's [milestone](https://github.com/kinopeer/kinopeer/milestones). An issue still open in it moves to the next milestone or is closed as not planned, with the reason.

The image is public, so Umbrel can pull it without a login.

## Umbrel package

The package lives in [umbrel-homelab-store](https://github.com/MrShakhov/umbrel-homelab-store), in `homelab-kinopeer/`. It sets the qBittorrent and Prowlarr addresses, the default qBittorrent login and `KINOPEER_ALLOWED_HOSTS: "*"` (from the release after 1.0.0: Umbrel's gateway keeps the `Host` a person typed, which may be any name of theirs, and signs in first, so the host check has nothing to add there), and mounts Prowlarr's config folder read-only. From the first release with Kinopeer's own login it also sets `KINOPEER_AUTH: "off"`, since Umbrel's login is in front: that release's store PR adds it to `docker-compose.yml`, and without it the update would ask every Umbrel user to set a password behind Umbrel's own. After a release, bump `version` and `releaseNotes` in `umbrel-app.yml` and the image tag and digest (from the GitHub Release) in `docker-compose.yml`. Umbrel then offers the update. Umbrel shows whatever the `icon:` URL in an app's `umbrel-app.yml` points at, a raw GitHub link to an `icon.svg` kept in a store repository, so each app's icon is a copy of `scripts/icons/icon.svg` there: when the icon changes, the copy is replaced, or the app's `icon:` is pointed at a new one.

## Edge builds

Kinopeer Edge is `main` running on the owner's Umbrel next to the released app, so changes get used day to day before a release. The `Edge` workflow (`.github/workflows/edge.yml`) runs on every push to `main` that changes what goes into the image (its `paths` list: the app's and the server's sources without their tests, `public/`, the build config), and only the newest of several pushes in a row is built:

1. It deploys the `kinopeer-tmdb-edge` worker from that commit (The TMDB proxy, below).
2. It takes the build's fingerprint (`scripts/edge/fingerprint.ts`), a hash of what the image would run and of how it's built: the app built without the commit, the server bundled and minified by Vite (only for the hash: the image runs the sources), the `Dockerfile` without its comments, `package.json`'s `type` and `version`, the TMDB proxy address, and `.dockerignore` and `edge.yml` whole, so a change to the build's context, the BuildKit pin or the actions that build the image builds, and the next Edge run tries it first as the release checklist and TESTING count on. It does so in a job with no secrets and nothing to write, since that job installs the dependencies and builds on the runner. When the image the edge store points at carries the same fingerprint (its `com.kinopeer.fingerprint` label), the run stops here: a change to a comment, a test helper, a script or dev dependency in `package.json` or a tool's config that leaves the build alone offers no update. Otherwise the log names the fingerprint it found beside this commit's, and an image it can't read builds anyway.
3. It builds `ghcr.io/kinopeer/kinopeer` for `linux/arm64` only (the Raspberry Pi), tagged `edge` and `sha-<commit>`, with that fingerprint as its label and without a provenance attestation, which release images keep. The build passes `KINOPEER_COMMIT`, so Settings → About and bug reports show the version with the commit, `0.6.0+abc1234`; release images leave it out.
4. It commits to the edge store, [umbrel-homelab-edge](https://github.com/MrShakhov/umbrel-homelab-edge) (store id `homelab-edge`, app `homelab-edge-kinopeer`, port 8798): the image by tag and digest in `docker-compose.yml`, and in `umbrel-app.yml` that version and the commit subjects since the previous edge build as release notes. It pushes with a deploy key that can write to that repository only, kept in the `EDGE_STORE_DEPLOY_KEY` secret of the `deploy` environment (The TMDB proxy, below).
5. umbrelOS checks community stores every 5 minutes and offers an update whenever the version differs from the installed one; the owner installs it from the App Store.

Nothing in the edge store is edited by hand but the manifest's links (`repo`, `website`, `support`) and two variables in `docker-compose.yml`'s `web` service that Umbrel's sign-in in front calls for: `KINOPEER_ALLOWED_HOSTS: "*"` (the host check, as in the released package below, since Umbrel's gateway keeps the `Host` a person typed), and `KINOPEER_AUTH: "off"` (Kinopeer's own login, as in the released package below). The workflow writes none of them: it rewrites only `.services.web.image`. Its package is the released one's with another id, name and port: it keeps its own settings and torrent-to-title matches, and works with the same qBittorrent and Prowlarr, so what it does to torrents is real. The store only moves forward: a run for a commit the store already has (a re-run of an older push) builds nothing and leaves it as it is. When a run's store step failed, re-run it, or run the workflow from the Actions tab (`workflow_dispatch`), which builds main's head and ignores other branches.

## The TMDB proxy

Kinopeer's own TMDB key sits behind a Cloudflare Worker, `tmdb-proxy/worker.ts`, for installs that have no key of their own; SPEC's decision log (2026-11-04) says why a key can't ship in the image. The worker takes TMDB's paths under `/3/`, answers only GET and HEAD, and OPTIONS (a CORS preflight), for the ones `src/api/tmdb/client.ts` calls (404 for the rest), adds the key, and limits the calls that reach TMDB to 100 per IP in 10 seconds, an IPv6 caller counted by its /64 (`limitKey`), since one client gets a whole /64 and could take a new address in it for every call. That limit is soft: Workers' rate limiting counts in each instance and syncs in the background, and on the deployed worker 500 calls at 20 a second from one IP all went through (2026-11-04). What bounds a script is the path list, the cache and the Free plan's daily cap; a strict limit would be a WAF rule on `kinopeer.com` or a counter in a Durable Object. Workers Cache, in front of the worker, keeps TMDB's answers for an hour (searches) to a day (a title's page) by the `s-maxage` the worker sets, and runs the worker only on a miss; the older Cache API (`caches.default`) does nothing on `workers.dev`. The cache is shared across the worker's versions (`cross_version_cache`), since every deploy makes one: a change to what an answer looks like reaches the answers already kept within their time, a day at most, or perhaps two where the cache's tiers each keep an entry for its time from when they stored it, which Cloudflare's docs don't say. For that the worker passes TMDB's validators (`ETag`, `Last-Modified`) on no more and gives each answer it makes an `ETag` of its own, from the time it was made: by Cloudflare's [Revalidation](https://developers.cloudflare.com/cache/concepts/revalidation/), a refresh with a new `ETag` replaces the cached entry, while a 200 that repeats the cached `ETag` "does not reliably replace the old content". With TMDB's `ETag`, which doesn't change for `/3/configuration`, that entry was refreshed and kept the headers it was stored with before #565, with no CORS, for days after (seen in the zone's analytics and with `curl`, #617). A `Last-Modified` of its own would replace the entry as well, but with no `max-age` a browser keeps an answer that has one fresh by heuristic, for a tenth of its time since then (RFC 9111 §4.2.2; Chromium, Firefox and WebKit do), and Kinopeer's server passes it on with no `Age` (1.3.0 and before, which stay in use, among them), so the browser would answer Settings' check itself while the proxy fails. With an `ETag` alone a browser keeps the answer fresh for no time, since `s-maxage` binds only shared caches, and Settings' check still asks the proxy. The worker can't be told to empty its cache from outside (Workers Cache is purged only from inside a worker, `ctx.cache.purge`, and this one has no route for it), so to get rid of a bad answer sooner, deploy with `cross_version_cache` set to `false`, which puts the version back in the key, and leave it off for a day: switched back on sooner, the answers kept without the version are served again while within their time. Errors, the worker's own refusals (a 429 included) and HEAD answers are `no-store`; TMDB's own 429 keeps the `Retry-After` it carries, which the worker passes on as a positive whole number of seconds, ten minutes at most, and leaves out in any other form (`src/logic/retryAfter.ts`, the client's rule too; released clients take it as sent, and every install on the key shares it), so the title lookups wait as long as TMDB asks, up to ten minutes; TMDB's [rate limiting](https://developer.themoviedb.org/docs/rate-limiting) page asks to respect a 429 but doesn't say it sends one, and without it the lookups wait their own 10 seconds (#619). CORS headers go only to a page on a private origin (`isPrivateOrigin` in `src/logic/privateOrigin.ts`, which the WebUI build shares, so a change to it also changes where that build asks for a TMDB key of the user's own): an IP address in a private, loopback, link-local or CGNAT range (`::1`, `fc00::/7` and `fe80::/10` for IPv6), `localhost` and `*.localhost`, `*.local`, `*.home.arpa`, `*.internal`, or a name of one label, as Kinopeer is at when qBittorrent serves it as its Alternative WebUI; a page on a public origin gets none, so it can't read the answers and a public site can't use the shared key as the TMDB backend of its own pages. It can still send the calls, since a GET with no custom headers needs no preflight, and spend the Free plan's daily requests with them, as a script can. An install on a public domain (a seedbox) uses a TMDB key of its own (SPEC's decision log, 2026-11-22). Such a page may read `Retry-After` (`Access-Control-Expose-Headers`), and a preflight (`OPTIONS`) for a path the worker serves gets a 204 with the methods, kept by the browser for a day, without the key, the limit or TMDB; it names no allowed request headers, so it admits nothing until a client needs one and its name is added (the client's GETs need none). Every answer says `Vary: Origin`, which Workers Cache honors, keeping an answer per distinct `Origin`, so no page gets another origin's headers from the cache; the cost is that each such install's pages fill a variant of their own, while Kinopeer's server, which sends no `Origin`, shares one. It keeps no request logs. Its tests run in the `server` Vitest project, and those of the origin rule and the Retry-After rule it shares in the `app` project.

Both workers run on Cloudflare's Free plan, which allows 100,000 requests a day for the whole account, cache hits included (a hit doesn't run the worker or meet its limit, but it counts). Over that, the workers answer with an error until midnight UTC, so every install without a key of its own loses TMDB for the rest of the day; installs with their own key don't notice. Cloudflare's dashboard shows the daily count per worker.

It runs as two workers, the environments in `tmdb-proxy/wrangler.jsonc`, each going out with the builds that call it:

| Worker | Address | Called by | Deployed by |
| --- | --- | --- | --- |
| `kinopeer-tmdb-edge` | `https://tmdb-edge.kinopeer.com` | Kinopeer Edge | the `Edge` workflow, before the edge image (its `paths` include `tmdb-proxy/`), when the worker's fingerprint differs from the version it runs (below), also on a run that publishes no image because the image's fingerprint is the store's |
| `kinopeer-tmdb` | `https://tmdb.kinopeer.com` | released versions | the `Release` workflow, after the image and the GitHub Release, when the worker's fingerprint differs from the version it runs |

Both addresses are Workers Custom Domains: a worker's first deploy with one creates its DNS record and certificate, which needs `kinopeer.com` in the same Cloudflare account as the workers and a token that can edit Workers routes on that zone. Neither worker is on `workers.dev`, so the address released versions call doesn't change with the Cloudflare account's name. The edge worker was on `kinopeer-tmdb-edge.kinoseed.workers.dev` until the domain was bought (#259); nothing released called it there.

Kinoseed's workers from before the rename, `kinoseed-tmdb` and `kinoseed-tmdb-edge` on `kinoseed.workers.dev`, were deleted on 2026-11-06 (SPEC's decision log), so Kinoseed up to 0.7 has TMDB only with a key of its user's own.

In front of both workers, a WAF custom rule on the `kinopeer.com` zone, "Only the TMDB proxy's paths" (Security → Security rules in Cloudflare's dashboard, added by hand on 2026-11-06, not deployed from here), blocks every request to their hosts whose path doesn't start with `/3/`, except `/robots.txt`. Scanners found `tmdb-edge.kinopeer.com` in the certificate logs within hours of its first deploy (450 of its first 479 calls were 404s), and with the rule they get a 403 from Cloudflare without running a worker or counting against the Free plan's requests. Its expression, `starts_with` because scanners send the host with a port:

```
(starts_with(http.host, "tmdb.kinopeer.com") or starts_with(http.host, "tmdb-edge.kinopeer.com")) and not starts_with(http.request.uri.path, "/3/") and http.request.uri.path ne "/robots.txt"
```

A path the client calls outside `/3/` (TMDB's v4 API, say) needs the rule widened before a build that calls it goes out.

Both call `.github/workflows/tmdb-proxy.yml`, which has no trigger of its own, so a change to when Edge or Release runs changes when its worker goes out too. It deploys only when the proxy's code (every file Wrangler bundles into the worker, as its `wrangler deploy --dry-run --metafile` names them, so an import from `src/` counts without being listed; `tmdb-proxy/` without its tests, for what Wrangler reads there without naming it, such as its `package.json`; the root `tsconfig.json` and `package.json`; and the files that say how it's deployed, `tmdb-proxy.yml` among them, the same `BUILD_FILES` as its fingerprint below. A module a bundled file imports that Wrangler uploads beside the bundle (by its module rules, such as an `.html`, `.txt`, `.sql`, `.bin` or `.wasm` import, wherever it sits) fails the run, since the metafile names it only by a hash: a worker that needs one changes `tmdb-proxy/deployCheck.ts` first, to name its file) is the same as at main's head or the highest version tag, a release above its prereleases, so a re-run of an older push or tag leaves the worker as it is, while a run isn't skipped because main moved on with a change Edge doesn't build; `tmdb-proxy/deployCheck.ts` decides, with its tests. Then it deploys only when the worker would change: `tmdb-proxy/fingerprint.ts` hashes the bundle that dry run made (every module in it, but not its README and source maps, which differ on every build), what says how it's deployed (`wrangler.jsonc`, `tmdb-proxy/package-lock.json` with Wrangler's version, and `tmdb-proxy.yml` itself, so a Wrangler update or a change to the deploy deploys rather than only being bundled), and the job compares the hash with the tag of the version the worker runs (`wrangler deployments status`, then `wrangler versions view`). The same tag leaves the worker without a new version, with a notice in the run, and applies its routes again (`wrangler triggers deploy`, which makes no version): a deploy attaches the Custom Domain and sets workers.dev and Preview URLs only after the new version is live, so one that failed there (a token without Workers Routes on the zone, say) is put right by the next run, or fails it again; a change to them in the dashboard is undone the same way. (A DNS record or another worker's domain on the worker's hostname doesn't fail a run: Wrangler replaces it when it runs outside a terminal, as in CI.) The worker's script settings aren't among what it applies, observability and Workers Cache among them: logs turned on or the cache turned off in the dashboard stay so until the worker's next deploy, which a change to `wrangler.jsonc` brings. Another tag, none, or two versions sharing the traffic deploy, and so does a version it can't read, with a warning in the run; the new version gets the hash as its tag (`wrangler deploy --tag`). The key doesn't count, so nothing derived from it goes into a tag Cloudflare shows: a key changed in the `deploy` environment reaches the workers through the `TMDB proxy key` workflow (below), and with the next deploy. Wrangler comes from `tmdb-proxy/package-lock.json` (`npm ci` in that folder), and the Cloudflare token is only in the steps that call Cloudflare, not while npm installs it. A change to `tmdb-proxy/` alone also starts the Edge run, since Kinopeer Edge is a commit of `main` with its worker; the run deploys the worker when the worker's fingerprint changed, and publishes an image only when the image's did (Edge builds, above).

The workers' paths are a contract with every released version: a path is only added, never removed or changed in what it answers, while a supported version calls it. Changing the cache times, the limit or the key is fine. A change that breaks it (a path dropped, another answer, a check old versions don't pass) goes into a new worker, `kinopeer-tmdb-v2`, that the release with the change calls, while the old one keeps serving the versions before it; it's removed once Cloudflare's request counts show no calls for a month (Umbrel doesn't update apps by itself, so old versions stay). Those counts are the zone's GraphQL Analytics, `httpRequestsAdaptiveGroups` filtered on the worker's host (`clientRequestHTTPHost`), which on the zone's Free plan reach 31 days back, 30 days at most in one query. A path or a worker goes only when, grouped by `clientRequestPath` and `userAgent`, nothing but scanners calls it, whatever the answer (a browser may get a 304, anyone the limit's 429). Who calls: a Kinopeer server from 1.4.0 says `Kinopeer/<version>` (`server/tmdb.ts`), and `node` is a server released before it, Node's own `User-Agent`; the WebUI build's calls carry the browser's own, with no version; an edge image pointed at the release worker with `TMDB_PROXY_URL` shows as the release it was cut after. Scanners mostly ask paths outside `/3/`, which the WAF rule above refuses with a 403, or `/3/` paths the worker doesn't serve, which it answers 404; one with a browser's agent on a served path looks like the WebUI and keeps the path, which errs on the safe side. The `lets %s through` test in `tmdb-proxy/worker.test.ts` lists the paths and fails when one goes.

Deploying needs three secrets of the `deploy` environment (Settings → Environments), set in the GitHub web UI: `CLOUDFLARE_API_TOKEN` (a token from the "Edit Cloudflare Workers" template), `CLOUDFLARE_ACCOUNT_ID` and `TMDB_API_KEY` (Kinopeer's key, a v3 key or a v4 read access token). Without them the proxy job fails, and the edge image waits for it. The key reaches each worker as its secret, never the code or a log: the deploy uploads it with the code as one version (`wrangler deploy --secrets-file`, from a file only the runner's user can read, deleted after), so Cloudflare lists one deployment per run and a new worker never runs without it, and `secrets.required` in `wrangler.jsonc` makes a deploy fail rather than go out without the key. To replace a leaked or revoked key, change `TMDB_API_KEY` in the `deploy` environment and run the `TMDB proxy key` workflow from the Actions tab (`.github/workflows/tmdb-proxy-key.yml`), which puts it into both workers without a deploy: installs keep working without a release. A run of Edge or Release doesn't do it, since it leaves a worker whose code hasn't changed as it is.

Every deploy secret lives in that one environment, `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, `TMDB_API_KEY` and the edge store's `EDGE_STORE_DEPLOY_KEY`, none in the repository's secrets. Its deployment rules (Settings → Environments → `deploy` → Deployment branches and tags: "Selected branches and tags", a branch rule `main` and a tag rule `v*`) let only the `main` branch and `v*` tags use it, so a workflow on any other branch, a pushed one included, can't read them, and PRs (forks' and Dependabot's too) never could. The jobs that name it are `tmdb-proxy.yml`'s `deploy` (its callers pass the three by name), Edge's `edge` and `tmdb-proxy-key.yml`'s `key`; Release's `release` job needs only the workflow's token. A new job that needs one of them names `environment: deploy` too.

To try the worker locally, run `npm ci` and then `npx wrangler dev` in `tmdb-proxy/`, with the key in `tmdb-proxy/.dev.vars` (`TMDB_API_KEY=…`, git-ignored), and call `http://localhost:8787/3/configuration`. The top level of `wrangler.jsonc` is `kinopeer-tmdb-local`, so a deploy without `--env` makes a worker nobody calls instead of replacing the release one.
